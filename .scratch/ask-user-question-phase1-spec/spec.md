# Spec: 主子智能体 AskUserQuestion 状态解耦与交互体验优化（第一阶段）

Triage Label: `ready-for-agent`

## Problem Statement

在当前企业级数据查询会话系统中，当主智能体或 SQL 专家子智能体遇到口径模糊、缺少车身 FIS 号等关键参数而调用 `AskUserQuestion` 挂起（LangGraph Interrupt）等待用户输入时，前端的展示层存在严重的**状态语义混淆**：

1. **误导性恐慌文案**：系统在挂起等待用户澄清时，外层消息气泡顶部生硬地显示 **“已停止生成”**（琥珀色警示文本），子智能体卡片标签显示 **“已中断”**（配黄色警告感叹号）。用户看到后会误以为系统遭遇了网络故障、超时崩溃或任务被强制终止，进而产生操作困惑与焦虑。
2. **双重矛盾的视觉表现**：在同一条消息气泡中，顶部声明“已停止生成”，底部却展示着让用户继续填写的 `AskUserQuestionCard` 交互卡片，形成了“既已终止、又让填写”的逻辑冲突。
3. **生命周期状态混淆**：在前端 Store 状态机中，将“等待人类输入（HITL Awaiting Input）”与“用户主动点击停止（User Abort）”共用了单一的 `isInterrupted` 标志位，无法根据真实场景做精细化、友好化的 UI 状态流转。

---

## Solution

在前端状态机与视图层彻底解耦**“挂起等待澄清（Waiting for Clarification）”**与**“主动终止/已停止（User Aborted）”**两种截然不同的生命周期：

1. **引入精确的状态判定与语义隔离**：
   - 当消息处于挂起状态且携带有待确认问题时（`hasQuestions`），系统将其判定为 **“等待确认态（Awaiting Clarification）”**，而非“已停止生成”。
   - 仅当用户主动点击“停止生成”按钮、或在澄清卡片中点击“取消”且没有待答复项时，才判定为 **“已停止生成/已取消”**。
2. **顶部状态 Banner 友好化**：
   - 等待确认态下，顶部显示温和友好的提示：“⏳ 等待您的确认” 或由统一的 `statusText` 驱动，采用柔和微光效果，消除红色/黄色警示感。
3. **子智能体卡片（SubagentCard）等待态优化**：
   - 子智能体在等待澄清时，状态标签展示为 **“等待确认”**（搭配平缓呼吸点），取代冷冰冰的“已中断”。
4. **提交与取消链路闭环**：
   - 用户提交回答后，卡片立即进入“已提交，恢复生成中...”并平滑过渡到下游流式响应；用户点击取消时，明确记录为“已取消”并结束任务。

## User Stories

1. As a 业务分析人员, I want 大模型在遇到需求不明确发起提问时看到“等待您的确认”提示, so that 我明确知道系统正在等待我输入，而不是系统崩溃或被中断。
2. As a 业务分析人员, I want SQL 专家子智能体提问时，其卡片标签显示“等待确认”, so that 我清晰了解子智能体当前的工作进展和停顿原因。
3. As a 业务分析人员, I want 看到清晰柔和的状态指示灯而非刺眼的黄色警告感叹号, so that 我在交互过程中保持舒适安心的心理体验。
4. As a 业务分析人员, I want 在消息顶部不再看到“已停止生成”与底部“填写问卷”同时出现的矛盾画面, so that 界面视觉与逻辑保持高度自洽。
5. As a 业务分析人员, I want 在点击“取消”按钮后界面准确显示“已取消/已停止”, so that 我清楚知晓任务已按我的意愿安全终止。
6. As a 开发者, I want 前端 Store 区分 `isInterrupted` 的具体诱因（等待提问 vs 用户主动 Abort）, so that 后续的流式恢复、重试与回放逻辑拥有清晰准确的状态边界。
7. As a 开发者, I want 子智能体在等待用户输入期间保持优雅的挂起状态，在用户恢复生成后能继续无缝流式输出, so that 多智能体协作链路完整可靠。

---

## Implementation Decisions

1. **状态判定逻辑解耦**
   - 在消息气泡组件与子智能体卡片中，抽象出 `isAwaitingClarification` 衍生状态：
     - 当满足 `isInterrupted && hasQuestions && !isQuestionSubmitted` 时，判定为等待澄清态。
     - 当满足 `isInterrupted && (!hasQuestions || isCanceled)` 时，判定为用户主动停止态。
2. **消息顶部状态栏重构**
   - 移除写死“已停止生成”的硬编码分支；
   - 根据计算状态分别渲染：
     - 等待澄清态：渲染带有温和呼吸动画的“等待您的确认”引导条；
     - 主动停止态：渲染“已停止生成”；
     - 普通流式态：由 `statusText` 驱动。
3. **Subagent 状态机扩展与标签映射**
   - 子智能体卡片组件在判定自身所处状态时，若父级或自身处于等待澄清态，将状态标签由 `已中断` 映射为 `等待确认`；
   - 将黄色警告感叹号图标调整为等待/交互图标（如时钟或微光点），视觉边框采用柔和的中性色/淡蓝色边框。
4. **提交与取消动作后的状态即时反馈**
   - 点击“确认并恢复生成”后，本地立即触发锁定并展示 loading 状态；
   - 点击“取消”后，传递取消意图，并在流式终止时正确落定为取消状态。

## Testing Decisions

### 良好测试的标准
- 聚焦组件与状态机的外部可观测行为（如渲染的文本、类名、按钮禁用状态、派发事件），不测试内部脆弱的实现细节。
- 确保测试在不同状态切换（Streaming -> Interrupt with questions -> Resume / Cancel -> Complete）时稳定断言。

### 重点测试范围
- `MessageItem.vue`：验证在有 `questions` 中断时顶部不出现“已停止生成”，且准确渲染等待提示；验证主动 Abort 时准确出现“已停止生成”。
- `SubagentCard.vue`：验证在中断等待输入时展示“等待确认”标签而非“已中断”警告。
- `AskUserQuestionCard.vue`：验证取消与提交事件的正常发射与状态禁用。

### 代码库现有先例 (Prior Art)
- `frontend/src/__tests__/MessageItem.spec.ts` 或现有聊天气泡组件测试规范。
