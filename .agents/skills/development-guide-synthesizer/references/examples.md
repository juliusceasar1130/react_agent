# 示例、关键点与易错点

## 一、建议给 LLM 的调用方式

当需要使用该技能时，可直接给出类似请求：

### 示例 1

“请根据这次开发和讨论内容，提炼成一份可复用的开发指南，要求包含：

- 背景
- 方案分层
- 关键调用链
- 关键设计取舍
- 易错点
- 复用模板
- 检查清单

文档放到 `backend/docs` 下，并同步更新 `README` 和 `changelog`。”

### 示例 2

“把这次功能实现沉淀成团队手册，不要只写 changelog，要写成以后还能复用的开发指南。请补模板、示例、关键点和常见错误。”

### 示例 3

“请把这轮开发内容总结成 troubleshooting + implementation handbook，结构清晰，保留踩坑、验证结果和后续优化建议。”

## 二、写作时必须覆盖的关键点

### 1. 背景

- 为什么做
- 不做会怎样
- 当时的约束是什么

### 2. 问题定义

- 这次到底解决了什么问题
- 是用户问题、工程问题，还是架构问题

### 3. 分层设计

- 系统被拆成了哪些层
- 每层负责什么
- 为什么这么分

### 4. 调用链

- 从输入到输出的真实处理链路
- 中间有哪些关键节点
- 最终返回什么

### 5. 关键取舍

- 为什么用 A，不用 B
- 当前方案的收益和代价

### 6. 踩坑与易错点

- 遇到过什么问题
- 根因是什么
- 下次如何避免

### 7. 验证

- 实际验证了什么
- 哪些还没有验证
- 风险边界是什么

### 8. 复用方式

- 哪些做法可以直接复制
- 哪些必须结合场景调整

## 三、常见错误写法

### 错误 1：写成 changelog

问题：

- 只记录“改了什么文件”
- 没写“为什么这样改”
- 没写“以后怎么复用”

修正：

- 增加背景、设计、取舍、复用清单

### 错误 2：写成泛泛经验贴

问题：

- 全是抽象原则
- 没有代码或调用链支撑
- 读完仍然不知道怎么落地

修正：

- 增加文件入口、执行流、示例和检查清单

### 错误 3：只写成功结果，不写坑

问题：

- 后续复用的人仍会重复踩坑

修正：

- 增加“实践中的关键经验”和“易错点/反模式”章节

### 错误 4：不区分事实与推断

问题：

- 容易把猜测写成确定事实

修正：

- 明确哪些是代码已验证
- 哪些是从讨论中归纳
- 哪些是面向未来的建议

### 错误 5：没有输出模板

问题：

- 下次还要重新想结构

修正：

- 固定模板
- 固定章节
- 固定检查清单

## 四、推荐的精简提示模板

如果只想快速调用该技能，可直接使用下面这段：

```text
请根据本次开发实现、讨论记录、关键代码和验证结果，提炼为一份可复用的开发指南手册。

要求：
1. 不要只写变更记录，要写成后续可以复用的实施手册
2. 必须包含：背景、问题、整体设计、调用链、分层职责、关键取舍、实践经验、易错点、检查清单、后续优化
3. 提供至少一个模板化示例
4. 明确哪些结论来自代码事实，哪些来自讨论归纳
5. 结构层次清晰，标题简短，适合沉淀到 docs
```

---

## 五、判断产出是否合格的标准

一份合格的开发指南，读完后应该满足：

- 能快速理解这次开发为什么这样做
- 能快速找到关键入口文件
- 能知道整条调用链如何运转
- 能知道哪些坑最容易重踩
- 能知道下次如何复用这套方案
- 即使不是原作者，也能继续维护或扩展
