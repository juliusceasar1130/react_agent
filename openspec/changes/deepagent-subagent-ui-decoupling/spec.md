# Feature Spec: Main Agent & Subagent Streaming and UI Decoupling

## Problem Statement

In the current data analytics chat assistant system, the execution information of the Coordinator (Main Agent) and domain Subagents (such as `sql_domain_agent`) is intermingled in a single, monolithic message container. 

Specifically:
- **Thinking/Reasoning Pollution**: Deep reasoning content generated by Subagents (e.g. schema probing, SQL construction thoughts) gets concatenated into the Main Agent's primary thinking accordion, resulting in confusing, cluttered reasoning timelines.
- **Tool Execution Interleaving**: High-frequency database execution tools (e.g., `sql_db_query`, `sql_db_schema`) are mixed together with the Coordinator's delegation tool (`task`), obscuring the delegation relationship and creating redundant output logs.
- **Dual Redundancy**: When a Subagent finishes, its full multi-thousand-word output is returned as the result of the `task` tool in the main bubble, while also appearing in the intermediate stream, causing massive duplication.
- **Lack of Subagent Context**: The user cannot easily distinguish which agent is performing which subtask, how long the domain agent's reasoning took, or what the intermediate SQL execution steps were.

## Solution

Decouple the Main Agent and Subagents across the streaming protocol, state management, and user interface layers:
1. **Scoped Stream Events**: The backend marks SSE events with session-scoped Subagent metadata (`subagent_id`, `subagent_name`) derived from task delegation call IDs and namespace analysis.
2. **Isolated Session State**: The frontend separates incoming tokens, reasoning traces, tool calls, and outputs into a dedicated `SubagentSessionState` bucket for each delegation instance.
3. **Dedicated Subagent Cards**: The UI renders a dedicated `SubagentCard` below the Main Agent bubble for each task delegation, featuring an independent status badge, isolated reasoning accordion with its own timer, domain tool execution list, and subagent output.
4. **Clean Coordinator View**: The Main Agent bubble retains only the high-level intent breakdown, delegation summaries, and synthesized final responses.
5. **Historical Replay & Persistence**: A complete Subagent session snapshot (reasoning, output, tool chain) is persisted in a dedicated `chat_messages.subagents` column (idempotent migration), with a `tool_calls`-based reconstruction fallback for legacy rows.

## User Stories

1. As a data analyst querying complex metrics, I want the system to show a dedicated SQL Assistant card when the Main Agent delegates a query, so that I can immediately tell when specialized domain execution begins.
2. As a user reviewing reasoning steps, I want the Subagent's deep thinking to be contained in its own collapsible panel, so that the Main Agent's strategic coordination thoughts are not cluttered with low-level SQL syntax generation details.
3. As a user waiting for a slow SQL query, I want the Subagent card to display an independent timer for its reasoning and execution, so that I know exactly how long the SQL domain agent took to analyze the schema and formulate queries.
4. As a developer debugging SQL generation, I want domain tools (like `sql_db_query` and `sql_db_schema`) to appear exclusively inside the Subagent card, so that tool call chains are clearly mapped to the worker executing them.
5. As a user reviewing the chat history, I want the Main Agent's `task` tool call to display as a concise delegation summary rather than printing thousands of redundant words in the main bubble, so that the chat feed remains clean and readable.
6. As a user asking a complex multi-step question that requires multiple SQL delegations, I want each delegation to render as an independent Subagent card, so that parallel or sequential queries do not overwrite or collide with each other.
7. As a user who cancels a query mid-flight by clicking Stop, I want already rendered Subagent cards to be preserved with an "interrupted" status, so that I can see the partial analysis and queries that were generated prior to cancellation.
8. As a user encountering a database execution error, I want the Subagent card to clearly display the error state within its tool chain without crashing the entire message bubble, so that I can inspect what failed.
9. As a user refreshing the browser or switching between sessions, I want all historical Subagent cards and their executed tools to be faithfully restored from the database, so that historical conversations preserve their complete execution context.
10. As a user asking a general question that does not require database querying, I want the message bubble to render cleanly without any empty or phantom Subagent cards, so that the interface does not feel over-engineered for simple chats.
11. As a user reviewing Subagent outputs, I want the Subagent's interim analysis and conclusions to be formatted in rich Markdown inside the Subagent card, so that tables and formatted figures are easy to inspect before reading the final synthesis.
12. As a user inspecting domain tools, I want to expand and collapse individual SQL queries and schema outputs inside the Subagent card, so that I can inspect raw SQL when needed while keeping the default view compact.
13. As a user viewing a long query session, I want Subagent thinking accordions to automatically collapse upon completion while retaining the ability to expand on demand, so that the focus shifts smoothly to the final answer.
14. As an operations engineer running offline or air-gapped deployments, I want all UI components and icons used in the Subagent card to load locally without external CDN dependencies, so that offline deployments remain 100% reliable.

## Implementation Decisions

### 1. Backend Event Scoping & Namespace Routing
- The backend event loop identifies Subagent events during graph streaming (`astream` with `subgraphs=True`, `version="v2"`).
- The routing mechanism reads the namespace (`ns`):
  - When `ns` is empty (`()`), the event belongs to the Coordinator (Main Agent).
  - When `ns` contains a `tools:<call_id>` prefix, the event is routed to the corresponding Subagent session.
  - The `subagent_id` is defined as the `call_id` of the Coordinator's `task` tool invocation (representing a unique delegation session).
  - The `subagent_name` is resolved from an in-memory lookup table (`active_task_targets[call_id]`) populated when the `task` tool is called. Unknown call IDs are left unmarked (with a warning) rather than silently attributed to a default agent.
- Metadata fields (`subagent_id`, `subagent_name`) are added to `TokenStreamEvent`, `ReasoningStreamEvent`, `StatusStreamEvent`, `ToolCallStreamEvent`, and `ToolResultStreamEvent` as optional fields. When `None`, serialization omits them, guaranteeing 100% backward compatibility.

### 2. Frontend State Isolation (Pinia Store & Composables)
- A new `SubagentSessionState` model is introduced:
```typescript
export interface SubagentSessionState {
  id: string // task call_id
  name: string // e.g. "sql_domain_agent"
  title?: string // human readable display name
  description?: string
  status: 'running' | 'completed' | 'error' | 'interrupted'
  reasoningText: string
  reasoningStartTime?: number
  reasoningEndTime?: number
  reasoningDuration?: number
  toolCalls: StreamToolCall[]
  toolResults: Record<string, string>
  content: string
  error?: string
}
```
- Both `StreamingMessage` and `Message` types are extended with a `subagents: Record<string, SubagentSessionState>` mapping indexed by `subagent_id` (the task `call_id`).
- The streaming event pipeline is updated across all four integration points:
  1. `StreamEvent` union types in `@/types/index.ts`
  2. `STREAM_EVENT_TYPES` whitelist Set in `@/api/chat.ts`
  3. `parseStreamEvent` parser in `@/api/chat.ts`
  4. `createEventHandler` dispatcher in `@/composables/useChatStream.ts`
- When an event with `subagent_id` arrives, updates to thinking, tool calls, and content are redirected to that Subagent's session bucket in the store. Tool calls are indexed by `(subagent_id, tool_call_id)` to prevent collisions.

### 3. Subagent Session Persistence & Replay
- A new nullable `subagents` TEXT column is added to `chat_messages` (model + `MessageCreate`), populated via an idempotent `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` executed inside `create_tables()` on application startup.
- On stream completion, `chat_service` aggregates each Subagent session (reasoning text, output tokens, and the `subagent_id`-tagged tool chain) into a snapshot carried by the `final` event; the router persists it as JSON in the `subagents` column.
- On historical replay (`GET /api/sessions/{session_id}/messages`), the frontend parses the snapshot directly. Legacy rows without the column fall back to reconstructing the tool chain from `subagent_id`-tagged `tool_calls`.

### 4. UI Presentation & Component Architecture
- A new `SubagentCard.vue` component is created in `frontend/src/components/chat/`.
- `SubagentCard` contains:
  - Header: Subagent icon, status badge (Running / Finished / Error), execution timer.
  - Body: An embedded `ReasoningAccordion` dedicated to the Subagent's thinking trace.
  - Tool Chain: List of domain tools (e.g. `sql_db_query`, `sql_db_schema`) with syntax highlighting and expandable query results.
  - Subagent Output: Rendered Markdown block for interim findings.
- `MessageItem.vue` embeds `SubagentCard` instances directly beneath the Main Agent's reasoning/delegation area and above the final response markdown.
- Coordinator `task` tool calls in the main bubble are rendered as lightweight delegation summary pills rather than expanding full worker outputs.

## Testing Decisions

### What Makes a Good Test
Tests must verify external behaviors (protocol contracts, stream event routing, store state isolation, and UI card rendering) rather than internal private variables.

### Module Test Plan
1. **Backend Event Tagging Tests**:
   - Verify that simulated graph events with `ns=("tools:call_task_1", "model_request:xxx")` emit SSE events containing `subagent_id="call_task_1"` and `subagent_name="sql_domain_agent"`.
   - Verify that main graph events with `ns=()` emit events with `subagent_id=None` (omitted in JSON).
2. **Frontend SSE Parser & Store Tests**:
   - Verify that `parseStreamEvent` extracts `subagent_id` and `subagent_name` without data loss.
   - Verify that `messagesStore.appendStreamingReasoning` and `upsertStreamingToolCall` isolate Subagent updates from Main Agent state.
   - Verify that historical message replay correctly groups tools into `subagents` sessions.
3. **UI Integration & Visual Verification**:
   - Verify that Subagent thinking displays inside `SubagentCard` with its own timer.
   - Verify that Main Agent thinking displays separately in the main bubble.
   - Verify graceful rendering on user interruption (Abort) and database error states.

### Prior Art
- Existing test patterns in `backend/tests/` using `pytest` and async event verification.
- Frontend component tests using Vitest and Vue Test Utils.

## Out of Scope

1. **Arbitrary Deep Subagent Nesting**: Subagent-calling-Subagent (3+ tier hierarchies) is not used in the current single-subagent SQL architecture. The `subagent_id` (task call_id) identifies a single delegation session; multi-level nesting UI is out of scope.
2. **Modifying Agent Graph Topologies**: The underlying LangGraph compilation and `create_deep_agent` definition remain untouched.
3. **External CDN Font/Icon Loading**: All UI elements strictly utilize local asset bundles in accordance with offline deployment constraints.
4. **Standalone Migration Scripts**: No separate migration tooling is introduced; the idempotent column addition is inline within `create_tables()` (startup path only, non-destructive).

---

## Further Notes

- **Performance**: Isolating reasoning and tool calls prevents continuous re-renders of the large primary message content block, improving UI responsiveness during long database queries.
- **Maintainability**: Clear boundary between Coordinator and Subagents sets a repeatable pattern for future specialized agents (e.g., Charts Agent, Python Code Sandbox Agent).
