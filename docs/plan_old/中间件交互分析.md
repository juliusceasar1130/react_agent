# SkillMiddleware 与 RAG 中间件交互分析

## 1. SkillMiddleware 运行机制

### 1.1 核心工作原理

`SkillMiddleware` 使用 `wrap_model_call` 钩子，在每次模型调用前修改 `ModelRequest`：

```43:60:backend/app/agent/middleware/skill_middleware.py
    def _modify_request(self, request: ModelRequest) -> ModelRequest:
        """将技能描述注入到系统提示词"""
        skills_addendum = (
            f"\n\n## Available Skills\n\n{self.skills_prompt}\n\n"
            "Use the load_skill tool when you need detailed information "
            "about handling a specific type of request."
        )

        # 追加系统提示词
        new_content = list(request.system_message.content_blocks) + [
            {"type": "text", "text": skills_addendum}
        ]
        new_system_message = SystemMessage(content=new_content)

        logger.info("SkillMiddleware: Injected skill descriptions into system prompt")
        logger.debug(f"Modified system message: {new_system_message}")

        return request.override(system_message=new_system_message)
```

**关键点**：
- 修改的是 `ModelRequest.system_message`
- 通过 `request.override(system_message=new_system_message)` 替换系统消息
- 追加技能描述到系统提示词的 `content_blocks` 中

### 1.2 执行时机

`wrap_model_call` 在模型调用前执行，此时：
- `ModelRequest` 已经从 `state` 构建完成
- `ModelRequest.system_message` 来自 Agent 创建时的 `system_prompt`
- `ModelRequest.messages` 来自 `state.messages`

- 在 `before_model` 阶段执行，早于 `wrap_model_call`

## 3. LangChain 中间件执行顺序

### 3.1 标准执行流程

```
1. before_model 钩子（按中间件列表顺序）
   ↓
   修改 state（包括 messages）
   ↓
2. 从 state 构建 ModelRequest
   - ModelRequest.system_message ← Agent 创建时的 system_prompt
   - ModelRequest.messages ← state.messages
   ↓
3. wrap_model_call 钩子（按中间件列表顺序）
   ↓
   修改 ModelRequest
   ↓
4. 模型调用
```

### 3.2 关键理解

**`ModelRequest.system_message` 和 `state.messages` 是分离的**：

- **`ModelRequest.system_message`**：
  - 来自 Agent 创建时的 `system_prompt`
  - 由 `wrap_model_call` 修改（如 SkillMiddleware）
  - 作为系统提示词发送给模型

- **`state.messages`**：
  - 包含对话历史消息
  - 由 `before_model` 修改（如 RAG 中间件）
  - 作为消息列表发送给模型

## 4. 是否会相互覆盖？

### 4.1 结论：**不会相互覆盖**

原因：

1. **不同的修改位置**：
   - RAG 中间件修改 `state.messages`（添加 SystemMessage 到消息列表）
   - SkillMiddleware 修改 `ModelRequest.system_message`（修改系统提示词）

2. **不同的执行时机**：
   - `before_model` 先执行（RAG 中间件）
   - `wrap_model_call` 后执行（SkillMiddleware）

3. **不同的作用域**：
   - RAG 的 SystemMessage 在 `messages` 列表中，作为普通消息
   - SkillMiddleware 的修改在 `ModelRequest.system_message` 中，作为系统提示词

### 4.2 实际效果

当两个中间件同时工作时：

```
ModelRequest {
    system_message: SystemMessage(
        content=[
            // 原始系统提示词
            "You are an 120JPH paint shop agent...",
            // SkillMiddleware 追加的技能描述
            "## Available Skills\n\n- **skill1**: ..."
        ]
    ),
    messages: [
        // RAG 中间件添加的业务知识系统消息
        SystemMessage("## 业务知识库\n\n..."),
        // 对话历史消息
        HumanMessage("用户查询"),
        AIMessage("之前的回复"),
        ...
    ]
}
```

**模型会同时看到**：
1. 系统提示词（包含技能描述）
2. 业务知识系统消息（在 messages 中）
3. 对话历史消息

## 5. 潜在问题与解决方案

### 5.1 潜在问题

虽然不会相互覆盖，但可能存在以下问题：

#### 问题 1：消息顺序

RAG 中间件在 `messages` 开头添加 SystemMessage，但如果 `state.messages` 中已经有其他 SystemMessage，顺序可能不理想。

**解决方案**：
- RAG 中间件已经实现了消息去重和替换逻辑
- 确保业务知识 SystemMessage 在合适的位置

#### 问题 2：Token 消耗

两个中间件都会增加 Token 消耗：
- SkillMiddleware：追加技能描述到系统提示词
- RAG 中间件：添加业务知识系统消息

**解决方案**：
- 控制检索数量（top_k）
- 考虑缓存机制
- 优化提示词长度

#### 问题 3：信息冗余

如果业务知识库中包含了技能信息，可能会与 SkillMiddleware 的技能描述重复。

**解决方案**：
- 业务知识库应该专注于业务数据、规则、流程等
- 技能描述专注于工具使用指导
- 两者职责分离，避免重复

### 5.2 最佳实践

1. **职责分离**：
   - SkillMiddleware：提供工具使用指导（静态）
   - RAG 中间件：提供业务知识检索（动态）

2. **执行顺序**：
   ```python
   middleware=[
       BusinessRagMiddleware(vector_store=vector_store),  # 先执行 before_model
       summarization_middleware,
       SkillMiddleware(),  # 后执行 wrap_model_call
   ]
   ```

3. **消息管理**：
   - RAG 中间件负责管理业务知识 SystemMessage（去重、替换）
   - SkillMiddleware 只修改系统提示词，不涉及 messages

## 6. 验证建议

### 6.1 测试场景

1. **同时启用两个中间件**：
   - 验证技能描述是否正常显示
   - 验证业务知识是否正常检索和注入
   - 验证两者是否同时生效

2. **检查模型输入**：
   - 查看 `ModelRequest.system_message` 内容
   - 查看 `ModelRequest.messages` 内容
   - 确认两者都包含预期信息

3. **功能验证**：
   - Agent 能否使用技能描述指导工具调用
   - Agent 能否使用业务知识回答问题
   - 两者是否协同工作

### 6.2 调试方法

1. **日志输出**：
   - SkillMiddleware 已记录修改后的系统消息
   - RAG 中间件应记录检索结果和注入的消息

2. **状态检查**：
   - 检查 `state.messages` 中是否有业务知识 SystemMessage
   - 检查 `ModelRequest.system_message` 中是否有技能描述

3. **模型响应分析**：
   - 验证 Agent 是否同时使用了技能和业务知识

## 7. 总结

### 7.1 核心结论

**SkillMiddleware 不会被 RAG 中间件覆盖**，因为：

1. ✅ 修改位置不同：`state.messages` vs `ModelRequest.system_message`
2. ✅ 执行时机不同：`before_model` vs `wrap_model_call`
3. ✅ 作用域不同：消息列表 vs 系统提示词

### 7.2 协同工作

两个中间件可以**协同工作**，各自负责不同的职责：

- **SkillMiddleware**：提供工具使用指导（静态技能描述）
- **RAG 中间件**：提供业务知识检索（动态业务知识）

### 7.3 注意事项

1. 确保消息去重逻辑正确
2. 控制 Token 消耗
3. 避免信息冗余
4. 保持职责分离
