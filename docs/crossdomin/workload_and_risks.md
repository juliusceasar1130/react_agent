# SQL Agent 架构 1 实施工程量与副作用评估报告 (Workload & Risks)

本报告详细评估了 **架构 1：前置 LLM 意图路由方案 (Phase 1 级联子查询)** 落地实施的工程量、潜在副作用及防御性设计对策。

---

## 一、 工程量评估 (Workload Estimation)

架构 1 避开了复杂的 SQLAlchemy 物理连接生命周期控制及 DB 暂存表工具开发，工程改造集中于 Python 后端架构层，开发代价非常低。

### 1. 核心改造模块与估算 LOC (Lines of Code)

* **元数据扩展 (associated_tables 声明)**:  
  修改各个技能目录下的 `meta.py`（共计 3 个文件），在 `DOMAIN_META` 字典中添加物理表名列表。  
  *LOC 增量: ~10 行*
* **动态反射服务 `skeleton_service.py`**:  
  新建服务类，动态调用 `db_utils.py` 中的原生反射方法，并使用正则剥离样本数据输出。  
  *LOC 增量: ~80 行*
* **意图判定路由节点 (Router Node)**:  
  在 LangGraph 的开头新增路由判定节点。编写轻量级分类 Prompt，驱动 LLM 输出主辅分类结果。  
  *LOC 增量: ~60 行*
* **中间件重构 `SkillMiddleware`**:  
  拦截 State 中的主辅标记，提取并拼接主 DDL（全量）与辅助 DDL 骨架。  
  *LOC 增量: ~40 行*
* **系统提示词微调**:  
  在 `service.py` 提示词模板中追加“EXISTS 嵌套直连”规则。  
  *LOC 增量: ~20 行*

### 2. 人天工期估算 (Timeline)

| 阶段 | 任务 | 预计工期 |
|---|---|---|
| **第一阶段** | `meta.py` 扩展、编写 `skeleton_service.py`、单元测试反射输出。 | 1.0 人天 |
| **第二阶段** | LangGraph 路由节点开发、`SkillMiddleware` 动态拼装、系统提示词微调。 | 0.5 人天 |
| **第三阶段** | 跨域联合提问联调、别名冲突防御及性能测试。 | 1.0 人天 |
| **总计** | **Phase 1 稳定上线** | **2.5 人天** |

## 二、 潜在副作用 (Side Effects) 与防御性对策

为了保障 Phase 1 生产环境的高可用，我们在设计上对以下三个副作用做出了针对性的防御：

### 1. 副作用 A：前置 Router 节点带来的首字响应延迟 (Router Latency)
* **问题描述**：在进入主 SQL 生成智能体之前多了一次大模型路由调用。哪怕 Token 很少，仍然会产生约 **200ms - 400ms** 的网络响应开销，稍微拖慢首字流式输出时间。
* **防御性设计**：
  - **轻量模型分流**：路由判定节点选用体积最轻、速度最快的 LLM 模型（如 GPT-4o-mini 或 8B 以下的本地开源模型）。
  - **静态前置判定 (Optional)**：若用户提问不包含跨域特征词，后端直接静态将当前技能标记为主技能，直接跳过前置 Router 节点的 LLM 调用。

### 2. 副作用 B：列名歧义导致 PG 17 语法报错 (Ambiguous Column Reference)
* **问题描述**：由于大模型在一行 SQL 中直接关联两张表，如果主表与辅助表包含同名字段（如物流表和质量表都有 `vehicle_id` 和 `carrier_id`），一旦模型编写 SQL 时省略了表前缀别名，PostgreSQL 17 会直接抛出 `column reference is ambiguous` 报错。
* **防御性设计**：
  - **别名强约束军规**：在 System Prompt 提示词中写入强红线指令：
    > *“【避免同名歧义】在编写 SQL（特别是使用多表 JOIN 或子查询）时，必须为每一个列显式加上表别名前缀（如 `mq.vehicle_id` 而不是 `vehicle_id`），严禁使用不带前缀的裸列。”*
  - **校验测试用例**：在一期自动化单元测试用例中，重点测试覆盖含有同名列查询的 SQL 正确性断言。

### 3. 副作用 C：辅助技能骨架造成的长上下文“注意力漂移”
* **问题描述**：虽然单个辅助技能 DDL 仅约 100 Tokens，但如果级联了过多辅助技能（如 3 个以上），System Prompt 长度增加，可能会让模型遗忘主技能中的关键 Gotchas 规则（例如：开始乱用 SELECT *）。
* **防御性设计**：
  - **表清单物理裁剪**：后端在读取辅助 DDL 时，**仅保留主外键和关联列**。在代码层直接剔除对 JOIN 无意义的杂列（如操作人、时间、备注等），将辅助骨架的大小压缩到极致（每个表控制在 30 Tokens 左右）。
  - **限制辅助技能数**：在 Router 逻辑中限制 `len(secondary_skills) <= 1`。在当前涂装场景下，单次辅助关联的领域表仅 1 个即可满足所有复合需求。
