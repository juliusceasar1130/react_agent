# SQL Agent 跨领域查询双架构设计对比报告 (Architecture Comparison)

本报告对比了实现跨领域多步查询的两套主流 Agent 架构设计：
1. **架构 A：前置 LLM 意图路由方案 (Two-Stage LLM Pre-routing)**
2. **架构 B：ReAct 循环内 Tool 路由加载方案 (In-ReAct Loop Tool Routing)**

---

## 1. 架构图解对比 (Visual Topology)

### 架构 A：前置 LLM 意图路由方案 (本规范一期首选)
```
                  [ 用户复合跨域输入 ]
                           │
                           ▼
              (RAG 提前检索 business_rag_context)
                           │
                           ▼
          ┌──────────────────────────────────┐
          │   1. Router LLM 意图路由节点     │ (仅用技能大纲，不读 DDL)
          └────────────────┬─────────────────┘
                           │ 判定出: 主=质量，辅=物流
                           ▼
          ┌──────────────────────────────────┐
          │   2. Python 中间件 DDL 拼装     │ (反射提取物流骨架并拼入)
          └────────────────┬─────────────────┘
                           │ 组装成: 全量主 DDL + 极简辅助骨架
                           ▼
          ┌──────────────────────────────────┐
          │   3. SQL Generator LLM (ReAct)   │ (一睁眼拥有全部 DDL 视野)
          └────────────────┬─────────────────┘
                           │ 直接一步写出 EXISTS 关联子查询
                           ▼
                    [ 数据库执行成功 ]
```

### 架构 B：ReAct 循环内 Tool 路由加载方案
```
                  [ 用户复合跨域输入 ]
                           │
                           ▼
              (RAG 检索 business_rag_context)
                           │
                           ▼
          ┌──────────────────────────────────┐
          │   1. SQL Generator LLM (ReAct)   │ (初始仅载入默认/主技能 DDL)
          └────────────────┬─────────────────┘
                           │
                           ▼ (LLM 推理发现缺数据)
          ┌──────────────────────────────────┐
          │  2. 调用 load_skill('物流') Tool │ (互斥替换或追加)
          └────────────────┬─────────────────┘
                           │
                           ▼ (后端返回物流 DDL)
          ┌──────────────────────────────────┐
          │   3. SQL Generator LLM (ReAct)   │ (结合新 DDL 准备写 SQL)
          └────────────────┬─────────────────┘
                           │ 编写最终 SQL 运行
                           ▼
                    [ 数据库执行成功 ]
```

## 2. 核心技术维度多维度比对 (Trade-offs)

| 评估维度 | 架构 A：前置 LLM 意图路由 (Pre-routing) | 架构 B：ReAct 循环内 Tool 路由 (In-Loop Tool) |
|---|---|---|
| **首字响应速度 (TTFT/延迟)** | 🟢 **极快**。虽然调用了两次 LLM，但第一步 Router LLM 不包含任何 DDL 资料，Token 极少（速度约 200ms）。第二步 SQL LLM 无需经过任何 Tool 迭代，一轮直接输出 SQL，**总耗时最低**。 | 🔴 **较慢**。大模型需要先思考 $\rightarrow$ 输出 Tool Call $\rightarrow$ 等待后端返回新 DDL $\rightarrow$ 再次思考 $\rightarrow$ 编写 SQL。由于多了一轮 ReAct Tool 交互的网络往返，**总耗时会多出 1~3 秒**。 |
| **SQL 编写成功率** | 🟢 **极高**。SQL LLM 一睁眼就同时看到了主技能细节和辅助技能骨架，它拥有全局连表视野，写出的 `EXISTS` 子查询逻辑自洽，出错率低。 | 🔴 **中/低**。如果 DDL 切换是**互斥**的，当加载了技能 B，技能 A 的 DDL 就被冲掉了，大模型“顾此失彼”极易拼错表名和字段；如果是**追加**的，中途 DDL 突变膨胀容易引起上下文碎片化。 |
| **Token 消耗开销** | 🟡 **中等**。第一步 Router 只读技能描述，Token 开销微乎其微。第二步 SQL LLM 引入了压缩后的辅助骨架（约 100 词），总 Token 处于健康范围（约 3000~4000）。 | 🔴 **高**。如果在 ReAct 中途全量加载辅助技能，会瞬间往上下文追加 2000 个 Token，且整个推理链历史（Message History）变长，会带来极大的 Token 浪费。 |
| **大模型心智负担** | 🟢 **极低**。大模型不需要做复杂的“我接下来到底该调用什么工具去补全我的知识”的逻辑规划，它只需要看着已给出的表写 SQL 即可。 | 🔴 **极高**。模型在写 SQL 的同时，还要分心去规划：“我缺什么表？对应什么技能？我该调哪个 load 工具？”容易导致多步推理发生执行偏离。 |
| **开发与框架复杂度** | 🟡 **中等**。需要在 LangGraph 拓扑图的开头增加一个分流 Node，并将 RAG 提前，稍微增加了图的路径设计。 | 🟢 **低**。无需修改 LangGraph 拓扑，完全依赖原有的 ReAct Agent 循环，只需要在 Tool 定义中新增 `load_skill` 即可。 |

## 3. 架构选择与演进建议 (Recommendations)

### 1. 为什么 Phase 1 (一期) 强力推荐使用【架构 A：前置 LLM 意图路由】？
在绝大多数涂装车间的数据查询场景中，复合查询仅跨越 **1 个主技能（如质量指标）** 和 **1 个辅助技能（如物流定位）**。
* 在这种双技能关联场景下，**“前置路由一次性全装配”** 能够将复杂性完美屏蔽在 Python 后端（即通过 `SkillMiddleware` 和 `SkeletonService` 动态组装）。
* 大模型只需做纯粹的 SQL 编译，耗时最短，语法成功率最高。

### 2. 架构 B 的价值与演进空间（二期兜底降级）
架构 B（ReAct 内 Tool 路由）虽然存在延迟和心智负担，但当系统未来扩展到 **3 个以上复杂的跨领域长链依赖**、或者需要模型根据数据库执行结果**动态自愈、回滚重试**时，作为 Fallback 兜底方案是必不可少的。

**结论**：
* **Phase 1 (一期)**：采用**架构 A**，通过前置 RAG 检索与 Router 节点锁定主辅，中间件直接级联注入，大模型一句嵌套子查询直连数据库。
* **Phase 2 (二期)**：在架构 A 的基础上，将**架构 B 作为自愈 fallback 嵌入**，允许大模型在子查询报错时，通过 Tool 调用 `load_skill` 重新对调主辅角色，修正并覆盖临时表数据。
