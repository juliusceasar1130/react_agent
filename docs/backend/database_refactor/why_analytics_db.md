# 为什么设计 Analytics DB

修改时间：2026-04-11 Asia/Shanghai

主要修改内容：
- 新增 `analytics_db` 设计动机说明，补充“为什么要有统一分析库”而不只是“如何落地”
- 结合当前项目的 Agent、技能系统、源库结构与已验证实现，总结设计背景、取舍和复用原则
- 为后续数据库重构、技能扩展和 Agent 接库改造提供统一设计依据
- 补充当前“异常车 / 调试车”场景下的事实建模限制说明
- 补充下一阶段需要将“正式产品车事实”和“异常车事实”分开的设计依据
- 同步 2026-04-11 已实际落地的当前车辆事实分层结果

## 1. 背景

当前项目已经有两套强相关的业务数据源：

- `rollerbed_tracking_db`
  - 负责车辆在涂装车间中的位置、区域、载体、车型、颜色、平台等状态信息
- `defect_db`
  - 负责缺陷检测结果，当前重点使用 `history_station_defect_summary`

同时，项目里的 SQL Agent 与技能系统已经具备如下基础能力：

- 领域技能（domain skill）和场景技能（scenario skill）已经支持自动发现与按需加载
- SQL 工具链已经具备只读保护、结果限流、技能加载校验等机制
- 业务分析问题已经开始跨“车辆位置”和“质量缺陷”两个域

但在这套基础之上，原始架构仍有一个明显约束：

- Agent 运行时更适合面向一个统一的 SQL 查询面，而不是同时管理多套源库和跨库语义

## 2. 这个设计解决什么问题

设计 `analytics_db` 的核心，不是为了“再建一个数据库”，而是为了给 Agent 提供一层更稳定、更安全、更易推理的分析数据面。

它主要解决下面几类问题：

### 2.1 跨域查询复杂度过高

如果直接让 Agent 面对两个源库：

- 需要理解每个库分别存什么
- 需要知道跨域关联键是什么
- 需要自己推断先查哪边、再怎么拼接
- 很容易把跨域问题退化成多次查询后在上下文中手工拼接

这对 LLM 并不友好，稳定性和正确性都会下降。

### 2.2 源库结构适合业务系统，不一定适合 Agent

源库表结构通常更偏向业务运行：

- 表较细
- 字段命名可能带业务遗留色彩
- 编码字段和展示字段分散
- 统计口径分布在多个表、多个规则里

但 Agent 更需要：

- 少量稳定入口表或视图
- 明确的关联键
- 已标准化的字段语义
- 尽量少的复杂 `JOIN`

### 2.3 直接查源库不利于安全与运维

让 Agent 直连源库存在这些隐患：

- 大模型容易生成高成本聚合 SQL
- 多表统计容易影响业务库性能
- 源库结构演进时，Agent 查询面也会被迫同步变化
- 权限隔离和后续运维边界不清晰

### 2.4 技能系统需要一个稳定的数据承载面

技能系统负责给模型补充领域知识和查询口径，但技能本身不应该承担“数据库编排层”的复杂度。

也就是说：

- 技能应该告诉模型“有哪些业务对象、字段含义和统计规则”
- 数据库层应该尽量保证“这些对象在一个统一的只读分析面里可直接查询”

## 3. 为什么不是直接继续查两个源库

这是当前设计中最重要的取舍之一。

### 3.1 不是不能查，而是不适合长期演进

理论上可以给 Agent 做多库路由：

- 查车辆问题走 `rollerbed_tracking_db`
- 查缺陷问题走 `defect_db`

但这样一来，一旦用户问题跨域，复杂度会迅速上升。

例如：

- 某车型在某区域停留后缺陷是否升高
- 黑车顶车型在当前区域分布与缺陷水平是否有关系
- 某通道缺陷高发的车辆是否集中在特定区域或载体类型

这类问题天然要求统一查询面。

### 3.2 统一只读分析库比“多库切换”更适合 Agent

统一分析库的价值在于：

- 跨域关联提前在数据库层表达清楚
- 模型不再需要自己决定跨库流程
- 高价值聚合对象可以直接做成 `fct` / `mart`

这会显著降低 Agent 的推理负担。

## 4. 为什么不是直接物理合并两个源库

这里要区分“源库合并”和“分析层统一”。

当前设计选择的是：

- 源库继续保留各自边界
- 在 `analytics_db` 中统一接入、统一建模、统一消费

这样做的原因是：

1. 业务边界更清晰  
   `rollerbed_tracking_db` 和 `defect_db` 仍然分别服务各自业务系统，不被分析需求反向绑架。

2. 风险更低  
   不需要直接改造已有源库结构，也不需要把所有新需求都塞回源库。

3. 分析层可以自由优化  
   `analytics_db` 可以引入：
   - `ods`
   - `dim`
   - `fct`
   - `mart`
   - `meta`

4. 更适合给 Agent 做权限隔离  
   Agent 只需要只读访问分析库，不必直接接触业务源库。

## 5. 为什么采用 `src -> ods -> dim/fct -> mart -> Agent`

这是当前设计的核心分层。

```text
源库 -> FDW 外表(src) -> ODS -> DIM/FCT -> MART -> Agent
```

### 5.1 `src`

`src_rb` 和 `src_defect` 只是 FDW 外部表映射层。

用途：

- 把源库数据暴露给 `analytics_db`
- 避免应用层自己做跨库搬运
- 保留与源表的清晰边界

### 5.2 `ods`

`ods` 是贴源落地层。

用途：

- 把外部表数据同步成本地实体表
- 建本地索引
- 后续刷新和统计可以不直接依赖 FDW 实时执行

为什么 ODS 不能省略：

- 直接查 FDW 外表不利于稳定查询性能
- 不利于本地索引和后续视图计算
- 不利于刷新日志和水位管理

### 5.3 `dim`

`dim` 是统一解释层。

当前已经建设：

- `dim.dim_process_area`
- `dim.dim_vehicle_profile`

用途：

- 把区域、车型、平台、颜色、黑车顶等语义收敛到统一入口
- 为 Agent 提供更清晰的业务解释面

### 5.4 `fct`

`fct` 是事实层。

当前已经建设：

- `fct.fct_position_current_all`
- `fct.fct_vehicle_position_current`
- `fct.fct_abnormal_vehicle_current`
- `fct.fct_vehicle_defect_detection`

用途：

- 表达“当前全量占位事实”
- 表达“当前车辆位置事实”
- 表达“当前异常车事实”
- 表达“缺陷检测事实”

### 5.5 `mart`

`mart` 是面向 Agent 的消费层。

当前已经建设：

- `mart.mart_abnormal_vehicle_current`
- `mart.mart_position_current_overview`
- `mart.mart_vehicle_quality_360`

用途：

- 用一张稳定入口表/视图承接高频查询
- 降低 LLM 写复杂 SQL 的门槛

## 6. 为什么当前的 `mart_vehicle_quality_360` 只关联“当前最新位置”

这是一个有意识的阶段性取舍。

当前设计优先目标是：

- 先把统一分析库跑通
- 先让 Agent 能稳定回答跨域分析问题
- 先用简单、可验证的口径完成第一阶段落地

所以当前 `mart.mart_vehicle_quality_360` 采用的是：

- 一次缺陷检测记录
- 关联该车当前最新位置

这不是最完整的业务还原，但它有两个优势：

1. 落地快  
   不需要先补一整套位置历史快照体系

2. 易验证  
   当前位置事实已经有稳定来源，缺陷检测事实也已汇总完成

需要明确的是：

- 这是“当前阶段的简化分析口径”
- 不是“检测发生时位置”的严格还原口径

如果后续要回答下面的问题，就必须继续演进：

- 检测时车辆所在区域
- 某区域停留时长与缺陷的相关性
- 检测前路径与缺陷分布关系

## 7. 关键设计决策

### 决策 1：保留源库，统一分析层

原因：

- 降低对现有业务库的侵入
- 分析需求和业务运行需求分层治理

### 决策 2：Agent 面向分析库，而不是源库

原因：

- 降低跨域 SQL 复杂度
- 提高 Agent 查询稳定性
- 便于权限隔离

### 决策 3：引入 ODS，而不是直接查 FDW

原因：

- 本地索引更可控
- 物化视图刷新更稳定
- 便于后续做增量刷新和水位管理

### 决策 4：先做全量刷新，再考虑增量刷新

原因：

- 先求稳，再求快
- 在对象边界尚未完全稳定前，全量刷新更容易校验与排错

### 决策 5：先做一个高价值 `mart`

原因：

- 先满足高频分析问题
- 给 Agent 一个明确且低复杂度的入口

### 决策 6：当前产品车事实与异常车事实不应长期混用

原因：

- 正式产品车通常可以按 `vehicle_id` 建模
- 异常车和调试车不一定能按 `vehicle_id` 唯一建模
- 如果继续把两者放在同一套“按 `vehicle_id` 去重”的事实口径里，容易丢失异常占位信息

因此当前实现可以先跑通，但下一阶段应把：

- 正式产品车当前事实
- 异常车当前事实
- 全量当前占位事实

明确分开。

## 8. 当前已验证的实现事实

以下内容已经在数据库中验证过：

- `analytics_db` 已存在
- `src_rb` / `src_defect` / `ods` / `dim` / `fct` / `mart` / `meta` 已存在
- `meta.refresh_analytics_all()` 已存在并能成功执行
- `dim.dim_process_area`、`dim.dim_vehicle_profile` 会随着刷新过程一起重建
- `dim.dim_vehicle_profile` 已补充 `current_carrier_id`、`current_process_area` 等当前绑定快照字段
- `meta.refresh_watermark` 会随着刷新更新
- `agent_ro` 对 `dim` / `mart` 已具备查询权限

这意味着，`analytics_db` 已经不只是一个架构设想，而是进入了可操作、可验证、可演进的阶段。

同时也要明确两个当前已验证的边界：

- `fct.fct_vehicle_position_current` 现在已经显式收敛为正式产品车当前事实
- `mart.mart_vehicle_quality_360` 仍然是“缺陷检测 + 当前最新位置”口径，不是“检测当时位置”

## 9. 踩坑与经验

### 9.1 不能只写“ODS + 物化视图”流程

如果手册里只写：

- 同步 `ods`
- 刷新 `fct`
- 刷新 `mart`

那么后续容易漏掉：

- `dim` 刷新
- `refresh_watermark` 更新

这会导致文档和真实数据库状态脱节。

### 9.2 文档必须区分“当前口径”和“最终目标”

当前 `mart_vehicle_quality_360` 的位置口径是“当前最新位置”，不是“检测当时位置”。  
如果文档不写清楚，后面业务分析就会误用。

同样也必须区分：

- 当前产品车事实口径
- 当前异常车占位问题
- 后续统一现场占位分析口径

否则后续会误把“按 `vehicle_id` 唯一去重”的产品车事实，拿去回答异常车或调试车分布问题。

### 9.3 设计说明和操作手册要分开

“为什么要这样设计”和“具体怎么执行”是两类文档。

- 操作手册负责可执行性
- 设计说明负责统一认知

两者都要有，才能降低后续沟通成本。

## 10. 后续复用检查清单

当后续新增新的分析域或重构数据库时，可以按下面清单复用这套思路：

- 是否存在多个强相关但独立演进的源库
- Agent 是否已经开始出现跨域查询诉求
- 是否需要一个统一只读查询面
- 是否需要把编码解释、业务口径、聚合对象提前在数据库层表达出来
- 是否已经具备稳定的关联键
- 是否应该先做全量刷新，再逐步增量化
- 是否已经明确“当前可用口径”和“后续目标口径”的区别

## 11. 后续演进建议

### 11.1 增加位置历史快照层

如果要从“当前状态分析”升级到“时序关系分析”，建议增加：

- 位置历史快照事实表
- 停留时长汇总表
- 检测前窗口特征表

### 11.2 逐步引入增量刷新

当前全量刷新适合第一阶段。后续数据量上来后，可以逐步改成：

- `ods` 增量同步
- `fct` 分区或局部刷新
- `mart` 按时间窗口或业务主题刷新

### 11.3 面向技能继续收敛分析对象

当前已经有统一分析层，后续可以继续围绕技能设计更明确的消费对象，例如：

- 车型缺陷分布主题 `mart`
- 工位缺陷趋势主题 `mart`
- 质量关联分析主题 `mart`

### 11.4 将当前车辆事实进一步拆分

这一阶段已经部分落地，当前状态如下：

- `fct_position_current_all`
  - 已落地，当前每个有效占位一条
- `fct_vehicle_position_current`
  - 已调整为正式产品车当前事实
- `fct_abnormal_vehicle_current`
  - 已落地，面向异常车 / 调试车当前状态
- `mart_abnormal_vehicle_current`
  - 已落地，面向异常车查询与监控
- `mart_position_current_overview`
  - 已落地，作为当前现场总览统一入口

## 12. 一句话总结

`analytics_db` 的本质，不是多建一个数据库，而是把“多源业务数据、复杂关联语义和 Agent 的查询需求”收敛成一个稳定、只读、可演进的统一分析面。
