## 4. 阶段 4：跨域质量关联领域

### 4.1 阶段目标

新增独立领域 `paint_shop_quality_correlation`，承接“车辆状态 + 缺陷”的联合分析问题，而不是继续把这类问题混在 tracking 或 defect 单领域里。

### 4.2 为什么现在还没做

当前数据库和场景已经足够支持很多单领域问题，但跨域问题是否高频、是否需要专门的技能入口，还缺少真实使用反馈。

### 4.3 主要任务

- 新增 `backend/app/skills/domains/paint_shop_quality_correlation/`
- 编写 `meta.py`
- 编写 `domain.md`
- 根据高频问题补第一批 correlation 场景
- 明确它与 `paint_shop_vehicle_tracking`、`paint_shop_defect_analysis` 的职责边界

### 4.4 适合承接的问题

- 当前哪些车型既分布在某些区域，又存在较高缺陷量
- 正式产品车与异常车的当前状态，是否与质量表现存在明显差异
- 某车型当前分布和近期缺陷情况的联合观察

### 4.5 完成标准

- 新领域可自动发现
- 至少有 2 到 3 个真实可用的跨域场景
- Agent 不再需要靠单领域技能“硬拼”跨域解释

### 4.6 是否建议立即做

建议：**暂缓到真实跨域问题变多后再做**

原因：

- 当前 tracking 与 defect 两个领域已经能覆盖大部分已知问题
- 跨域领域过早拆出，容易形成“为可能的问题预建很多结构”

## 5. 阶段 5：补高频主题 `mart`

### 5.1 阶段目标

把已经高频出现、且当前虽然能由 LLM 从 `mart_vehicle_quality_360` 自主生成 SQL 但稳定性和成本不够理想的问题，沉淀为专门的主题对象。

### 5.2 当前候选主题

建议优先观察这两个：

- `mart_defect_daily_by_model`
- `mart_defect_station_distribution`

### 5.3 主要任务

- 统计真实问答中高频 SQL 主题
- 识别哪些问题在 `mart_vehicle_quality_360` 上反复出现
- 设计主题 `mart` 字段与粒度
- 调整对应 scenario 直接面向新 `mart`

### 5.4 进入条件

满足以下任一条件就建议实施：

- 某类缺陷趋势问题非常高频
- 某类部位分布问题非常高频
- 同类 SQL 被反复生成
- 结果口径需要更稳定
- 响应速度需要明显提升

### 5.5 完成标准

- 至少 1 个高频主题有专门 `mart`
- 对应技能场景不再依赖临时 SQL 拼装
- 文档中明确新 `mart` 与 `mart_vehicle_quality_360` 的分工

### 5.6 是否建议立即做

建议：**先观察，再做**

原因：

- 当前直接基于 `mart_vehicle_quality_360` 的单表聚合已经足够稳
- 先看真实高频问法，能减少过度设计

## 6. 阶段 6：优化现有技能与场景

### 6.1 阶段目标

继续提升 tracking 与 defect 两个领域的可用性，让 Agent 更少依赖临时 SQL 生成，更多依赖贴近真实业务问题的场景技能。

### 6.2 主要任务

#### tracking 领域

- 增加 `abnormal_vehicle_current_distribution`
- 增加按 `carrier_id` / `carrier_type` 反查车辆的场景
- 增加更贴近现场问法的“当前现场总览”场景

#### defect 领域

- 根据真实问法继续补充 scenario
- 增加更明确的时间范围、车型、黑车顶、`tunnel`、`cycle` 参数约束
- 优化 `domain.md` 中的高频问法示例

### 6.3 完成标准

- 现有高频问题能优先命中固定场景
- LLM 临时拼 SQL 的比例下降
- 场景描述和数据库口径保持一致

### 6.4 是否建议立即做

建议：**可以小步推进**

原因：

- 这类工作改动小、收益直接
- 不依赖新增数据库对象

## 7. 阶段 7：端到端验证与灰度

### 7.1 阶段目标

把“配置正确、对象存在、单点 SQL 可跑”升级为“真实 Agent 会话链路稳定”。

### 7.2 当前还缺什么

当前已完成的是：

- 配置接库
- 代码级与局部查询级验证
- 技能注册测试
- CSV 导出关键缺陷修复

当前还未系统完成的是：

- Agent 聊天链路冒烟
- 导出链路端到端回归
- 常见业务问题回归清单
- 灰度观察与回滚预案沉淀

### 7.3 主要任务

- 设计真实问答冒烟用例
- 验证 `load_skill -> load_scenario -> sql_db_query -> export_to_csv`
- 验证 tracking、defect 两个领域的常见问题
- 验证 CSV 导出下载链路
- 补充灰度期间问题记录与回滚步骤

### 7.4 完成标准

- 至少覆盖 5 到 10 个真实问题
- 查询结果、导出结果、技能口径一致
- 出现失败时能快速判断是数据库、技能还是 Prompt 问题

### 7.5 是否建议立即做

建议：**优先做**

原因：

- 这是当前最接近真实价值的一步
- 可以帮助决定阶段 4 和阶段 5 是否真的有必要继续投入

## 8. 阶段 8：后续可选增强

### 8.1 位置历史快照层

适用场景：

- 停留时长分析
- 路径分析
- 时序相关质量分析

当前建议：

- 不是近期必须项

### 8.2 检测时位置关联主题层

适用场景：

- 检测位置不固定
- 需要严格还原检测发生时的现场状态

当前建议：

- 你已经确认当前检测位置固定
- 现阶段不建议优先投入

### 8.3 缺陷明细层接入

适用场景：

- 缺陷类型分析
- 坐标分析
- 明细归因分析

当前建议：

- 汇总分析阶段可以暂缓
- 高级质量分析时再做

## 9. 推荐优先级

如果从今天开始往下走，我建议优先级如下：

1. 先做阶段 7：端到端验证与灰度
2. 同步小步推进阶段 6：优化现有技能与场景
3. 观察真实问答高频问题后，再决定是否进入阶段 5
4. 等跨域问题变多后，再决定是否进入阶段 4
5. 阶段 8 保持按需推进

## 10. 简化版执行建议

如果你希望保持节奏简单，后面可以按下面的顺序做：

### 方案 A：稳妥推进

1. 先做端到端验证
2. 修补现有 tracking / defect 场景
3. 收集高频问题
4. 再补主题 `mart`

### 方案 B：快速扩功能

1. 先新增更多 scenario
2. 再做少量端到端验证
3. 观察一段时间后再补 `mart`

推荐选择：**方案 A**

原因：

- 先验证链路，再扩结构，更不容易返工

## 11. 一句话结论

从当前状态往后，最值得优先做的不是继续扩数据库对象，而是先把真实 Agent 会话链路验证稳，再根据高频问题决定是补主题 `mart`，还是拆出跨域质量关联领域。
