# 聊天取消与中断机制开发指南

修改时间: 2026-03-31 22:08 Asia/Shanghai

主要修改内容:
- 沉淀本次“前端停止生成 + 后端取消渗透”改造经验
- 说明聊天取消链路的机制、原理、实现边界与开发建议
- 为后续继续优化停止生成体验和下游取消能力提供统一参考

---

## 1. 背景

聊天类 Agent 项目里，“停止生成”看起来像一个简单按钮，但真正要做稳定，通常要同时处理三层问题：

1. 前端要能立刻停止接收流式响应
2. 后端要能感知客户端已经断开，不再继续转发 SSE
3. Agent / LangGraph / LLM 调用链要尽量收到取消信号，避免本地继续白跑

如果只做第一层，用户界面虽然停了，但后端和 Agent 还可能继续运行；如果只做后端断连检测，而不把取消继续传到图执行链路，那么本地服务可能还是会继续等待底层模型调用结束。

---

## 2. 这套机制解决什么问题

这套取消机制主要解决以下问题：

- 用户点击“停止生成”后，界面能快速停止，不再继续追加 token
- 后端在 SSE 断开后尽量停止继续消费 Agent 流
- 非流式与流式两条链路都能收到主动取消，而不是只停在 API 层
- 主动停止不会被误判为系统报错
- 后续扩展“已中断”“保留部分结果”等体验时，有稳定的底层机制可复用

---

## 3. 当前项目里的实现分层

### 3.1 前端层

前端取消的入口在：

- `frontend/src/api/chat.ts`
- `frontend/src/composables/useChatStream.ts`
- `frontend/src/views/ChatView.vue`

核心机制：

1. `useChatStream.ts` 为每次流式请求创建 `AbortController`
2. 用户点击“停止生成”后调用 `abort()`
3. `fetch(..., { signal })` 被中断
4. 前端识别 `AbortError`，不走普通错误分支
5. 清理临时流式状态，并回源同步消息与会话

这意味着前端停止生成的本质不是“通知后端停一下”，而是先把浏览器侧的 HTTP 流读取终止掉。

### 3.2 FastAPI SSE 层

后端 SSE 路由在：

- `backend/app/api.py`

核心机制：

1. 路由接收 `Request`
2. 在等待下一条流式事件时轮询 `await request.is_disconnected()`
3. 一旦检测到客户端断开：
   - 取消当前等待中的任务
   - 结束 SSE 生成
   - 关闭流式迭代器
4. 已断开连接时不再发送 `[DONE]`

这一层解决的是“HTTP 连接已经没了，后端别再继续往前端写”。

### 3.3 Agent 服务层

服务兼容层在：

- `backend/app/services.py`

这里做了两类取消收敛：

1. 非流式：
   - 将 `agent.ainvoke(...)` 包装成 `invoke_task`
   - 上层取消时显式 `invoke_task.cancel()`
2. 流式：
   - 将 `agent.astream(...)` 的消费放进独立 `producer_task`
   - 通过 `queue` 向外层输出结构化事件
   - 上层取消或断连时，反向取消 `producer_task`
   - 同时主动关闭底层 async iterator

这一层解决的是“不是只停 SSE，而是尽量把取消继续传到 Agent 执行任务本身”。

## 4. 机制与原理

### 4.1 前端为什么能停止

因为浏览器的 `fetch` 支持 `AbortSignal`。

调用 `AbortController.abort()` 后：

- 当前 HTTP 请求的读取被终止
- `reader.read()` 不再继续产出数据
- 前端侧会抛出 `AbortError`

这是一种标准的 Web 平台取消机制。

### 4.2 后端为什么能感知

因为 SSE 本质上还是 HTTP 长连接。

当前端中断请求、关闭页面或网络断开时，FastAPI / Starlette 可以通过：

- `request.is_disconnected()`

判断底层连接是否还活着。

一旦连接断开，后端继续 `yield` SSE 数据就没有意义了，所以会尽早结束生成逻辑。

### 4.3 Agent 为什么会停

这是最关键的一层。

Agent 并不是一个独立可远程关停的外部进程，而是运行在当前 Python async task 里的协程逻辑。当前实现是通过：

- `task.cancel()`

来取消它。

当一个 async task 被取消时，Python 会在下一个可中断的 `await` 点抛出：

- `asyncio.CancelledError`

如果 LangChain / LangGraph / 模型 SDK 没有吞掉这个异常，那么这条协程链就会一路中断，不再继续执行。

所以这套机制的本质是：

**通过取消承载 Agent 的协程任务，让 `CancelledError` 沿着 async 调用链传播，从而间接停止 Agent。**

## 5. 一条完整的停止链路

当前项目中，一次“停止生成”的完整链路如下：

1. 用户点击前端“停止生成”
2. `AbortController.abort()` 中断浏览器请求
3. FastAPI SSE 路由检测到 `request.is_disconnected()`
4. SSE 层停止等待下一条事件，结束响应
5. `services.py` 中的流式消费端收到取消
6. 取消 `producer_task`
7. `producer_task` 内部正在消费的 `agent.astream(...)` 收到取消
8. `CancelledError` 沿着 LangGraph / LangChain await 链传播
9. 本地 Agent 执行尽早停止

非流式链路则类似，只是对应的是 `ainvoke()` 的 `invoke_task`。

---

## 6. 这套机制的边界

这点非常重要。

### 6.1 能保证停止的部分

当前实现能够较稳定地停止：

- 前端继续接收流
- FastAPI 继续转发 SSE
- 本地 `services.py` 的 Agent 执行任务
- LangGraph / LangChain 本地 await 链的继续消费

### 6.2 不能绝对保证停止的部分

不能绝对保证远端 LLM provider 一定已经停止推理。

原因是：

- 请求可能已经发送到远端模型服务
- 你本地取消后，远端不一定支持请求级取消
- 有些 SDK 只是让本地不再等待结果，但对方服务可能仍把推理算完

也就是说：

- **本地停止**：当前方案已经做得比较完整
- **远端一定停止**：取决于 provider / SDK 能否继续接收并执行取消信号

## 7. 为什么要把取消做成“多层渗透”

如果只做前端取消：

- 用户看起来停了
- 但后端和 Agent 还可能继续运行

如果只做后端断连检测：

- SSE 停了
- 但底层 `astream()` / `ainvoke()` 仍可能继续挂着

如果只在 Agent 层做取消：

- 前端可能还在等待
- API 层也可能还没意识到客户端已离开

所以更稳的做法一定是三层联动：

1. 前端停止读取
2. API 层停止转发
3. 服务层停止 Agent 执行任务

## 8. 本次实践中的开发经验

### 8.1 停止生成不是“错误”

主动取消和异常失败不能混在一起。

前端当前做法是：

- 识别 `AbortError`
- 不显示错误提示
- 清理临时流式状态
- 重新同步服务端消息

这样用户点击停止生成时，不会看到“系统出错了”的错误体验。

### 8.2 API 层停止，不等于 Agent 真停

这是这次优化里最关键的经验之一。

最初如果只在 `api.py` 停掉 SSE，服务层的 `process_stream()` 仍可能继续消费 `agent.astream()`。所以这次才继续在 `services.py` 里引入：

- `producer_task`
- `invoke_task`
- 显式 `task.cancel()`

### 8.3 取消必须依赖 cooperative cancellation

取消是否足够及时，取决于底层是否处于可中断的 `await` 点。

如果某个环节：

- 正在跑长时间同步阻塞函数
- 没有回到 async 边界

那 `CancelledError` 不会立刻生效，只能等它重新回到可中断的 await 链路。

### 8.4 文档必须说明“本地停”和“远端停”的区别

这是很容易产生误解的地方。

开发时应始终明确：

- 我们能稳定控制的是本地链路
- 远端 provider 是否真停，不由 LangChain 单独保证

## 9. 当前项目的体验策略

当前实现下，用户主动停止生成后的体验是：

1. 前端立即停止继续显示新 token
2. 不弹出普通错误提示
3. 将已经生成的片段落定为一条本地 assistant 消息
4. 该消息会明确标记为“已停止生成”
5. 会话列表仍会回源同步，但当前消息视图不会立刻用服务端结果覆盖本地中断片段

这是一种“保留片段 + 明确中断”的产品策略，优点是：

- 用户不会感觉内容突然消失
- 当前轮对话是否被主动打断是可感知的
- 不会把中断误认为一次完整成功回答

如果后续要继续细化体验，通常有三种方向：

1. 清空过程态
   - 实现简单
   - 状态最干净
2. 保留已生成片段，并标记“已中断”
   - 用户感知更自然
   - 但要定义消息持久化策略
3. 保留片段，但不入正式消息
   - 适合调试模式
   - 需要额外区分“临时展示”和“最终消息”

## 10. 推荐实现清单

后续在其他聊天项目复用时，建议至少检查这些点：

### 前端

- 是否使用 `AbortController`
- 是否把主动取消和普通错误区分开
- 是否在停止后做状态收敛或服务端同步

### API 层

- 是否使用 `request.is_disconnected()`
- 是否能在断连时停止等待下一条事件
- 是否能在 `finally` 中关闭流式迭代器

### 服务层

- 是否把 `ainvoke()` / `astream()` 包装为可取消任务
- 是否在取消后显式 `task.cancel()`
- 是否处理 `CancelledError`
- 是否避免 producer / consumer 残留悬挂任务

### 文档与协议

- 是否明确区分“停止”“错误”“完成”
- 是否说明本地取消与远端 provider 取消的边界
- 是否把当前产品策略写清楚

## 12. 一句话总结

聊天里的“停止生成”不是一个单点功能，而是一条**从前端 HTTP 中断、到 SSE 断连感知、再到 Agent 协程取消传播**的完整链路。

真正稳定的实现方式，不是“只把界面停住”，而是让取消信号逐层渗透到本地 Agent 执行任务，同时明确告知团队：**本地可以尽早停，远端 provider 是否真停取决于更底层的 SDK 与服务能力。**
