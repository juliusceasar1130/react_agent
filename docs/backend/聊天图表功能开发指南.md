## 1. 背景

这次图表功能开发的起点，不是“单纯想加一个前端图表组件”，而是用户在使用聊天式 SQL Agent 做趋势分析时，已经能够拿到表格结果和文本解读，但面对时间趋势、分类对比、Top N 排名这类问题时，单看表格不够直观。尤其在缺陷趋势分析场景中，用户往往希望继续追问“生成趋势图”“看柱状图”，而不是跳出当前聊天界面去单独做报表。

需求讨论一开始就明确了几个边界：

- 图表不是默认输出，避免每次查询都把聊天界面变成报表页
- LLM 需要主动提醒用户“这类结果适合生成图表”，但只有用户明确要求时才真正作图
- 大量 `rows` 不能重复进入 LLM 上下文，否则会带来 token 膨胀、ToolMessage 冗余和存储压力
- 图表必须能在前端聊天消息中直接渲染，而不是只生成图片或导出文件

围绕这些约束，图表功能最终被设计成一个“聊天内嵌 artifact 能力”，而不是传统报表系统。

## 2. 这套方案解决什么问题

- 让聊天式分析结果在当前会话内完成“表格 -> 解释 -> 图表”的自然升级
- 让 LLM 只负责判断“该不该画、画什么”，不承担大数据载荷搬运
- 避免图表数据重复回流到模型上下文，控制 token 成本
- 复用现有 `tool_call / tool_result / final` 流式协议，不新开第二条聊天链路
- 复用现有 CSV artifact 的设计经验，让图表也走 `artifact ref -> 前端拉取实体` 的模式
- 把图表逻辑限制在“聚合结果可视化”，避免明细大表直接绘图带来的性能和体验问题
- 为后续扩展堆叠图、双 Y 轴、多系列趋势图留下稳定的数据契约基础

## 3. 整体设计

这次实现采用了“4 层分工”：

1. `LLM 决策层`
2. `图表工具层`
3. `artifact 存储与 API 层`
4. `前端渲染层`

核心设计原则是：
**LLM 只输出小而明确的图表意图，后端工具生成并存储完整图表实体，前端按 `chart_id` 拉取并渲染。**

这套设计不是一开始就直接定下来的，而是经过了多轮方案评审：

- 放弃“把完整 `chart_spec + rows` 作为工具结果直接回给 LLM”
- 放弃“前端根据表格结果自动猜图”
- 借鉴了 Vanna 一类产品“引用传递而非数据搬运”的思路
- 最终选定 `chart_artifact_ref -> chart_spec` 这条路径

## 4. 需求讨论到技术路径选型

### 4.1 产品规则如何定下来的

需求讨论阶段最终收敛为三条产品规则：

1. 默认不自动生成图表
2. 当结果明显适合可视化时，LLM 只做提醒
3. 当用户明确说“生成图表 / 趋势图 / 柱状图”时，才调用图表工具

这条规则最后体现在 [backend/app/agent/service.py](/f:/000_dev/Python/workplace/rearch_agent/.tree/features/agent/backend/app/agent/service.py) 的系统提示词中。

### 4.2 为什么没有采用“完整结果直接回给 LLM”

讨论过程中很早就识别出一个关键风险：LangChain / LangGraph 的工具执行循环会把工具结果回传给模型。如果图表工具直接返回完整 `rows`：

- SQL 查询结果先进入一次上下文
- 图表工具结果又把同样的数据再塞一次
- 最终 assistant 还会基于这些内容继续回答

这会导致：

- token 成本明显上升
- `tool_results` 持久化体积变大
- 多轮会话时更容易造成上下文污染

因此最终选定：

- LLM 只拿轻量 `chart_artifact_ref`
- 前端单独通过 `chart_id` 取完整 `chart_spec`

### 4.3 为什么没有采用“文件名传递”的 Vanna 式表层方案

讨论中专门研究过 Vanna 2.0 一类方案：`run_sql` 保存 CSV，LLM 再把 `filename` 传给 `visualize_data`。

最终借鉴的是其**架构原则**，不是其**具体协议**：

- 借鉴：通过引用传递数据，不让 LLM 搬运大表
- 不照搬：不把文件系统文件名作为长期协议核心

在本项目中，更稳定的做法是：

- 查询或图表实体由服务端管理
- 对前端和 LLM 暴露的是 `file_id` / `chart_id`
- 不暴露底层真实文件名

### 4.4 为什么第一阶段允许重跑 SQL

第一阶段没有去改造 `sql_db_query` 的协议，让它返回结构化 `query_result_ref`。所以当用户跨轮说“把刚才结果画成图”时，图表工具会重跑一条聚合 SQL。

这是一个明确的取舍：

- 收益：改动小、落地快、风险低
- 代价：可能重复执行一次聚合 SQL

对于当前聚合型图表场景，这个取舍是可接受的。

## 5. 核心调用链 / 执行流

最终落地后的正确链路如下：

1. 用户先提分析问题，Agent 正常走 `load_skill -> sql_db_query -> 文本/表格答复`
2. 如果结果属于趋势、对比、Top N 等适合可视化的类型，LLM 在回答末尾明确提醒用户可生成图表
3. 用户回复“生成趋势图”或类似请求
4. Agent 根据 [backend/app/agent/service.py](/f:/000_dev/Python/workplace/rearch_agent/.tree/features/agent/backend/app/agent/service.py) 的提示词，调用 `build_chart_artifact`
5. `build_chart_artifact` 在 [backend/app/agent/tools/chart_artifact_tool.py](/f:/000_dev/Python/workplace/rearch_agent/.tree/features/agent/backend/app/agent/tools/chart_artifact_tool.py) 中执行只读聚合 SQL、校验参数、生成 `chart_spec`
6. `chart_spec` 通过 [backend/app/chart_artifacts.py](/f:/000_dev/Python/workplace/rearch_agent/.tree/features/agent/backend/app/chart_artifacts.py) 落成 artifact 文件，并返回轻量 `chart_artifact_ref`
7. `final` 消息与 `tool_results` 一起落库，前端消息中拿到 `chart_id`
8. 前端 [frontend/src/components/MessageItem.vue](/f:/000_dev/Python/workplace/rearch_agent/.tree/features/agent/frontend/src/components/MessageItem.vue) 识别图表 artifact
9. [frontend/src/components/ChartArtifactCard.vue](/f:/000_dev/Python/workplace/rearch_agent/.tree/features/agent/frontend/src/components/ChartArtifactCard.vue) 用 [frontend/src/api/charts.ts](/f:/000_dev/Python/workplace/rearch_agent/.tree/features/agent/frontend/src/api/charts.ts) 调用 `/api/chat/charts/{chart_id}`
10. 前端拿到完整 `chart_spec` 后，使用 `ECharts` 渲染聊天内嵌图表卡片

不应该走的链路是：

- LLM 直接把完整图表大 JSON 填进工具参数
- 或工具把完整图表大 JSON 再回传给 LLM

这两条都会把本来应该给前端消费的数据再次引回模型上下文。

## 6. 分层职责说明

### 6.1 LLM 决策层

入口文件：

- [backend/app/agent/service.py](/f:/000_dev/Python/workplace/rearch_agent/.tree/features/agent/backend/app/agent/service.py)

职责：

- 决定什么时候提醒用户可生成图表
- 决定用户明确要求后调用 `build_chart_artifact`
- 约束 LLM 如何填写 `series`
- 限制模型不要使用未支持的 `metric / label / type / axis` 这类自定义字段

为什么这样设计：

- 图表生成规则最好在 Agent 提示词层统一约束
- 让模型理解“什么时候该提醒、什么时候该执行”比前端硬编码更灵活

设计经验：

- 仅靠“简短提醒”太弱，模型会退化成“是否需要进一步分析”这类泛泛收尾，必须写成明确引导语

### 6.2 图表工具层

入口文件：

- [backend/app/agent/tools/chart_artifact_tool.py](/f:/000_dev/Python/workplace/rearch_agent/.tree/features/agent/backend/app/agent/tools/chart_artifact_tool.py)

职责：

- 定义图表工具结构化入参 `BuildChartArtifactInput`
- 执行只读 SQL
- 校验 `x_field`、`series.field`、`category_field/category_value`
- 识别 `line / bar / auto`
- 生成完整 `chart_spec`
- 返回轻量 `chart_artifact_ref`

为什么这样设计：

- 数据校验应该放在后端工具，不应该完全信任 LLM
- `series` 必须用结构化 schema 收紧，否则模型很容易“脑补”参数

设计经验：

- `series` 从 `list[dict[str, Any]]` 收紧到明确 schema，是整套图表能力稳定性的关键转折点

### 6.3 artifact 存储与 API 层

入口文件：

- [backend/app/chart_artifacts.py](/f:/000_dev/Python/workplace/rearch_agent/.tree/features/agent/backend/app/chart_artifacts.py)
- [backend/app/api.py](/f:/000_dev/Python/workplace/rearch_agent/.tree/features/agent/backend/app/api.py)
- [backend/app/schemas.py](/f:/000_dev/Python/workplace/rearch_agent/.tree/features/agent/backend/app/schemas.py)

职责：

- 生成 `chart_id`
- 持久化完整 `chart_spec`
- 校验 `chart_id` 与过期时间
- 提供 `/api/chat/charts/{chart_id}` 读取接口
- 给前后端定义统一的 `ChartArtifactRef / ChartArtifactResponse / ChartSeriesDefinition`

为什么这样设计：

- 前端应拿到稳定的图表实体协议，而不是直接解析 tool 文本
- 图表实体要和聊天消息解耦，方便刷新页面后重渲染

设计经验：

- 图表 artifact 与 CSV export record 虽然思路相近，但不建议混为同一套文件下载语义

### 6.4 前端渲染层

入口文件：

- [frontend/src/components/MessageItem.vue](/f:/000_dev/Python/workplace/rearch_agent/.tree/features/agent/frontend/src/components/MessageItem.vue)
- [frontend/src/components/ChartArtifactCard.vue](/f:/000_dev/Python/workplace/rearch_agent/.tree/features/agent/frontend/src/components/ChartArtifactCard.vue)
- [frontend/src/api/charts.ts](/f:/000_dev/Python/workplace/rearch_agent/.tree/features/agent/frontend/src/api/charts.ts)
- [frontend/src/types/index.ts](/f:/000_dev/Python/workplace/rearch_agent/.tree/features/agent/frontend/src/types/index.ts)

职责：

- 从消息的 `tool_results` 中识别图表 artifact
- 根据 `chart_id` 拉取完整图表数据
- 按 `chart_type / x_field / series / rows` 组织 ECharts option
- 在聊天消息中直接渲染卡片

为什么这样设计：

- 前端是 renderer，不是 planner
- 不让前端自己猜图，可以降低语义偏差

设计经验：

- `ChartArtifactCard` 只消费受控 `chart_spec`，不要让前端直接接受模型生成的任意 ECharts option

## 7. 关键设计取舍

### 7.1 选择 artifact-ref，而不是完整图表结果回流给 LLM

选择：

- 工具返回 `chart_artifact_ref`

原因：

- 控制上下文体积
- 控制 ToolMessage 冗余
- 让前端通过 `chart_id` 取实体

收益：

- 对话更轻
- 存储更稳
- 便于刷新重渲染

代价：

- 前端需要多发一次读取请求

### 7.2 选择“显式触发生成”，而不是自动作图

选择：

- 默认提醒，不自动画图

原因：

- 聊天不是报表系统
- 避免在不需要时增加前端负担

收益：

- 交互更自然
- 不会稀里糊涂地把每次结果都作图

代价：

- 需要更强的提示词来引导用户发现图表能力

### 7.3 选择后端决定契约，前端只渲染

选择：

- 图表格式由后端 schema 控制

原因：

- 减少前端猜测
- 减少 LLM 输出自由度

收益：

- 工具入参与前端渲染更稳定

代价：

- 图表能力扩展时需要同步调整 schema

### 7.4 第一阶段允许重跑 SQL

选择：

- 用户跨轮要求作图时，允许重新执行聚合 SQL

原因：

- 暂不改造 `sql_db_query` 协议

收益：

- 第一阶段能快速上线

代价：

- 会重复跑一次聚合 SQL

## 8. 实现项目落地的关键模块

### 8.1 后端配置

图表功能首版引入了三个关键配置：

- `CHART_ARTIFACT_DIR`
- `CHART_ARTIFACT_TTL_HOURS`
- `CHART_ARTIFACT_MAX_POINTS`

对应目标：

- artifact 文件目录可控
- 过期策略可控
- 点数上限可控

### 8.2 后端类型契约

核心契约定义在 [backend/app/schemas.py](/f:/000_dev/Python/workplace/rearch_agent/.tree/features/agent/backend/app/schemas.py)：

- `ChartArtifactRef`
- `ChartSeriesDefinition`
- `ChartArtifactResponse`

这三个模型分别承担：

- 给 LLM 的轻量返回
- 给前后端共享的系列定义
- 给前端渲染的完整图表实体

### 8.3 图表工具参数模型

图表工具最终使用两个 Pydantic 模型来约束参数：

- `ChartSeriesInput`
- `BuildChartArtifactInput`

其中最重要的约束包括：

- `field` 必须引用数值列
- `category_field` 和 `category_value` 必须成对出现
- 未支持的系列键不能混进来
- 顶层未知字段默认拒绝，但允许框架注入的 `runtime`

### 8.4 前端图表卡片

前端最终不是直接画“整个 rows 表”，而是根据 `series` 去组织数据：

- 用 `x_field` 生成横轴
- 若存在 `category_field/category_value`，先过滤出对应分类的行
- 再为每条系列生成自己的数据数组

这一步是解决多分类拆线的关键。

## 9. 开发过程中遇到的问题与解决方案

### 9.1 问题一：图表该自动生成，还是显式触发

现象：

- 如果自动生成，聊天回答会变得很重
- 如果完全不提醒，用户又不知道图表能力存在

解决方案：

- 系统提示词要求：适合可视化时必须提醒，但只有用户明确要求时才调用工具

经验结论：

- 聊天式图表最适合“提醒 + 明确触发”的双阶段模式

### 9.2 问题二：把完整 `rows` 回给 LLM 会导致上下文膨胀

现象：

- SQL 结果已经给过模型一次
- 图表工具若再返回完整 `rows`，就是重复搬运

解决方案：

- 工具返回 `chart_artifact_ref`
- 完整 `chart_spec` 只给前端

经验结论：

- 图表数据实体应交给前端，不应反复回流给模型

### 9.3 问题三：图表卡片拿到了数据，但页面仍然空白

现象：

- 标题、说明、点数都显示出来了
- 图表区域却是空白

根因：

- `ChartArtifactCard` 在 `loading=true` 时就调用了 `renderChart()`
- 此时真实图表容器还没挂载

解决方案：

- 将渲染延后到 `loading` 结束后
- 重建实例前先 dispose 旧实例
- 补一次 `resize()`

经验结论：

- ECharts 初始化时机必须晚于真实 DOM 就绪时机

### 9.4 问题四：多系列对比图里 A7 和 TiguanL 重合

现象：

- 多系列图看起来像只有一条线
- A7 和 TiguanL 实际画成了同一组数据

根因：

- 首版只支持“多个不同数值字段”
- 对“同一指标按分类拆线”支持不完整

解决方案：

- 引入 `category_field / category_value`
- 前端按分类过滤 `rows`
- 后端支持从系列名自动推断分类值

经验结论：

- 多系列图不能只重复 `field`，必须明确“系列属于哪个分类值”

### 9.5 问题五：LLM 会填出 `metric / label / type / axis` 这类错误参数

现象：

- LLM 虽然调用了正确工具，但会自己发明字段
- 还可能把 `field` 填成分类列，如 `defect_type_name`

根因：

- `series` 早期是 `list[dict[str, Any]]`
- 契约太松，模型容易脑补

解决方案：

- 用 `BuildChartArtifactInput / ChartSeriesInput` 收紧 schema
- 明确 `extra` 行为
- 增加数值列校验和分类配对校验

经验结论：

- 只靠提示词不够，必须让工具自身做强校验

### 9.6 问题六：单车型图表在结构化调用下失败

现象：

- `tool.func(...)` 正常
- 实际工具链里却报 `missing 1 required positional argument: 'runtime'`

根因：

- 切到结构化 `args_schema` 后，某些调用路径没有拿到 runtime 注入

解决方案：

- 将工具函数里的 `runtime` 调整为可选

经验结论：

- 在真实 Agent 路径、直接 `tool.invoke(...)` 路径和测试路径之间，要特别留意注入参数兼容性

### 9.7 问题七：真实 ToolNode 又因为注入 `runtime` 被 `args_schema` 拦住

现象：

- LangSmith trace 中出现 `Error invoking tool ...`
- 工具函数内部的错误字符串根本没有机会返回

根因：

- LangGraph `ToolNode` 会把 `runtime` 注入 tool kwargs
- `BuildChartArtifactInput` 顶层使用 `extra="forbid"`
- `runtime` 在进入函数体前就被 Pydantic 当成非法字段拦截

解决方案：

- 将顶层策略改成“允许 `runtime`，继续拒绝其他未知字段”
- 补上覆盖该链路的回归测试

经验结论：

- 要区分“给 LLM 的 schema”与“给框架注入参数的真实执行上下文”

## 10. 易错点 / 反模式

- 不要让图表工具直接把完整 `rows` 回给 LLM，否则会造成重复上下文
- 不要让前端自己根据表格猜图，否则图表语义会漂移
- 不要把多系列对比理解成“同一个 `field` 重复几次”，分类拆线必须显式建模
- 不要只靠提示词约束参数，工具端必须做数值列校验和未知键拦截
- 不要假设 `tool.invoke(args)` 和真实 `ToolNode` 路径的注入行为完全一致
- 不要在 `loading` 状态下过早初始化 ECharts

## 11. 推荐复用模板 / 标准做法

如果后续要在别的分析主题上复用聊天图表能力，建议按这套步骤走：

1. 先定义清晰的图表触发规则：默认提醒还是自动生成
2. 先定义 artifact 模式：是否给 LLM 返回 ref，是否给前端单独读取实体
3. 先定义后端统一 schema：
   - 顶层图表请求
   - 系列定义
   - 轻量 ref
   - 完整实体
4. 先把工具端校验补齐，再放给 LLM 使用
5. 前端只消费受控 schema，不接收任意可执行配置
6. 补三类测试：
   - 普通 invoke
   - 注入 runtime 的真实链路
   - 前端 / API 渲染链路

哪些内容可以直接复制：

- `artifact ref -> artifact entity` 的整体架构
- `series` 结构化 schema 设计方式
- `category_field / category_value` 的分类拆线模式
- 图表卡片按 `chart_id` 拉取实体的前端组织方式

哪些内容必须按场景调整：

- SQL 聚合口径
- 图表字段命名
- 点数上限
- 图表类型白名单

## 12. 推荐检查清单

### 后端

- [ ] 是否明确只有用户显式要求时才调用图表工具
- [ ] 工具是否只允许只读 SQL
- [ ] 是否限制了图表点数上限
- [ ] 是否将完整图表数据存成 artifact，而不是回传给 LLM
- [ ] 是否对 `series.field` 做了数值列校验
- [ ] 是否对多分类拆线做了 `category_field/category_value` 约束
- [ ] 是否兼容 `runtime` 注入与无 runtime 的调用路径

### 前端

- [ ] 是否通过 `chart_id` 拉取完整图表实体
- [ ] 是否在 DOM 就绪后再初始化 ECharts
- [ ] 是否支持多系列按分类拆线
- [ ] 是否在 artifact 过期或不存在时给出可理解错误提示

### 协议 / 数据 / 文档

- [ ] `ChartArtifactRef` 与 `ChartArtifactResponse` 是否已统一
- [ ] 是否明确顶层允许的额外字段只有 `runtime`
- [ ] 是否在提示词中明确告诉 LLM 图表工具的字段约束
- [ ] 是否把已踩过的坑记录进文档或 changelog

## 13. 验证与交付经验

图表功能落地后，关键验证不应只做“能不能出图”，而应至少覆盖：

- 后端 artifact 存取是否正常
- 图表工具是否能返回轻量 ref
- 图表工具是否能拒绝错误参数
- ToolNode 注入 `runtime` 时是否仍能通过 schema 校验
- API 是否能按 `chart_id` 正确读取 artifact
- 前端是否能在聊天消息中恢复渲染图表

在本次开发历史中，已明确跑通过的回归包括：

- `backend/app/test_chart_artifact_tool.py`
- `backend/app/test_chart_api.py`
- `backend/app/test_agent_service_prompt.py`

历史实现阶段也对前端跑过构建校验，确认 `ChartArtifactCard` 这条渲染链路可编译通过。已知非阻塞告警主要包括：

- SQLAlchemy `MovedIn20Warning`
- 前端构建的大包体 warning
- LangSmith 在本地无网络时的连接告警

这些不是图表功能本身的阻塞问题，但在交付说明里应单独标记，不要和图表故障混为一谈。

## 14. 后续可选优化方向

- 第二阶段把 `sql_db_query` 升级为 `query_result_ref`，减少跨轮作图时的重复 SQL
- 支持更多图型，如堆叠柱状图、组合图、占比图
- 在图表卡片中增加导出 PNG / 切换图型能力
- 为图表 artifact 增加后台清理任务，而不是只靠读取时判断过期
- 在前端加入更细粒度的空数据、过期数据、权限异常提示

## 15. 一句话总结

聊天图表功能最值得复用的原则不是“怎么画图”，而是：**让 LLM 决策图表意图，让后端工具生成受控 artifact，让前端按引用渲染实体，并把所有易错点收敛到 schema 与工具校验里。**
