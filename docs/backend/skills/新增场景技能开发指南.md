# 新增场景技能开发指南

修改时间：2026-04-05 Asia/Shanghai

主要修改内容：
- 新增一份面向维护者的操作教程，说明如何在已有领域下新增一个固定场景
- 覆盖场景元数据、SQL 模板、注册方式、验证步骤与易错点

## 背景

当前业务技能系统采用二级披露结构：

1. 领域 skill 负责提供公共业务知识
2. 场景 skill 负责提供固定任务的 workflow、规则、易错点和模板引用

当用户提问属于高频、稳定、可复用的固定统计或固定流程时，推荐在已有领域下新增一个场景，而不是继续把细节堆进 `domain.md`。

## 适用场景

适合新增为场景 skill 的问题通常具备以下特征：

- 高频重复出现
- 统计口径稳定
- workflow 固定
- 输出结构比较稳定
- 后续可能升级为模板执行器或专用 tool

例如：

- 每日各区域车身数量统计
- 当前缓冲区车辆快照
- 各缺陷类型分布汇总
- 班次成本汇总

## 场景层在整体架构中的位置

以当前结构为例：

```text
backend/app/skills/domains/<domain_name>/
  domain.md
  meta.py
  scenarios/
    <scenario_name>.py
  sql/
    <scenario_name>.sql
  scripts/
```

其中：

- `domain.md` 放公共知识
- `scenarios/*.py` 放场景元数据
- `sql/*.sql` 放模板
- `scripts/` 预留给后续执行脚本或后处理逻辑

## 新增场景的标准步骤

### 第 1 步：确定场景是否值得独立

在新增前，先判断这个问题是否应该独立成场景：

建议新增场景的情况：

- 有明确统计口径
- 有明确输入参数
- 有固定输出格式
- 后续很可能被复用

不建议新增场景的情况：

- 只是临时一次性查询
- 口径还经常变化
- 本质上只是普通自由探索问题

### 第 2 步：新增场景元数据文件

位置示例：

```text
backend/app/skills/domains/paint_shop_vehicle_tracking/scenarios/current_area_distribution.py
```

推荐字段模板：

```python
SCENARIO = {
    "skill_name": "paint_shop_vehicle_tracking",
    "name": "current_area_distribution",
    "title": "当前各区域车身分布",
    "description": "统计当前快照下各工艺区域的有效车身数量分布。",
    "triggers": [
        "当前各区域有多少车",
        "查看区域车身分布",
        "统计当前区域车辆情况",
    ],
    "intent_keywords": ["区域", "分布", "当前", "车身数量"],
    "required_inputs": ["snapshot_time"],
    "optional_inputs": ["area_names"],
    "workflow": [
        "确认是否为当前快照统计。",
        "应用有效车辆规则。",
        "按 process_area 聚合统计。",
        "输出区域分布和总计。",
    ],
    "rules": [
        "只统计有效车辆。",
        "聚合必须在数据库中完成。",
    ],
    "gotchas": [
        "当前快照与时间窗口不能混用。",
    ],
    "output_contract": "输出 process_area、vehicle_count，并附带口径说明。",
    "sql_template_refs": [
        {
            "type": "sql",
            "name": "current_area_distribution",
            "path": "paint_shop_vehicle_tracking/sql/current_area_distribution.sql",
            "description": "当前区域车身分布 SQL 模板。",
        }
    ],
    "script_refs": [],
}
```

### 第 3 步：新增外部 SQL 模板

对应场景的 SQL 应独立存放，不要内嵌到场景文件正文中。

位置示例：

```text
backend/app/skills/domains/paint_shop_vehicle_tracking/sql/current_area_distribution.sql
```

建议：

- SQL 模板只负责表达核心查询逻辑
- 如果未来需要参数替换，可在第二阶段升级为模板执行器
- 当前阶段只作为引用和渲染展示来源

### 第 4 步：在领域注册表中挂接

当前项目的 `registry.py` 是显式注册模式，所以新增场景后需要：

1. 导入新的场景常量 `SCENARIO`
2. 将其追加到 `_RAW_SCENARIOS[SCENARIO["skill_name"]]`

示例：

```python
from ...current_area_distribution import SCENARIO as CURRENT_AREA_DISTRIBUTION

_RAW_SCENARIOS[CURRENT_AREA_DISTRIBUTION["skill_name"]].append(
    CURRENT_AREA_DISTRIBUTION
)
```

只新增场景而不改注册中心，系统不会识别该场景。

## 场景设计原则

### 1. 一个场景只解决一个稳定问题

不要把“区域统计 + 车型分布 + 异常分析”塞进同一个场景。  
一个场景应只服务一个固定任务。

### 2. 公共知识仍留在领域层

不要在场景里重复写：

- 全量表结构
- 所有字段说明
- 所有业务规则

这些内容应该继续留在 `domain.md`。

### 3. 场景层重点写四类信息

场景层最有价值的信息通常是：

- 这个场景解决什么问题
- 固定 workflow 是什么
- 有哪些统计口径和易错点
- 输出格式应该如何约束

### 4. 模板和脚本独立文件

不要把大段 SQL 或脚本正文塞进场景文件。  
场景文件更像 playbook，不是执行实现本身。

## 验证清单

新增场景后，建议至少检查：

1. `get_scenario_by_name("<skill>", "<scenario>")` 能查到
2. `list_scenarios_by_skill("<skill>")` 包含该场景
3. `load_scenario_content("<skill>", "<scenario>")` 能输出完整 playbook
4. 渲染文本中包含：
   - `workflow`
   - `rules`
   - `gotchas`
   - `output_contract`
   - SQL 模板引用

## 常见错误

### 1. 场景未加入注册中心

表现：

- `load_scenario()` 提示找不到场景

### 2. `skill_name` 写错

表现：

- 场景被挂到错误领域
- 场景查找失败

### 3. SQL 模板路径不对

表现：

- 渲染阶段读取 `.sql` 文件失败

### 4. 场景定义过大

表现：

- 场景文件越来越像“第二份 domain.md”
- 后续维护困难

## 一句话总结

场景 skill 的本质不是“再写一份领域文档”，而是把一个高频稳定任务沉淀成可按需加载的 playbook，并通过外部 SQL/脚本资产保持实现与说明解耦。
