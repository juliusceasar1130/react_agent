# 新增场景技能开发指南

修改时间：2026-04-06 Asia/Shanghai

主要修改内容：
- 新增一份面向维护者的操作教程，说明如何在已有领域下新增一个固定场景
- 覆盖场景元数据、SQL 模板、注册方式、验证步骤与易错点
- 新增场景参数化筛选机制说明

## 背景

当前业务技能系统采用二级披露结构：

1. 领域 skill 负责提供公共业务知识
2. 场景 skill 负责提供固定任务的 workflow、规则、易错点和模板引用

当用户提问属于高频、稳定、可复用的固定统计或固定流程时，推荐在已有领域下新增一个场景，而不是继续把细节堆进 `domain.md`。

## 适用场景

适合新增为场景 skill 的问题通常具备以下特征：

- 高频重复出现
- 统计口径稳定
- workflow 固定
- 输出结构比较稳定
- 后续可能升级为模板执行器或专用 tool

例如：

- 每日各区域车身数量统计
- 当前缓冲区车辆快照
- 各缺陷类型分布汇总
- 班次成本汇总

## 场景层在整体架构中的位置

以当前结构为例：

```text
backend/app/skills/domains/<domain_name>/
  domain.md
  meta.py
  scenarios/
    <scenario_name>.py
  sql/
    <scenario_name>.sql
  scripts/
```

其中：

- `domain.md` 放公共知识
- `scenarios/*.py` 放场景元数据
- `sql/*.sql` 放模板
- `scripts/` 预留给后续执行脚本或后处理逻辑

## 新增场景的标准步骤

### 第 1 步：确定场景是否值得独立

在新增前，先判断这个问题是否应该独立成场景：

建议新增场景的情况：

- 有明确统计口径
- 有明确输入参数
- 有固定输出格式
- 后续很可能被复用

不建议新增场景的情况：

- 只是临时一次性查询
- 口径还经常变化
- 本质上只是普通自由探索问题

### 第 2 步：新增场景元数据文件

位置示例：

```text
backend/app/skills/domains/paint_shop_vehicle_tracking/scenarios/current_area_distribution.py
```

推荐字段模板：

```python
SCENARIO = {
    "skill_name": "paint_shop_vehicle_tracking",
    "name": "current_area_distribution",
    "title": "当前各区域车身分布",
    "description": "统计当前快照下各工艺区域的有效车身数量分布。",
    "triggers": [
        "当前各区域有多少车",
        "查看区域车身分布",
        "统计当前区域车辆情况",
    ],
    "intent_keywords": ["区域", "分布", "当前", "车身数量"],
    "required_inputs": ["snapshot_time"],
    "optional_inputs": ["area_names"],
    # 参数定义（新增）
    "parameters": {
        "process_area": {
            "type": "array",
            "items_type": "string",
            "description": "工艺区域名称列表，用于筛选特定区域的车身数量",
            "required": False,
            "source_column": "process_area",
            "source_table": "process_areas",
            "example_values": ["电泳", "面漆", "烘干"],
            "usage": "当用户询问特定区域时，将此参数添加到 SQL 的 WHERE 子句中",
            "sql_fragment": "AND rp.process_area IN ('{values}')",
        }
    },
    "workflow": [
        "确认是否为当前快照统计。",
        "应用有效车辆规则。",
        "按 process_area 聚合统计。",
        "输出区域分布和总计。",
    ],
    "rules": [
        "只统计有效车辆。",
        "聚合必须在数据库中完成。",
    ],
    "gotchas": [
        "当前快照与时间窗口不能混用。",
    ],
    "output_contract": "输出 process_area、vehicle_count，并附带口径说明。",
    "sql_template_refs": [
        {
            "type": "sql",
            "name": "current_area_distribution",
            "path": "paint_shop_vehicle_tracking/sql/current_area_distribution.sql",
            "description": "当前区域车身分布 SQL 模板。",
        }
    ],
    "script_refs": [],
}
```

### 参数定义说明（parameters）

当场景需要支持动态参数筛选时，应在 `parameters` 字段中详细描述每个参数：

**字段解释：**

| 字段 | 类型 | 说明 |
|------|------|------|
| `type` | str | 参数类型：`array`、`string`、`integer` 等 |
| `items_type` | str | 数组元素类型（仅 `type="array"` 时使用） |
| `description` | str | 参数用途说明，帮助 LLM 理解何时使用 |
| `required` | bool | 是否必填 |
| `source_column` | str | 数据库列名 |
| `source_table` | str | 可选值来源表（用于 LLM 查询可选值） |
| `example_values` | list | 示例值列表 |
| `usage` | str | 使用方式说明 |
| `sql_fragment` | str | SQL 片段模板，`{values}` 为占位符 |

**设计原则：**

1. 参数说明应让 LLM 能自主判断是否需要填充
2. 提供 `source_table` 让 LLM 能查询可选值
3. `sql_fragment` 应是可直接拼接的 SQL 条件
4. `description` 和 `usage` 要描述清楚触发条件

### 第 3 步：新增外部 SQL 模板

对应场景的 SQL 应独立存放，不要内嵌到场景文件正文中。

位置示例：

```text
backend/app/skills/domains/paint_shop_vehicle_tracking/sql/current_area_distribution.sql
```

建议：

- SQL 模板只负责表达核心查询逻辑
- 如果场景支持参数筛选，应在 SQL 中添加参数注释和使用示例
- 当前阶段只作为引用和渲染展示来源

**参数化 SQL 模板示例：**

```sql
-- 当前区域车身分布 SQL 模板
--
-- 参数说明:
--   process_area: 可选，工艺区域名称列表（如 ['电泳', '面漆']）
--                 不传则查询所有区域
--
-- 使用示例:
--   1. 查询所有区域: 保持原 SQL 不变
--   2. 查询电泳区域: 在 WHERE 子句末尾添加 AND rp.process_area = '电泳'
--   3. 查询多区域: 在 WHERE 子句末尾添加 AND rp.process_area IN ('电泳', '面漆')

SELECT
    rp.process_area,
    COUNT(*) AS vehicle_count
FROM rb_position_data rp
WHERE rp.vehicle_id LIKE '782026%'
  AND rp.body_type != '-----'
  AND rp.carrier_id <> '0'
  -- 可选参数: process_area（当用户指定特定区域时取消注释并填充值）
  -- 单区域示例: AND rp.process_area = '电泳'
  -- 多区域示例: AND rp.process_area IN ('电泳', '面漆')
GROUP BY rp.process_area
ORDER BY vehicle_count DESC;
```

**参数化 SQL 设计要点：**

1. 在文件头部添加参数说明，描述参数含义和默认行为
2. 提供多种使用示例（单值、多值、不传）
3. 在 SQL 中用注释标记可选条件，方便 LLM 参考
4. 注释示例应与 `sql_fragment` 字段保持一致

### 第 4 步：在领域注册表中挂接

当前项目的 `registry.py` 是显式注册模式，所以新增场景后需要：

1. 导入新的场景常量 `SCENARIO`
2. 将其追加到 `_RAW_SCENARIOS[SCENARIO["skill_name"]]`

示例：

```python
from ...current_area_distribution import SCENARIO as CURRENT_AREA_DISTRIBUTION

_RAW_SCENARIOS[CURRENT_AREA_DISTRIBUTION["skill_name"]].append(
    CURRENT_AREA_DISTRIBUTION
)
```

只新增场景而不改注册中心，系统不会识别该场景。

## 场景设计原则

### 1. 一个场景只解决一个稳定问题

不要把“区域统计 + 车型分布 + 异常分析”塞进同一个场景。  
一个场景应只服务一个固定任务。

### 2. 公共知识仍留在领域层

不要在场景里重复写：

- 全量表结构
- 所有字段说明
- 所有业务规则

这些内容应该继续留在 `domain.md`。

### 3. 场景层重点写四类信息

场景层最有价值的信息通常是：

- 这个场景解决什么问题
- 固定 workflow 是什么
- 有哪些统计口径和易错点
- 输出格式应该如何约束

### 4. 模板和脚本独立文件

不要把大段 SQL 或脚本正文塞进场景文件。  
场景文件更像 playbook，不是执行实现本身。

## 验证清单

新增场景后，建议至少检查：

1. `get_scenario_by_name("<skill>", "<scenario>")` 能查到
2. `list_scenarios_by_skill("<skill>")` 包含该场景
3. `load_scenario_content("<skill>", "<scenario>")` 能输出完整 playbook
4. 渲染文本中包含：
   - `workflow`
   - `rules`
   - `gotchas`
   - `output_contract`
   - SQL 模板引用

## 常见错误

### 1. 场景未加入注册中心

表现：

- `load_scenario()` 提示找不到场景

### 2. `skill_name` 写错

表现：

- 场景被挂到错误领域
- 场景查找失败

### 3. SQL 模板路径不对

表现：

- 渲染阶段读取 `.sql` 文件失败

### 4. 场景定义过大

表现：

- 场景文件越来越像“第二份 domain.md”
- 后续维护困难

## 一句话总结

场景 skill 的本质不是“再写一份领域文档”，而是把一个高频稳定任务沉淀成可按需加载的 playbook，并通过外部 SQL/脚本资产保持实现与说明解耦。
