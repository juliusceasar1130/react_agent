# 新增业务领域技能开发指南

修改时间：2026-04-05 Asia/Shanghai

主要修改内容：
- 新增一份面向维护者的操作教程，说明如何在当前二级 Skill 架构下增加新的业务领域
- 覆盖目录结构、注册机制、场景挂载、验证步骤与常见错误

## 背景

当前项目的业务技能系统已经从单文件 `backend/app/skills.py` 升级为 `backend/app/skills/` package，并采用了“领域 skill + 场景 skill”二级披露结构：

1. 领域 skill 提供公共业务知识、表结构说明和场景摘要
2. 场景 skill 提供固定任务的 workflow、规则、易错点和模板资产引用
3. 运行时先通过 `load_skill()` 加载领域，再按需通过 `load_scenario()` 加载固定场景

本文档用于指导后续如何新增一个新的业务领域，例如：

- `paint_shop_defect_analysis`
- `paint_shop_cost_analysis`
- `weld_shop_vehicle_tracking`

## 这份教程解决什么问题

如果只在 `backend/app/skills/domains/` 下新建一个目录，系统并不会自动发现该领域。当前实现使用的是“显式注册（manual registry）”模式，新领域需要同时完成：

1. 新建领域目录与元数据文件
2. 新建领域公共说明文档
3. 按需新增场景定义与外部 SQL 模板
4. 在注册中心中显式接入
5. 验证 `SKILLS`、`load_skill()`、`load_scenario()` 都能识别

## 当前技能系统结构

以现有的 `paint_shop_vehicle_tracking` 为例：

```text
backend/app/skills/
  __init__.py
  assets.py
  loaders.py
  models.py
  registry.py
  renderers.py
  domains/
    paint_shop_vehicle_tracking/
      domain.md
      meta.py
      scenarios/
        daily_area_body_count.py
      sql/
        daily_area_body_count.sql
      scripts/
        README.md
```

职责分层如下：

- `models.py`
  - 定义 `DomainSkill`、`ScenarioSkill`、`AssetRef` 等结构
- `assets.py`
  - 负责读取 `domain.md`、`.sql` 等外部文本资产
- `renderers.py`
  - 将领域和场景渲染成 LLM 可读文本
- `registry.py`
  - 将领域、场景和资产组织成运行时注册中心
- `loaders.py`
  - 对外提供 `load_domain_content()` 和 `load_scenario_content()`
- `domains/<domain_name>/`
  - 保存领域自己的元数据、文档、场景和模板

## 新增一个业务领域的标准步骤

### 第 1 步：创建领域目录

在 `backend/app/skills/domains/` 下新建新的领域目录，例如：

```text
backend/app/skills/domains/paint_shop_defect_analysis/
```

建议至少创建以下文件与目录：

```text
paint_shop_defect_analysis/
  __init__.py
  meta.py
  domain.md
  scenarios/
    __init__.py
  sql/
  scripts/
    README.md
```

### 第 2 步：编写 `meta.py`

`meta.py` 只放领域元数据，不放详细业务正文。

参考模板：

```python
DOMAIN_META = {
    "name": "paint_shop_defect_analysis",
    "description": "涂装车间缺陷分析领域，用于处理缺陷分布、缺陷趋势、缺陷责任归因等统计与分析问题。",
    "tags": ["paint_shop", "defect_analysis", "scenario_enabled"],
}
```

设计要求：

- `name` 必须全局唯一
- 建议使用稳定的英文 snake_case 标识
- `description` 要简洁，供 `SkillMiddleware` 注入系统提示词使用
- `tags` 用于后续扩展，不参与当前主链路判断

### 第 3 步：编写 `domain.md`

`domain.md` 放该领域的公共业务知识，不要把所有固定问题直接写进去。

建议内容包括：

- 核心业务表
- 字段含义
- 主关联关系
- 通用业务规则
- 统计口径总原则
- 空值、状态位、时间口径等公共注意事项

不建议放：

- 所有场景的完整 SQL
- 每个报表的详细 workflow
- 大段脚本实现

这些内容应该留给场景层和外部资产层。

### 第 4 步：新增场景定义

如果这个领域暂时还没有固定场景，可以先只完成领域注册。  
如果已经有高频稳定场景，建议至少新增一个样板场景。

场景文件位置示例：

```text
backend/app/skills/domains/paint_shop_defect_analysis/scenarios/daily_defect_summary.py
```

参考模板：

```python
SCENARIO = {
    "skill_name": "paint_shop_defect_analysis",
    "name": "daily_defect_summary",
    "title": "每日缺陷汇总统计",
    "description": "统计指定日期下各类缺陷数量及占比。",
    "triggers": [
        "今天缺陷情况怎么样",
        "统计每日缺陷汇总",
        "查看各类缺陷数量",
    ],
    "intent_keywords": ["缺陷", "汇总", "统计"],
    "required_inputs": ["stat_date"],
    "optional_inputs": ["shift", "line_name"],
    "workflow": [
        "先确认是按自然日还是按班次口径统计。",
        "应用有效缺陷记录过滤规则。",
        "按缺陷类型聚合统计。",
        "输出数量、占比和口径说明。",
    ],
    "rules": [
        "只统计有效缺陷记录。",
        "聚合必须在数据库中完成。",
    ],
    "gotchas": [
        "自然日和班次口径不能混用。",
    ],
    "output_contract": "输出 defect_type、defect_count、defect_ratio，并附带统计口径说明。",
    "sql_template_refs": [
        {
            "type": "sql",
            "name": "daily_defect_summary",
            "path": "paint_shop_defect_analysis/sql/daily_defect_summary.sql",
            "description": "每日缺陷汇总 SQL 模板。",
        }
    ],
    "script_refs": [],
}
```

### 第 5 步：新增外部 SQL 模板

场景中的 SQL 模板不要写在场景文件正文里，应该独立成 `.sql` 文件，放在对应领域的 `sql/` 目录下。

例如：

```text
backend/app/skills/domains/paint_shop_defect_analysis/sql/daily_defect_summary.sql
```

这样做的好处：

- 模板职责清晰
- 后续便于复用和测试
- 为未来模板执行器预留稳定入口

### 第 6 步：在 `registry.py` 中显式注册

这是当前实现里最容易漏掉的一步。

系统现在不会自动扫描所有领域目录，所以新增领域后，必须显式接入：

1. 导入新的 `DOMAIN_META`
2. 导入新的场景 `SCENARIO`
3. 把场景加入 `_RAW_SCENARIOS`
4. 把领域加入 `DOMAIN_SKILLS`

可参考当前 `paint_shop_vehicle_tracking` 的做法。

推荐按下面的模式扩展，而不是继续堆单个领域：

```python
from xxx.meta import DOMAIN_META as DEFECT_DOMAIN_META
from xxx.scenarios.daily_defect_summary import SCENARIO as DAILY_DEFECT_SUMMARY

_RAW_SCENARIOS[DAILY_DEFECT_SUMMARY["skill_name"]].append(DAILY_DEFECT_SUMMARY)

DOMAIN_SKILLS[DEFECT_DOMAIN_META["name"]] = {
    "name": DEFECT_DOMAIN_META["name"],
    "description": DEFECT_DOMAIN_META["description"],
    "domain_content": read_asset_text("paint_shop_defect_analysis/domain.md"),
    "scenario_summaries": _build_scenario_summaries(
        SCENARIOS_BY_SKILL.get(DEFECT_DOMAIN_META["name"], [])
    ),
    "tags": DEFECT_DOMAIN_META["tags"],
}
```

注意：

- 当前注册中心是“显式注册”机制，不是“自动发现”
- 只有进入 `DOMAIN_SKILLS` 的领域，才会进入 `SKILLS`
- 只有进入 `SCENARIOS_BY_SKILL` 的场景，才会被 `load_scenario()` 识别

## 运行时调用链

新增领域接入后，运行时主链路如下：

1. `backend.app.skills` 被导入
2. `registry.py` 顶层代码执行，生成 `DOMAIN_SKILLS`、`SCENARIOS_BY_SKILL`、`SKILLS`
3. `SkillMiddleware` 读取 `SKILLS`，把领域摘要注入系统提示词
4. 模型根据用户问题先调用 `load_skill("<domain_name>")`
5. `load_skill()` 通过 `load_domain_content()` 加载领域全文
6. 若问题命中固定场景，再调用 `load_scenario("<domain_name>", "<scenario_name>")`
7. 场景 playbook 进入上下文后，再使用现有 SQL 工具链查询

## 验证清单

新增领域后，建议按下面顺序验证：

1. 静态检查
   - 新目录结构是否完整
   - `meta.py`、`domain.md`、场景文件、SQL 模板是否存在

2. 注册检查
   - `get_skill_by_name("<domain_name>")` 能返回对象
   - `list_scenarios_by_skill("<domain_name>")` 能返回场景列表

3. 渲染检查
   - `load_domain_content("<domain_name>")` 能输出领域正文
   - `load_scenario_content("<domain_name>", "<scenario_name>")` 能输出场景 playbook

4. 运行链路检查
   - `SkillMiddleware` 能在系统提示词里看到新领域摘要
   - `load_skill()` 能成功加载新领域
   - `load_scenario()` 能成功加载该领域下的场景
   - `sql_db_query(required_skill="<domain_name>")` 不被技能校验拦截

## 常见错误

### 1. 只建目录，不改 `registry.py`

表现：

- `SKILLS` 里没有新领域
- `load_skill()` 找不到新领域

原因：

- 当前不是自动发现机制，必须显式注册

### 2. `skill_name` 与领域名不一致

表现：

- 场景挂不到正确领域下
- `get_scenario_by_name()` 查不到

要求：

- 场景里的 `skill_name` 必须和 `DOMAIN_META["name"]` 完全一致

### 3. SQL 模板路径写错

表现：

- `render_scenario_for_llm()` 读取 SQL 模板时报错

要求：

- `sql_template_refs[*]["path"]` 必须是相对于 `skills/domains/` 的路径

### 4. 把场景细节写进 `domain.md`

表现：

- 领域文档越来越大
- 每次 `load_skill()` 都带入过多低频内容

建议：

- `domain.md` 只放公共知识
- 固定报表、固定统计逻辑放到场景层

## 推荐扩展策略

当前阶段推荐采用“多领域显式注册”策略，而不是立即做全自动扫描。

原因：

- 可控
- 易调试
- 不容易因半成品目录导致系统启动异常

当领域数量明显增多后，再考虑把 `registry.py` 从“单个领域手工注册”升级为“统一列表注册”或“半自动发现”。

## 新领域接入模板

后续新增领域时，可直接复用下面这份清单：

1. 在 `domains/` 下创建新领域目录
2. 新增 `meta.py`
3. 新增 `domain.md`
4. 新增 `scenarios/`、`sql/`、`scripts/`
5. 至少落一个样板场景
6. 在 `registry.py` 中导入并注册
7. 验证 `SKILLS`、`load_skill()`、`load_scenario()`
8. 更新 `changelog.md`
9. 必要时更新 `README.md`

## 一句话总结

在当前架构下，新增业务领域不是“只建一个目录”就完成了，而是“目录、元数据、场景、资产、注册中心、验证链路”六件事一起完成，系统才真正认识这个新领域。
