# 聊天流式输出结构化事件开发指南

修改时间: 2026-03-31 21:31 Asia/Shanghai

主要修改内容:
- 沉淀本次聊天流式输出协议升级的前后端设计经验
- 总结 LangGraph 流式模式、SSE 解析、工具状态一致性等关键实践
- 补充本次真实踩坑与排错方法，方便后续复用与学习
- 追加事件 schema 收敛约束，明确后端发送前校验与前端解析时拒绝未知事件

---

## 1. 背景与目标

本项目原有的聊天流式输出采用“纯文本 chunk + 最终块补充工具信息”的模式，能够工作，但存在几个典型问题：

1. 前端很难展示 Agent 的阶段状态（如检索中、查询中、整理答案中）。
2. 工具调用与工具结果缺乏统一事件协议，UI 很容易出现“执行中卡住”或状态丢失。
3. SSE 解析如果只按 `reader.read()` 的结果逐块 `split('\n')`，很容易在 JSON 跨 chunk 时解析失败。
4. LangGraph / LangChain 的 streaming 能力没有被充分利用，尤其是 `messages / updates / custom` 的组合。

因此，这次优化的目标是：

- 将流式协议升级为结构化事件流（structured event stream）
- 保持前后端事件语义一致
- 让“文本增量、阶段状态、工具调用、工具结果、最终结果、错误”都能独立显示
- 保证最终落库消息与流式临时消息的一致性

---

## 2. 推荐的整体设计

### 2.1 后端职责

后端负责三件事：

1. 调用 LangGraph / LangChain 的 streaming 接口
2. 将底层 streaming 输出统一整理成项目自己的结构化事件协议
3. 在 `final` / `error` 路径做最终落库

推荐输出的事件类型如下：

- `token`
  - 含义：正文文本增量
  - 典型字段：`text`, `node`
- `status`
  - 含义：阶段状态更新
  - 典型字段：`stage`, `text`, `source`
- `tool_call`
  - 含义：工具调用开始或参数流
  - 典型字段：`id`, `name`, `args_text`, `status`
- `tool_result`
  - 含义：工具结果返回
  - 典型字段：`id`, `content`
- `final`
  - 含义：本轮回答完成
  - 典型字段：`content`, `tool_calls`, `tool_results`, `message_id`, `created_at`
- `error`
  - 含义：本轮生成失败
  - 典型字段：`message`, `retryable`

### 2.2 前端职责

前端负责四件事：

1. 稳定解析 SSE
2. 将事件驱动到临时消息状态（streaming state）
3. 在 UI 中分别展示文本、状态、工具调用、工具结果、错误
4. 在 `final` 事件到达时将临时消息原地转为正式消息

推荐的前端状态模型至少包含：

- `content`
- `statusText`
- `stage`
- `toolCalls`
- `toolResults`
- `error`
- `isStreaming`

### 2.3 事件 schema 应保持“有限集合 + 显式校验”

这一步很重要，尤其是在项目已经进入多人协作后。

推荐约束：

1. 后端只允许输出有限事件集合：
   - `token`
   - `status`
   - `tool_call`
   - `tool_result`
   - `final`
   - `error`
2. 后端在发送 SSE 前先做一次 schema 校验，不要把宽松 dict 直接透传给前端
3. 前端解析 SSE 时，不要保留 `type: string` 之类的宽松兜底分支
4. 如果收到不符合协议的事件，应记录告警并忽略，或直接视为协议错误

这样做的价值是：

- 后端新增字段时，必须显式更新 schema，而不是“先发出来再说”
- 前端不会默默吞掉未知事件，避免 UI 和持久化状态悄悄漂移
- TypeScript 可以通过穷尽分支检查，第一时间暴露协议变更

## 3. 本次实践中的关键经验

### 3.1 不要把“传输结束”和“业务完成”混为一谈

SSE 的 `[DONE]` 只表示传输层结束，不等于业务层成功完成。

正确做法：

- 业务完成以 `final` 事件为准
- 业务失败以 `error` 事件为准
- `[DONE]` 仅作为连接关闭标记

如果前端只依赖 `[DONE]` 判断成功，很容易出现：

- 后端已经抛错，但前端仍误判为完成
- 最终消息未落库，前端却提前清空了临时状态

### 3.2 SSE 解析必须做 buffer 累积

错误做法：

- 每次 `reader.read()` 后立即 `decoder.decode(...)`
- 直接 `split('\n')`
- 对每一行做 `JSON.parse`

这个方案在下面场景会出问题：

- 单个 JSON 被拆到两个 chunk
- 一个 SSE event 包含多行 `data:`
- 尾部残留 buffer 尚未形成完整事件

正确做法：

1. 持续累积字符串 buffer
2. 按 `\n\n` 拆分完整 SSE event
3. 把一个 event 中的多行 `data:` 合并
4. 对完整 payload 再做 `JSON.parse`

### 3.3 “最终落定消息”不能丢掉流式态里已经收集到的信息

这是这次最容易踩坑的点。

典型现象：

- 大模型回答已经结束
- 工具结果也已收到
- 但界面上的工具状态仍显示“执行中”

根因通常是：

- 流式过程中前端临时状态里已经把工具标记为 `completed`
- 但 `final` 事件里的 `tool_calls` 没带完成态
- 前端 `completeStreamingMessage()` 用最终消息覆盖了临时状态
- 结果正式消息中又退回成 `streaming/started`

推荐方案：

1. 后端在序列化 `final.tool_calls` 时，统一把已结束工具标记为 `completed`
2. 前端展示层增加兜底逻辑：
   - 如果某个工具已经存在对应 `tool_result`
   - 即使 `tool_call.status` 缺失，也优先显示为“已完成”

### 3.4 工具调用状态要分“流式态”和“最终态”

建议将工具状态划分为：

- `started`
- `streaming`
- `completed`

推荐规则：

- 首次收到 `tool_call_chunk` 时记为 `started`
- 后续参数片段继续拼接时记为 `streaming`
- 收到对应 `tool_result` 后记为 `completed`
- 生成 `final` 事件时再统一做一次完成态收敛，防止状态遗漏

### 3.5 自定义业务状态建议通过 `custom` stream 输出

文本 token 只能体现“正在输出内容”，并不能体现“系统正在做什么”。

更好的做法是利用 `custom` stream 主动输出业务状态，例如：

- `正在加载业务技能`
- `正在检索业务知识`
- `正在检索历史 SQL 示例`
- `正在检查 SQL 语法`
- `正在执行 SQL 查询`
- `已收到查询结果，正在整理数据`

这样可以显著提升用户体验，尤其是在工具调用耗时较长时。

## 4. LangGraph / LangChain 流式开发注意事项

### 4.1 `astream` 与 `stream` 不能只改一边

本次真实踩坑：

- 本地模式使用的是同步 `PostgresSaver`
- 流式代码切到了异步 `agent.astream(...)`
- LangGraph 在异步路径会调用 `checkpointer.aget_tuple(...)`
- 同步 saver 没实现异步能力时，就会抛 `NotImplementedError`

结论：

- 如果本地持久化层还是同步 `PostgresSaver`
- 流式执行应先使用同步 `stream(...)`
- 如果要切到 `astream(...)`
- 就必须同步升级到 `AsyncPostgresSaver`

补充结论（2026-03-27 20:40）：

- 本项目本地 FastAPI 已切回 `AsyncPostgresSaver + astream()/ainvoke()`
- 因此“短期止血回退到同步 `stream()`”只适合作为临时排障手段
- 长期稳定方案仍然是让持久化、graph 执行方式、生命周期管理三者都保持 async 一致

### 4.2 同步 `stream()` 与异步 `astream()` 的返回结构可能不同

这次另一个真实踩坑是：

- 我们一开始按 `astream(version="v2")` 的 `{"type": ..., "data": ...}` 结构处理
- 后来为了兼容同步 saver 改回 `stream(...)`
- 但当前本地 LangGraph 版本在多 `stream_mode` 下返回的是 `(mode, data)` tuple
- 于是直接出现 `'tuple' object has no attribute 'get'`

经验结论：

- 不要假设 sync/async 两条 streaming 路径返回结构完全一致
- 需要写一层统一的 `chunk unpack` 兼容逻辑
- 推荐同时兼容：
  - `{"type": ..., "data": ...}`
  - `(mode, data)`
  - `(namespace, mode, data)`（subgraph 场景）

### 4.3 `messages / updates / custom` 的职责边界要清晰

建议分工如下：

- `messages`
  - 负责 token 级文本与 tool call chunk
- `updates`
  - 负责 graph node 级别的阶段进度
- `custom`
  - 负责业务语义更清晰的状态提示

不要把所有东西都塞进 `messages`，否则前端很难做有层次的展示。

## 5. 本次排错经验总结

### 5.1 错误一：`NotImplementedError`（checkpointer）

现象：

```text
saved = await self.checkpointer.aget_tuple(...)
raise NotImplementedError
```

根因：

- 异步 `astream(...)`
- 搭配同步 `PostgresSaver`

修复：

- 短期止血：回退到同步 `stream(...)`
- 长期方案：升级为 `AsyncPostgresSaver`

### 5.2 错误二：`'tuple' object has no attribute 'get'`

现象：

```text
chunk_type = chunk.get("type")
AttributeError: 'tuple' object has no attribute 'get'
```

根因：

- 同步 `stream(...)` 在当前 LangGraph 版本中返回 tuple
- 但代码仍按 dict 结构解析

修复：

- 增加统一 `unpack_stream_chunk()` 兼容层

### 5.3 问题三：工具状态一直显示执行中

现象：

- 回答已结束
- 工具结果已显示
- 但工具标签仍是“执行中”

根因：

- `final` 事件中的 `tool_calls` 没有补 `completed`
- 正式消息覆盖了前端临时状态

修复：

- 后端最终序列化强制收敛为 `completed`
- 前端若发现已存在 `tool_result`，则状态显示兜底为“已完成”

### 5.4 问题四：Milvus 延迟初始化在线程池中缺少 event loop

现象：

```text
There is no current event loop in thread 'ThreadPoolExecutor-...'
```

结论：

- 这通常是 RAG 检索链路在同步调用 / 线程池环境下触发了依赖 event loop 的初始化路径
- 在当前实现里它被降级为空检索结果，不一定会直接打断主回答
- 但会导致业务知识增强失效

建议：

- 将这类问题单独治理，不要和主流式协议问题混在一起排查

### 5.5 问题五：FastAPI 模块导入时 eager 初始化不利于 async 资源管理

现象：

- `services.py` 在模块导入时直接创建全局 `agent_service`
- 一旦切到 `AsyncPostgresSaver`
- 就很难在合适的 startup/shutdown 生命周期内显式打开和关闭连接池

根因：

- async checkpointer 依赖运行中的 event loop
- 模块导入阶段不适合直接做本地 async 初始化

修复：

- 改为 `initialize_agent_service()` / `get_agent_service()` / `shutdown_agent_service()`
- 在 `FastAPI lifespan` 中显式管理单例与连接池生命周期

## 6. 推荐的开发流程

如果后续还要新增或重构流式输出，推荐按这个顺序做：

1. 先定义自己的结构化事件协议，不要直接把 LangGraph 原始对象暴露给前端
2. 再实现后端 streaming 适配层，把 `messages / updates / custom` 映射到项目事件
3. 然后实现前端 SSE parser，先保证稳定收事件
4. 再做 store 层，把临时消息建模完整
5. 最后才做 UI 展示和动画优化

如果顺序反过来，后面很容易出现：

- 协议一变，前端全链路都要推倒重来
- UI 先写好了，但状态字段不够
- 数据库落定消息和流式临时消息不一致

---

## 7. 推荐的最小复用清单

下次在其他 Agent / Chat 项目里复用时，优先检查以下几项：

### 后端

- 是否已定义统一 `StreamEvent`
- 是否区分 `final` 和 `[DONE]`
- 是否考虑 sync / async checkpointer 匹配关系
- 是否兼容不同 streaming 返回结构
- 是否在 `final` 时统一收敛工具状态

### 前端

- SSE parser 是否支持 buffer 累积
- 是否有独立的 streaming 临时状态
- 是否能展示 `status/tool_call/tool_result/error`
- `final` 到达时是否原地落定，而不是闪烁重拉
- 工具状态是否有结果驱动的兜底逻辑

---

## 8. 一句话总结

聊天流式输出做得稳定、可维护、可扩展，关键不在“能不能边生成边显示”，而在于：

**是否建立了前后端共享的结构化事件协议，以及是否把流式态、最终态、错误态和工具态统一成一条完整的数据链路。**
