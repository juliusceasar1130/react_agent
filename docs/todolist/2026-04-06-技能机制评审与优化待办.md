# 技能机制评审与优化待办

记录时间：2026-04-06 Asia/Shanghai

背景说明：
本次记录用于归档“领域技能 / 场景技能加载机制”的评审结论，聚焦技能上下文驻留、场景资产加载一致性，以及后续可持续演进方向。

用途说明：
本文档作为后续优化的待办与设计参考，供后续阶段性实施时复用；当前仅做问题与方案沉淀，不立即改动相关运行时机制。

## 背景

当前技能机制分为两层：

- 领域技能摘要由 `SkillMiddleware` 注入 `SystemMessage`
- 领域技能全文与场景技能全文通过 `load_skill()` / `load_scenario()` 返回的 `ToolMessage` 进入上下文

当前场景资产加载方式为：

- 场景文本会展示 `sql_template_refs` 与 `script_refs` 的引用信息
- 若存在 SQL 模板，会把第一份 SQL 模板正文直接拼接进场景文本
- scripts 当前只展示引用，不加载脚本正文

这套机制已经具备“领域摘要暴露 + 详细内容按需加载”的基本分层，但在长对话、摘要压缩和复杂场景扩展时，存在明显的可维护性与一致性问题。

## 当前评审发现的问题

### 问题 1：摘要后已加载状态与真实上下文失配

当前现象：

- `skills_loaded` / `scenarios_loaded` 记录在运行时 state 中
- 领域/场景详细内容依赖历史 `ToolMessage` 留在上下文
- 一旦 `SummarizationMiddleware` 对历史消息做摘要压缩，原始技能全文可能已不在上下文中

风险 / 影响：

- 工具权限校验仍然认为技能已加载
- 模型却未必还能看到对应技能的详细规则、workflow、参数和 SQL 模板
- 会出现“状态显示已加载，但模型真实可见上下文已丢失”的失配

建议方案：

- 不再把历史 `ToolMessage` 作为技能详细内容的唯一载体
- 将已加载技能的结构化内容保存在 state 中
- 每轮模型调用前按 active skill / scenario 重新注入关键上下文

优先级：

- `P0`

### 问题 2：场景资产加载策略不一致，SQL 与 scripts 处理方式不同

当前现象：

- 第一份 SQL 模板正文会直接注入场景文本
- scripts 只展示引用信息，不加载正文
- 其他类型资产也缺乏统一处理方式

风险 / 影响：

- 场景能力表达不一致
- 后续如果场景依赖多个 SQL、脚本或说明文档，维护者很难预测哪些资产会进入上下文
- 新增复杂场景时容易继续堆特殊分支

建议方案：

- 抽象统一资产结构
- 默认使用结构化摘要展示所有资产
- 对主 SQL 允许展开正文
- 其他资产通过按需展开机制加载

优先级：

- `P1`

### 问题 3：场景与历史 SQL 示例的优先级仍偏提示词约束，缺少机制级约束

当前现象：

- system prompt 中已提示：加载场景后不推荐继续使用 `search_saved_correct_tool_uses`
- 但当前仍主要依赖自然语言约束，而非更明确的运行时策略

风险 / 影响：

- 场景 playbook 与历史 SQL 示例可能竞争同一决策位置
- 对“固定统计 / 固定报表”类场景，模型仍可能被历史示例干扰
- 场景的稳定性与模板化收益无法完全发挥

建议方案：

- 后续为场景引入更明确的策略字段或调度规则
- 收敛到“场景模板优先，历史 SQL 检索回退”的机制

优先级：

- `P2`

### 问题 4：只展开第一份 SQL，不适合后续复杂场景

当前现象：

- 渲染器当前仅展开第一份 SQL 模板正文
- 其余 SQL、脚本和补充说明无法等价进入上下文

风险 / 影响：

- 一个场景难以自然承载主查询、辅助查询、维表探测 SQL、校验 SQL 等多资产组合
- 容易逼迫维护者把更多逻辑继续塞回单份 SQL 或注释中

建议方案：

- 统一资产建模
- 保留“主资产默认展开，其他资产结构化摘要 + 按需展开”的策略

优先级：

- `P1`

## 优化目标

- 技能上下文不能继续依赖历史 `ToolMessage` 长期保留
- 场景资产需要统一建模，避免 SQL 与 scripts 处理逻辑分裂
- 默认上下文应保持轻量，但要支持按需展开更详细资产
- 新增场景时应尽量减少特殊规则和后续补丁式修改

## 推荐方案

### 方案 A：技能内容采用“状态重注入”

核心思路：

- `load_skill()` / `load_scenario()` 除了返回 `ToolMessage`，还将结构化技能内容写入 state
- 中间件在每轮模型调用前，从 state 读取当前 active skill / active scenario 的关键内容
- 将这些关键内容重新注入模型上下文

建议落地方向：

- 在 state 中新增类似 `loaded_skill_payloads` / `loaded_scenario_payloads` 的结构化字段
- `skills_loaded` / `scenarios_loaded` 继续承担“已加载记录 / 工具权限校验”职责
- 历史 `ToolMessage` 保留为执行痕迹和调试信息，但不再作为唯一知识来源

预期收益：

- 摘要后仍可稳定恢复当前技能上下文
- 消除“权限状态真实、知识上下文丢失”的结构性失配

### 方案 B：场景资产采用“结构化摘要 + 按需展开”

核心思路：

- 不再只对第一份 SQL 做特殊文本注入
- 所有资产先统一整理成结构化清单
- 默认只展示摘要与用途说明
- 主 SQL 可按规则默认展开
- 其他 SQL / scripts / docs 按需展开

建议落地方向：

- 抽象统一资产模型，包含类型、名称、路径、角色、加载策略等字段
- 渲染器先构建 bundle，再渲染文本
- 统一呈现 SQL、scripts、说明文件的摘要

预期收益：

- 场景资产表达方式一致
- 更利于后续引入多 SQL、多脚本、多说明文件的复杂场景
- 上下文体积更可控

### 机制边界调整建议

- 明确保留 `ToolMessage`，但其角色调整为“执行痕迹 / 可观测输出”，不再承担唯一上下文驻留职责
- 后续可新增 `load_scenario_asset(...)` 之类工具，用于按需展开某个具体资产

## 分期待办

### `P0`

- 扩展 `CustomState`，新增 `loaded_skill_payloads` / `loaded_scenario_payloads`
- 调整 `load_skill()` / `load_scenario()`，在返回 `ToolMessage` 的同时写入结构化 payload
- 调整技能中间件，在每轮请求前按 state 重注入 active skill / active scenario 的关键内容
- 验证摘要压缩后，模型仍能看到当前活跃技能的关键上下文

### `P1`

- 抽象统一资产结构，统一 SQL / scripts / docs 的元数据表达
- 将渲染器改为“先组装 bundle，再渲染文本”
- scripts 进入统一资产摘要，而不是只显示裸引用
- 调整“主 SQL 默认展开，其余资产摘要展示”的渲染策略

### `P2`

- 增加 `load_scenario_asset(...)` 之类按需展开资产的工具
- 收敛“场景模板优先，历史 SQL 检索回退”的策略
- 评估 `search_saved_correct_tool_uses` 与场景技能之间的关系和优先级
- 评估是否需要为场景增加更明确的执行策略声明字段

## 验收与后续检查点

- 摘要后模型仍能看到 active skill / scenario 的关键内容
- 多轮对话中切换场景不会造成上下文污染
- scripts 与 SQL 的资产呈现机制保持一致
- 新增复杂场景时不再受“只展开第一份 SQL”这一结构限制
- 评审文档可直接作为后续分阶段实施清单继续推进
