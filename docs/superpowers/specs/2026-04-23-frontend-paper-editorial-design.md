# Frontend Paper Editorial Design

**日期：** 2026-04-23  
**范围：** `frontend` 聊天界面的视觉系统与布局表达优化，不调整后端接口、前端业务逻辑或主要信息结构。

## 目标

在保留当前聊天工作台骨架的前提下，将前端从“明亮 SaaS 卡片式工作台”调整为“淡暖棕 Paper Editorial 杂志风”。

最终界面应满足以下感受目标：

- 更安静、更耐看，减少当前蓝青科技感
- 更像专栏阅读界面，而不是后台管理台
- 保持聊天产品的操作效率，不牺牲现有功能路径
- 允许用户先在独立 worktree 中观察效果，再决定是否留用

## 已确认决策

- 视觉方向采用 `Paper Editorial`
- 色彩方向采用 `淡淡暖棕`
- 改造方式采用 `保守型`
- 保留当前主结构：左侧会话栏、右侧聊天区、底部输入区
- 不新增依赖，不做功能扩展，不改业务行为
- 真正开始代码实施前，先从 `feature/agent` 新建独立 worktree

## 背景判断

当前 `frontend` 已有一版“明亮卡片式聊天工作台”实现，核心结构和交互路径已经稳定：

- 桌面端双栏布局已经可用
- 移动端抽屉式会话栏已经存在
- 聊天消息、流式状态、上下文预警、导出卡片、图表卡片等功能已经接入

因此本次工作不适合推翻重做，而应聚焦于：

- 重建设计 token
- 调整排版节奏与视觉层级
- 将侧栏、消息区、输入区统一到同一套暖棕杂志语言

## 备选方向与取舍

### 方案 A：Paper Editorial（推荐）

特征：

- 暖米白背景
- 低饱和暖棕强调色
- 深墨褐正文
- 细线边框、纸面留白、弱化发光和玻璃感

优点：

- 与现有布局兼容性最高
- 最容易在最小改动下建立明显的新气质
- 能同时兼顾“高级感”和“工具可用性”

### 方案 B：Gallery Review

特征：

- 更明显的装裱感和材质感
- 更强的画刊氛围和展示感

不选原因：

- 容易偏向展示页
- 对聊天工作台的长期使用友好度不如方案 A

### 方案 C：Archive Journal

特征：

- 更理性、更克制、更接近档案期刊

不选原因：

- 稳定但记忆点较弱
- 对“优雅”气质的表达不如方案 A 明确

## 设计原则

- 最小改动：只动完成本次美化所必需的样式、布局表达和少量本地 UI 结构
- 保持功能：不改发送、流式、中断、会话切换、下载、图表展示等行为
- 统一语言：所有组件共享同一套暖棕 token，不混入旧蓝青体系
- 阅读优先：消息区首先是阅读界面，其次才是状态展示界面
- 目录感侧栏：左栏更像“期刊目录/栏目”，而不是工具菜单

## 视觉系统

### 色彩

目标色板采用暖中性色，不使用冷蓝为主视觉：

- 页面背景：暖米白、浅纸色
- 分层背景：浅沙色、淡燕麦色
- 主强调：胡桃棕 / 焦糖棕
- 次强调：柔和赭棕
- 正文：深墨褐
- 辅助文字：暖灰棕
- 风险提示：保留功能语义色，但降低荧光感和冲突感

要求：

- 全局 token 不再以蓝色为中心
- 原有 `primary / accent / neutral` 需要整体重定义
- 所有阴影应转为中性暖灰，不带蓝色 glow

### 排版

排版目标是“专栏阅读感”，不是“后台控件堆叠感”：

- 页头标题更像刊物栏目标题
- 次级说明文字更像导语或注释
- 消息正文更注重段落、行高、留白和版心
- 会话标题强调清晰的层级和目录扫描效率

预期策略：

- 标题使用更有编辑感的字体栈和字重层次
- 正文字号、行高、段间距统一到阅读优先配置
- Markdown 内容减少“技术面板味”，增强正文阅读体验

### 形状与边界

- 保留圆角，但比现状更克制
- 减少夸张的大圆角和强烈胶囊感
- 改用更细、更轻的边框来建立纸张层级
- 消息卡片和输入容器应更像“稿纸块”或“版面单元”

### 阴影与材质

- 去掉现有偏科技感的 glow
- 使用轻柔、贴纸面的阴影
- 在背景和卡片层之间建立柔和层级，而不是悬浮感过强的浮层

### 动效

- 保留必要动画
- 动效应更安静、更短、更轻
- 减少“按钮弹跳”和明显的 hover 漂浮感

## 布局策略

### 桌面端

- 保留双栏结构
- 左侧会话栏从“功能侧栏”转为“目录栏”
- 右侧聊天区强化版心与顶部标题区
- 消息容器最大阅读宽度继续收束，突出正文区
- 输入区维持底部固定位置，但外观改成更像编辑器页脚组件

### 移动端

- 保留当前会话抽屉模式
- 不新增复杂交互
- 保留现有触控路径，只做视觉语言同步
- 确保底部输入区、顶部栏和消息区留白一致

## 组件级设计

### `frontend/src/style.css`

职责：

- 重新定义全局颜色、阴影、圆角、背景、组件 token
- 重写 `btn-primary`、`panel`、`input`、`message-markdown` 等基础样式

重点：

- 从蓝青科技感迁移到暖棕纸面感
- Markdown 中的标题、引用、表格、代码块都要统一新风格

### `frontend/tailwind.config.js`

职责：

- 将扩展色板、阴影和语义色与新设计系统对齐

重点：

- 让组件类名继续可用
- 通过最小 token 迁移完成大部分视觉切换

### `frontend/src/views/ChatView.vue`

职责：

- 保留当前布局结构
- 微调页头、预警条、输入区和整体背景组织

重点：

- 顶部标题区增加“栏目感”
- 输入区更像版面底部编辑条
- 整个主区从工作台感转为阅读工作区感

### `frontend/src/components/SessionList.vue`

职责：

- 调整列表区域的密度和边界感

重点：

- 让左栏更接近目录页而不是菜单页

### `frontend/src/components/SessionItem.vue`

职责：

- 调整选中态、时间信息、删除按钮的视觉关系

重点：

- 选中态应更像栏目高亮，而不是科技感状态卡片

### `frontend/src/components/MessageList.vue`

职责：

- 保持滚动逻辑不变
- 调整消息列表版心、空状态和容器留白

### `frontend/src/components/MessageItem.vue`

职责：

- 统一用户消息、AI 消息、错误态、中断态、流式态的纸面层级

重点：

- AI 消息更像正文卡片
- 用户消息需要保留区分，但不能显得像聊天软件气泡
- 工具结果、CSV 下载卡片、图表卡片要融入新视觉，而不是成为独立风格岛

### `frontend/src/components/EmptyState.vue`

职责：

- 欢迎态改成更像刊物首页导语

### `frontend/src/components/ToggleSwitch.vue`

职责：

- 与新设计系统统一
- 维持状态表达清晰，不做复杂结构改动

## 数据与交互边界

本次设计不改变以下内容：

- API 请求方式
- Pinia store 结构
- 流式输出与非流式切换逻辑
- 中断逻辑
- 会话创建、删除、选择逻辑
- 图表与导出卡片的数据来源

换句话说，本次变更只改变“这些行为如何被呈现”，不改变“这些行为如何工作”。

## 风险与处理

### 风险 1：只换色，不像杂志风

原因：

- 如果仅替换主题色，而不调整版心、标题层级、边界和留白，最终只会得到“棕色 SaaS”

处理：

- 必须把排版和层级一起纳入实施范围

### 风险 2：为了杂志感而损伤工具效率

原因：

- 过度装饰会压缩消息效率和输入效率

处理：

- 保留现有布局骨架
- 仅在视觉表达上做升级

### 风险 3：局部组件风格脱节

原因：

- 导出卡片、图表卡片、错误态等容易保留旧风格

处理：

- 在组件级清单中把这些状态纳入统一视觉验收范围

### 风险 4：实施时直接污染主工作区

原因：

- 用户明确希望先观察效果，再决定是否留用

处理：

- 进入实现前，先基于 `feature/agent` 创建新 worktree
- 仅在新 worktree 中开展前端改造与验证

## 验证方式

### 设计验证

- 主题是否稳定体现“淡暖棕 Paper Editorial”
- 左栏是否更像目录栏
- 消息区是否具备专栏阅读感
- 输入区是否更统一、更安静、更高级

### 技术验证

- 在新 worktree 中运行 `frontend` 构建检查
- 检查桌面端与移动端布局是否保持可用
- 检查会话抽屉、消息渲染、流式状态、错误态、图表卡片、导出卡片是否正常

## 非目标

- 不做功能重构
- 不引入新依赖
- 不改接口协议
- 不增加主题切换器
- 不做暗色主题
- 不做与本次视觉改造无关的代码整理

## 实施前提

开始编码前需先完成以下动作：

1. 从 `feature/agent` 创建独立 worktree
2. 在新 worktree 中确认当前 `frontend` 基线可验证
3. 再开始按组件分步落地
