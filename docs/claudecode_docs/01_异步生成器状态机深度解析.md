## 第一阶段：概念奠基——从 Generator 到 Async Generator

在开始阅读 Claude Code 的核心源码之前，我们需要建立正确的心智模型。

### 1. 什么是 Generator（生成器）？
传统函数是“一路到底”并返回单个结果的。而 Generator 函数（使用 `function*` 声明）允许函数在执行过程中**暂停**并交出中间结果（`yield`），之后还可以在暂停处被**恢复**执行。

```javascript
function* numberGenerator() {
  console.log("开始生产");
  yield 1; // 第一次暂停，产出 1
  
  console.log("继续生产");
  yield 2; // 第二次暂停，产出 2
  
  return 3; // 结束
}

const iterator = numberGenerator();
console.log(iterator.next()); // 输出: 开始生产, { value: 1, done: false }
console.log(iterator.next()); // 输出: 继续生产, { value: 2, done: false }
console.log(iterator.next()); // 输出: { value: 3, done: true }
```

### 2. 什么是 Async Generator（异步生成器）？
如果将**生成器**与**异步 Promise** 相结合，就得到了 `async function*`。它允许你在 `yield` 之间加入 `await` 异步操作，这在网络数据流（Stream）传输中非常有用。

```javascript
async function* asyncStream() {
  yield "正在获取数据块 1...";
  const chunk1 = await fetchFromNetwork(1);
  yield chunk1;

  yield "正在获取数据块 2...";
  const chunk2 = await fetchFromNetwork(2);
  yield chunk2;
}

// 消费异步生成器：使用 for await...of 语法
for await (const chunk of asyncStream()) {
  console.log("收到：", chunk); // 每次数据块下载完成时，异步唤醒并输出
}
```

## 第二阶段：架构演进与多级消息压缩机制

大多数 Agent 框架（如 LangChain）采用传统的 **ReAct (Think → Act → Observe)** 循环，这往往会导致递归调用过深或状态难以恢复。

```text
传统 ReAct 循环：
LLM Response (包含工具调用) ──► 框架解析 ──► 阻塞式运行工具 ──► 将结果作为输入重新调用 LLM
```

Claude Code 采用了平铺的 **`while (true)` 循环 + `state = next`** 的异步生成器状态机（核心实现在 [src/query.ts](file:///f:/000_dev/github/cc-haha/src/query.ts) 的 `query()` 中）。

```text
Claude Code 状态机：
[State: 当前上下文 & 历史]
         │
         ▼
 ┌───────────────┐
 │ 1. 消息压缩   │ ◄─── (多级消息压缩机制，保障长对话稳定与缓存命中)
 └───────┬───────┘
         ▼
 ┌───────────────┐      (流式 yield stream_event 给前端)
 │ 2. API 流式调用│ ───►  
 └───────┬───────┘
         ▼
 ┌───────────────┐
 │ 3. 决策点     ├──────► (无可调用工具 ──► 退出状态机)
 └───────┬───────┘
         ▼
 ┌───────────────┐
 │ 4. 工具流式执行│
 └───────┬───────┘
         ▼
 ┌───────────────┐
 │ 5. 状态机跳转 │ ───► [更新 State = Next] ───► continue (回到循环顶部)
 └───────────────┘
```

### 1. 状态机的第一步：为什么先做消息压缩？
大模型单次请求的费用和延迟很大程度上取决于 **Prompt Token 数量**。而在 Agent 多轮调用工具的过程中，历史消息（尤其是大型工具的输出）会迅速累积。

为了防止爆 Token 且不破坏 **Prompt Cache（提示词缓存）**，状态机的第一步会运行四级渐进式压缩：
1. **第一级：Snip Compression / Tool Result Budget（裁剪与超限磁盘持久化）**：移除/持久化过长或无用的老工具输出。
2. **第二级：Micro-compaction（微压缩）**：对已完成的小消息在原地进行无 cache-breaking 的精简。
3. **第三级：Context Collapse（上下文折叠）**：把较老的消息段落逐步折叠/折叠为总结。
4. **第四级：Auto-compact（自动大纲合并）**：生成整场对话的全局高精大纲，彻底清除老消息。

---

### 2. 第一级压缩深度探秘：Snip & Tool Result Budget 机制
在开源及生产版本中，为了防止极其庞大的工具返回内容（如读取上万行代码或跑海量测试日志）撑爆 Token，Claude Code 引入了 **Tool Result Budget (工具结果预算/持久化)** 机制（核心代码见 [src/utils/toolResultStorage.ts](file:///f:/000_dev/github/cc-haha/src/utils/toolResultStorage.ts) 中的 `applyToolResultBudget` / `enforceToolResultBudget`）。

#### 核心机制：
*   **持久化与预览替换**：当单条工具返回的内容长度超过设定的阈值（例如 `getPerMessageBudgetLimit()`）时，状态机**不会**直接把这部分数据拼入 Prompt 发给大模型。相反，它会**把超限的文本持久化存储在磁盘上**，然后用一个极短的“预览/占位符”（Persisted Preview）替代发送。
*   **前缀缓存稳定（Prompt Cache Friendly）**：如果每次循环随便更换替换策略，缓存就会被破坏。因此它维护了一个会话级别的状态 `ContentReplacementState`：
    *   `seenIds`：记录已经做出决策的 `tool_use_id`。一旦决定不替换或已替换，在整场对话中绝不更改，保证前缀稳定性。
    *   `replacements`：保存 `tool_use_id` 对应的具体预览文本，在下一次状态机循环重试时，直接从内存 Map 里快速读取已替换好的值。

#### Snip & Tool Result Budget 执行流程图：

```text
               输入待处理消息 messages 
                        │
                        ▼
           收集 eligible 的工具返回 candidates
                        │
                        ▼
       [遍历工具返回] 是否已经被处理过 (在 seenIds 中)？
                 ├───► 是: [从 replacements Map 直接读取预览] (确保 Byte 一致，保护 Cache)
                 └───► 否 (新消息):
                        │
                        ▼
             是否为排除的工具 (如 Read)?
                 ├───► 是: 标记为 seenIds，直接发送原文
                 └───► 否:
                        │
                        ▼
               该消息的所有工具结果总大小 
               是否超过限制 (limit)？
                 ├───► 否: 标记为 seenIds，发送原文
                 └───► 是 (Over-Budget):
                        │
                        ▼
             [选择该消息中最大的工具结果进行持久化]
                        │
                        ▼
            1. 将原文写入本地磁盘 (.claude/...)
            2. 生成预览信息: "Output persisted to disk..."
            3. 将 id 与预览信息存入 replacements Map
            4. 将 id 标记为 seenIds
                        │
                        ▼
           用预览块替换 messages 中的对应块，
           并把替换决策写入 Session 恢复记录
                        │
                        ▼
               输出压缩后的 messagesForQuery
```

#### 机制示例：
如果大模型调用 `run_command` 跑了一次 `npm test` 并产生了 **150KB** 的日志输出（超过了单条消息的 Budget 限制）。

*   **写入前**：用户消息里包含了 `tool_result`，包含 150KB 日志文本。
*   **状态机压缩动作**：
    1. 检测到超限，异步将 150KB 写入磁盘。
    2. 生成预览文本：
       ```text
       <persisted_output tool="run_command" id="tool_use_123">
       [Persisted Output - 153,600 bytes. Preview of first 2,000 bytes:]
       > jest
       PASS  src/query.test.ts
       ...
       [Remaining 151,600 bytes persisted to disk. Use other tools to view if needed.]
       </persisted_output>
       ```
    3. 在 `ContentReplacementState` 中记录：`seenIds.add('tool_use_123')` 和 `replacements.set('tool_use_123', previewText)`。
*   **写入后**：原 150KB 被替换为 2KB 的预览，节省了 98% 的 Token 损耗。在后续的多轮对话重试中，由于 `seenIds` 已经记录，状态机将永远固定发送这段预览，绝不重新拼入 150KB 原文，完美维持了缓存的稳定性。

### 3. 状态对象 `State` 的核心结构
为了保持状态的“事务性”，在每次循环顶部解构 Bare-name 变量，并在底部组装成一个新的 `next` 对象覆盖原有 `state`。

```typescript
type State = {
  messages: Message[]             // 完整的对话历史（消息上下文）
  toolUseContext: ToolUseContext   // 工具执行上下文
  turnCount: number                // 对话轮次
  transition: Continue | undefined // 记录上一次为什么进入此轮（用于测试与追踪）
  // ... 其他自愈恢复相关的计数器
}
```

#### 为什么用 `state = next` 而非直接修改属性？
1. **事务性保障**：若中间步骤出错，`state` 保持为进入循环时的干净状态，防止脏属性残留。
2. **零递归**：所有故障修复或工具调用轮次，都是通过修改 `state` 后执行 `continue` 原地重启循环，调用栈永远只有 **1 层**，绝对不会栈溢出。

## 第三阶段：网络通信——SSE 流式传输与 SDK 解析

大模型生成的本质是一颗颗 Token 的流式输出。Claude Code 与 Anthropic 官方 API 采用 **SSE (Server-Sent Events)** 进行单向长连接传输。

### 1. 网络层协议（以字符流传递）
网络上传输的 SSE 数据包格式如下（以 `\n\n` 分隔每一帧）：
```text
event: content_block_delta
data: {"type": "content_block_delta", "index": 0, "delta": {"type": "input_json_delta", "partial_json": "{\"file_path\":"}}

event: content_block_delta
data: {"type": "content_block_delta", "index": 0, "delta": {"type": "input_json_delta", "partial_json": " \"main.ts\"}"}}
```

### 2. SDK 缓冲与解析（管道工角色）
底层适配层 [src/services/api/claude.ts](file:///f:/000_dev/github/cc-haha/src/services/api/claude.ts) 中的 `queryModel()` 负责拦截这些数据流：
1. 操作系统接收网卡 TCP 字节。
2. SDK 将其切分为独立的事件帧，解析出 JS 对象（`part`）。
3. 适配层通过 `for await (const part of stream)` 依次读取。

## 第四阶段：流式执行——工具实时调用的双轨发射机制

当大模型要求调用工具时，底层的 `queryModel` 进行了**双轨 `yield` 设计**：高频流式输出 UI 状态，低频完整生成后触发执行。

### 1. 工具参数拼装生命周期
大模型调用工具的事件流程如下：
*   **`content_block_start`**：底层收到信号，初始化一个空的参数容器：
    ```typescript
    contentBlocks[part.index] = { ...part.content_block, input: "" };
    ```
*   **`content_block_delta`**（高频触发）：源源不断地收到 `input_json_delta` 字符，在内存里拼接：
    ```typescript
    contentBlock.input += delta.partial_json; // "{\"file_path\": \"main.ts\"}"
    ```
*   **`content_block_stop`**（核心节点）：大模型输出参数完毕。此时底层开始反序列化 JSON，并触发第一次 `yield`：
    ```typescript
    const m = { type: "assistant", message: { content: JSON.parse(contentBlock.input) } };
    yield m; // ◄── 1. 触发工具执行的逻辑
    ```
*   **循环末尾**：紧接着把当前的 raw 事件抛出：
    ```typescript
    yield { type: "stream_event", event: part }; // ◄── 2. 刷新前端打字机/进度条 UI
    ```

### 2. 双轨发射时间线示例
外层状态机（`query.ts`）在流式周期内会被频繁唤醒，并根据 `message.type` 做出反应：

| 唤醒顺序 | 收到的数据类型 | 外层状态机行为 | 终端用户看到的画面 |
| :--- | :--- | :--- | :--- |
| **第 1~N 次** | `type: 'stream_event'` | `message.type === 'assistant'` ❌ 判定为假，跳过。 | 屏幕上字符闪烁、打字机动画实时展示工具参数。 |
| **第 N+1 次** | `type: 'assistant'` | `message.type === 'assistant'`  判定为真，立刻将工具块传递给 `StreamingToolExecutor`。 | **不等模型整句话流完，后台工具立刻异步跑起来！** |

### 3. [StreamingToolExecutor](file:///f:/000_dev/github/cc-haha/src/services/tools/StreamingToolExecutor.ts) 并发与排队调度
工具拿到后不会无脑运行，它根据并发属性进行调度：
*   **并发安全（Concurrency Safe）工具**（如 `view_file`, `grep_search` 等只读操作）：立刻并行执行。
*   **非并发安全工具**（如 `Bash` 或写入操作）：必须排队等前一个非并发安全工具执行完毕，防止引发竞态冲突。

## 第五阶段：稳健自愈——状态机故障恢复策略

这是状态机最强大的一部分：整个 Agent 系统遇到各类 API 报错或物理上限时，能进行无缝的自我修复（Self-Repair）。

以大模型常见的 **Prompt 超长（`prompt_too_long`）** 为例，状态机的修复流程：

```typescript
// query.ts 捕获到了被 withhold（扣留）的超长错误
const isWithheld413 = lastMessage.isApiErrorMessage && isPromptTooLongMessage(lastMessage);

if (isWithheld413) {
  // 1. 调用上下文折叠，对历史消息进行强力缩减/折叠
  const drained = contextCollapse.recoverFromOverflow(messagesForQuery, querySource);
  
  if (drained.committed > 0) {
    // 2. 构造干净的 next 状态，替换 state 
    const next: State = {
      messages: drained.messages, // 已经被大量折叠/缩减后的消息列表
      turnCount,
      transition: { reason: 'collapse_drain_retry' } // 记录转移原因
    };
    state = next;
    
    // 3. 原地 continue，状态机直接重新发起 API 请求
    continue; 
  }
}
```

此外，Claude Code 还包含了其他恢复策略：
*   **`reactive_compact_retry`**：折叠仍不足以缩容时，启动小模型压缩后原地 `continue`。
*   **`max_output_tokens_escalate`**：遭遇默认 8k 生成瓶颈时，修改 `maxOutputTokensOverride` 为 64k 并原地 `continue`。
*   **`max_output_tokens_recovery`**：被强行截断时，在末尾追加 Nudge Meta 提示词（“*请接续上文，不要道歉，切碎任务后继续*”）并原地 `continue`（最多 3 次）。
*   **Model Fallback**：若模型请求中断或不可用，拦截 `FallbackTriggeredError`，切换备用模型并原地 `continue`。
