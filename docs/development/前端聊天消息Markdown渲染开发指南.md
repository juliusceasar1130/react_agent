# 前端聊天消息 Markdown 渲染开发指南

修改时间: 2026-04-01 23:25 Asia/Shanghai

主要修改内容:
- 沉淀前端聊天消息从纯文本展示升级为 Markdown 展示的实现方法
- 记录“流式阶段纯文本、完成态再渲染”的分层设计与原因
- 总结 Markdown 安全清洗、消息组件接入和业务报表风格样式的复用套路
- 明确本次实现的验证结果、边界条件与后续复用注意事项

## 1. 背景

聊天类前端在最初实现时，通常会把模型回复直接按纯文本输出，这样接入简单、流式展示稳定，但当回复里开始出现 `**标题**`、表格、列表、代码块等结构化内容时，阅读体验会明显下降。对于统计结果、异常分析、SQL 摘要这类偏“结果呈现”的场景，纯文本尤其不利于快速扫读。

本次改造的背景，是前端已经具备稳定的会话与流式输出链路，但最终结果展示仍然是字符串直出，导致 Markdown 语义无法转成可视化结构。同时，聊天场景又不同于 Markdown 编辑器场景，不需要沉重的编辑能力，而更需要轻量、安全、观感舒服的展示能力。

如果不做这层改造，模型即使输出了结构化 Markdown，用户看到的仍然只是带符号的原始文本，尤其在表格和业务统计类内容上，信息密度高但可读性差，影响最终使用体验。

## 2. 这套方案解决什么问题

- 让助手最终回复中的粗体、列表、表格、代码块和链接能够按 Markdown 语义展示
- 避免在流式生成阶段频繁重排 HTML，保持打字效果稳定
- 通过 `DOMPurify` 对渲染后的 HTML 做安全清洗，降低 `v-html` 带来的 XSS 风险
- 为业务统计、异常汇总、分析说明等结果提供更适合扫读的“业务报表风格”样式
- 保持改动集中在前端渲染层，不影响后端消息协议
- 为后续其他“聊天结果结构化展示”能力提供统一接入模板

## 3. 整体设计

这次实现采用了“3 层分工”：

1. Markdown 渲染层
2. 消息展示分支层
3. 报表化样式层

这个分层的关键思想是：
**把“文本内容的生成”和“最终态的结构化展示”解耦，流式阶段求稳定，完成阶段求可读。**

## 4. 核心调用链 / 执行流

1. 后端仍按原有协议返回消息内容，`content` 字段不变。
2. 前端消息组件 [frontend/src/components/MessageItem.vue](F:\000_dev\Python\workplace\rearch_agent\.tree\features\agent\frontend\src\components\MessageItem.vue) 先通过 `streamingState` 判断当前消息是否处于流式生成阶段。
3. 如果是用户消息或流式中的助手消息，组件继续走纯文本分支，用 `{{ content }}` 展示。
4. 如果是助手完成态消息，组件调用 [frontend/src/utils/markdown.ts](F:\000_dev\Python\workplace\rearch_agent\.tree\features\agent\frontend\src\utils\markdown.ts) 中的 `renderMarkdown(content)`。
5. `renderMarkdown` 先用 `markdown-it` 把 Markdown 转成 HTML，再用 `DOMPurify` 做 HTML sanitize。
6. 清洗后的 HTML 通过 `v-html` 注入到 `message-markdown` 容器中。
7. [frontend/src/style.css](F:\000_dev\Python\workplace\rearch_agent\.tree\features\agent\frontend\src\style.css) 中的 `.message-markdown` 系列样式对段落、表格、列表、代码块、引用和链接做统一视觉呈现。
8. 对于偏统计类表格，样式层额外做了“第二列数字右对齐、等宽数字、说明列放宽换行”的业务报表风格增强。

正确链路是：

- 流式阶段只展示纯文本
- 完成态再做 Markdown 渲染

不建议走的旧链路是：

- 从流式第一帧开始持续把增量内容转成 Markdown HTML 并实时重绘

因为这样更容易出现闪动、滚动抖动、半截表格被重复重排等问题。

## 5. 分层职责说明

### 5.1 Markdown 渲染层

入口文件：

- `frontend/src/utils/markdown.ts`

职责：

- 创建统一的 `markdown-it` 实例
- 负责 Markdown -> HTML 转换
- 负责 `DOMPurify` 安全清洗
- 为链接自动补充 `target="_blank"` 与安全 `rel` 属性

为什么这样设计：

- 把渲染与安全逻辑从组件中抽离，避免 `MessageItem.vue` 里混入过多解析细节
- 便于后续在其他消息卡片、预览面板、说明区块中复用同一套能力

设计经验：

- 只要项目里存在多个 Markdown 展示入口，就应该尽早把渲染与 sanitize 逻辑做成单独工具模块。

### 5.2 消息展示分支层

入口文件：

- `frontend/src/components/MessageItem.vue`

职责：

- 判断消息角色和消息状态
- 保留用户消息与流式助手消息的纯文本展示
- 仅对助手完成态消息启用 Markdown HTML 渲染

为什么这样设计：

- 流式文本是“过程态”，重点是稳定和即时反馈
- 完成态消息是“结果态”，重点是结构化和可读性

设计经验：

- 在聊天场景里，不要把“流式体验”和“最终展示体验”混成一个策略，分开处理更稳。

### 5.3 报表化样式层

入口文件：

- `frontend/src/style.css`

职责：

- 统一定义 `.message-markdown` 的排版规则
- 优化标题、列表、引用、代码块、链接的阅读体验
- 将常见统计表格增强为更贴近业务报表的视觉风格

为什么这样设计：

- Markdown 解析器解决的是“结构语义”，真正决定“舒服不舒服”的主要还是样式层
- 统计类结果与博客文章的阅读方式不同，更需要扫读效率而不是装饰感

设计经验：

- 想要“看起来舒服”，不要先换解析器，先把样式目标定清楚：是文档风格，还是业务报表风格。

## 6. 关键设计取舍

### 6.1 选择 `markdown-it + DOMPurify`

选择：

- 使用 `markdown-it` 负责解析，`DOMPurify` 负责安全清洗

原因：

- 这是前端展示型 Markdown 场景中比较轻量、成熟、可控的组合
- 当前项目只需要展示，不需要 Markdown 编辑器能力

收益：

- 接入成本低
- 表格、列表、链接、代码块支持足够
- 逻辑集中，便于维护

代价：

- 如果未来需要 AST 级自定义规则，可能需要再引入 `remark/rehype` 一类更重的工具链

### 6.2 只在完成态启用 Markdown 渲染

选择：

- 用户消息与流式消息继续纯文本，助手完成态再转 Markdown

原因：

- 流式过程中内容是不完整的，Markdown 结构经常处于半闭合状态
- 提前渲染会导致布局不断跳动

收益：

- 打字体验稳定
- 最终结果可读性高
- 实现简单，状态边界明确

代价：

- 用户在生成过程中看到的仍然是原始 Markdown 文本，而不是最终格式

### 6.3 用样式做“业务报表风格”，不改消息协议

选择：

- 不要求后端输出额外结构化字段，仍基于 Markdown 文本渲染

原因：

- 当前问题是展示层问题，不是协议表达能力不足
- 保持协议不变，前后端耦合最小

收益：

- 改动范围小
- 不影响后端和数据库存储
- 后续可以按同一套路继续增强其他 Markdown 内容

代价：

- 某些更强的“字段级样式语义”只能通过 CSS 约定做近似处理，而不是精确的结构化控制

## 7. 实践中的关键经验

### 7.1 聊天消息的 Markdown 渲染重点不在解析，而在分支时机

现象：

- 如果只从“能不能把 Markdown 转成 HTML”思考，很容易忽略流式阶段的体验问题

原因：

- 聊天消息存在明显的过程态和结果态，展示策略不能完全复用静态文档页

经验结论：

- 聊天场景优先先决定“什么时候渲染”，再决定“用什么渲染”。

### 7.2 `v-html` 不是不能用，但必须配 sanitize

现象：

- Markdown 最终通常要落到 `v-html`，否则无法展示真实 HTML 结构

原因：

- Vue 模板插值会自动转义，不适合直接展示解析后的标签结构

经验结论：

- 只要用了 `v-html`，就默认要有 `DOMPurify` 之类的安全清洗层，不要直接信任模型输出。

### 7.3 业务报表风格的关键是“扫读效率”

现象：

- 同样一段 Markdown，博客风格和报表风格给人的阅读感完全不同

原因：

- 统计结果通常是为“快速判断”服务，而不是为“慢速阅读”服务

经验结论：

- 表头、数字列、说明列、模块标题的视觉层次，比花哨装饰更重要。

### 7.4 样式层可以做轻度业务假设，但要知道边界

现象：

- 本次样式对第二列做了数字列右对齐增强，比较适合“类型 / 数量 / 说明”这类表格

原因：

- 当前业务截图就是这一类典型统计表格

经验结论：

- 可以针对主要业务场景做适度样式优化，但要在手册里写清楚这种假设，不要误以为适合所有 Markdown 表格。

## 8. 易错点 / 反模式

- 直接把消息内容用 `{{ content }}` 输出，并期待 Markdown 自动生效：不会生效，只会原样显示。
- 对渲染后的 HTML 直接 `v-html` 注入而不做清洗：存在安全风险。
- 在流式阶段持续做 Markdown 重渲染：容易导致闪动、滚动抖动和半成品结构不断重排。
- 只引入 Markdown 解析库，不补样式：功能上“能渲染”，观感上仍然不舒服。
- 过度把表格样式写死成某一种业务格式：会压缩其他 Markdown 内容的适配空间。
- 忽略现代 CSS 特性的兼容边界：例如 `:has()` 在旧浏览器环境下需要额外评估。

## 9. 推荐复用模板 / 标准做法

1. 先确认场景是“纯展示”还是“编辑 + 预览”。
2. 如果只是聊天结果展示，优先使用 `markdown-it + DOMPurify` 这种轻量组合。
3. 新增一个独立的 Markdown 工具模块，统一封装渲染和 sanitize。
4. 在消息组件中只对“完成态消息”接入 Markdown 渲染，流式阶段保留纯文本。
5. 单独为 Markdown 容器定义样式类，不要把样式零散写到多个组件分支中。
6. 如果业务里存在统计表格、异常汇总、摘要报告，再额外做“报表风格”增强。
7. 构建完成后，至少验证一次生产构建是否通过。

可以直接复制的部分：

- `frontend/src/utils/markdown.ts` 的渲染与清洗结构
- `MessageItem.vue` 中“流式文本 / 完成态 Markdown”分支思路
- `.message-markdown` 的基础排版规则

必须按场景调整的部分：

- 表格列样式假设
- 标题强化方式
- 代码块、链接、引用块的品牌色和视觉语言

## 12. 后续可选优化方向

- 为“数据说明 / 总结说明”类段落增加摘要块样式，让报表说明区更突出
- 针对代码块接入语法高亮
- 评估是否需要对不同类型表格引入更细粒度的样式 class 或约定
- 如果后续需要更复杂的 Markdown 扩展，再评估升级到 `remark/rehype`
- 如果需要兼容更老的浏览器，评估替换或降级 `:has()` 相关样式策略

## 13. 一句话总结

聊天消息 Markdown 展示真正可复用的关键，不是“把文本转成 HTML”，而是：
**把流式过程态和最终结果态拆开处理，再用安全渲染和目标明确的样式去承接最终内容。**
