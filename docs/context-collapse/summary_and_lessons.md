## 一、 大模型会话管理中的三大精简机制

在长对话 ReAct 纠错环路中，我们建立了一套**串行互斥、职责分层**的消息精简体系，由以下三种机制协同工作：

### 1.1 窗口内 Linter 重试抹除 (Redaction)
* **作用范围**：当前对话轮次（最后一条 `HumanMessage` 之后）的最新 ReAct 重试区间内。
* **触发机制**：当前轮次尚未成功时，保留最近 $N$ 个（默认 3）失败尝试作为大模型的改错参考线索。对于超过 $N$ 个的更早失败，**仅抹除 AI 的思考（`AIMessage.content`）与工具的报错（`ToolMessage.content`）**，将其重写为精简占位符。
* **核心价值**：既释放了大量冗余报错（往往几百 Token）带来的空间压力，又保留了历史工具调用的参数痕迹，同时提供了最近几次报错的对比推理线索。

### 1.2 窗口外辅助工具及陈旧失败成对物理删除 (Physical Deletion)
* **作用范围**：滑动窗口保护范围之外（已过期的历史对话轮次中）的物理词典检索工具对，以及失败的 SQL / 图表 / CSV 导出等工具对。
* **触发机制**：遍历滑动窗口外的陈旧消息，识别出：
  1. 三层检索工具 (`search_db_value_lexicon`, `search_db_row_lexicon`, `search_db_table_schema`，定义在 `ULTIMATE_DELETION_TOOLS` 中) 的调用对（无视成功或失败，一律物理删除）。
  2. `sql_db_query`、`build_chart_artifact` 以及 `export_to_csv` 等支持静态拦截/运行时报错工具的失败调用对。
  在模型调用前，将这几类 `ToolMessage` 及其发起的 `AIMessage` **成对从消息列表中彻底 Pop 过滤移除**。
* **核心价值**：对于已经过期、且已没有参考价值的失败历史，直接进行“物理删除”能实现最大化的 Token 节省，并避免陈旧垃圾干扰模型的注意力。

### 1.3 窗口外历史成功常规折叠 (Collapse)
* **作用范围**：滑动窗口保护范围之外的、不可物理删除的成功工具调用对（如成功 SQL、SQL 案例检索等）。
* **触发机制**：对未被物理删除的历史成功 SQL 结果、案例检索成功骨架（`search_saved_correct_tool_uses`）及 CSV 导出数据，仅重载其 `ToolMessage.content`，替换为极简文本（例如：`[SQL execution successful. Result content collapsed.]`）。
* **核心价值**：保护“推导链条连续性”。由于模型后续的回答依赖这些成功拿到的数据，它们在物理上不能被删除，只能对内容进行占位折叠，防止大模型发生幻觉或逻辑断裂。

### 1.4 核心定义与判定边界
为确保三大精简机制安全、幂等运行，系统底层对以下三个关键定义进行了高保真限定：

#### A. 什么是“成功”的判定？
系统采用**反向排除法**定义 SQL 工具执行成功：
* **定义**：只有**既非 Linter 拦截错误（`is_linter_error = False`），又非数据库运行时错误（`is_runtime_error = False`）**的 SQL 查询对，才算成功（`is_failed = False`）。
* **排查特征**：排除含 `X-SQL-LINTER-STATUS: FAILED` 协议头、`validation failed by Linter` 占位符、以及含 `error`/`exception` 底层报错的 SQL 执行。

#### B. 成功后保留多少消息？
一旦判定本轮 ReAct 纠错重试中**产生了成功 SQL**：
* **本轮失败清零**：本轮提问后产生的所有失败尝试（无论新旧）**全部在 Stage 3 被抹除折叠**，只保留该唯一的成功 SQL 对（保留失败对 = 0）。
* **历史成功折叠**：当该成功对在后续提问后落入滑动窗口外，它不会被物理删除，而是**进入 Stage 5 被常规折叠为骨架占位符**，保留 `tool_calls` 参数和 `ToolMessage` 骨架以保证推导链路完整。

#### C. 什么是“最后一条提问之后”的物理范围？
它在消息队列（`messages` 列表）中物理定位为：**从列表中最后一条最新出现的 `HumanMessage` 索引（`last_human_idx`）开始，直到列表最末尾的全部区间。**

```text
[0] HumanMessage 1: "提问 A"
[1] AIMessage A1 (SQL) -> [2] ToolMessage (成功数据)
[3] AIMessage A2 (回答)
[4] HumanMessage 2: "提问 B"  <-- 🎯 last_human_idx（最新提问起点）
[5] AIMessage B1 (SQL)     <-- ⚡【最后一条提问之后】的 ReAct 重试区间
[6] ToolMessage (失败)      <-- ⚡
[7] AIMessage B2 (SQL)     <-- ⚡
[8] ToolMessage (失败)      <-- ⚡
```
在 `_stage_redaction` 处理中，所有的保留集计算与最新重试失败检测**只在 [5]~[8] 区间内扫描**，前序的 [0]~[3] 被物理隔离，杜绝跨轮次污染。

## 二、 重大漏洞复盘与原因分析 (Lessons & Gotchas)

在迭代开发与优化过程中，我们遭遇并解决了以下四个由于“状态共享”和“消息重入”引发的经典设计漏洞：

### 2.1 大模型失控模仿 `-- redacted --` 与参数丢失 Bug
* **现象**：在抹除历史失败的 `AIMessage` 时，如果我们简单粗暴地将 `AIMessage` 替换为没有任何参数的纯文本（如 `AIMessage(content="[-- redacted --]")`），大模型在后续回答中会产生认知失调，并去刻意模仿这种中括号格式，导致其随后的工具调用丢失了 `required_skill` 或 `query` 等必需参数，系统抛出 Pydantic 参数校验异常。
* **原因**：大模型是通过上下文模仿来进行工具调用的。如果我们把历史真实工具调用的骨架给抹除了，模型就会忘记该如何正确发起工具调用。
* **启示与方案**：**只抹除思考，原样保留工具参数结构。** 采用 `tool_calls=aimsg.tool_calls` 保留参数结构，只重载清空 `content` 思考，从根本上杜绝了模型的失控模仿风险。

### 2.2 已折叠历史特征丢失引发的“重入误判” Bug
* **现象**：随着 ReAct 纠错重试超过 3 次，原本工作良好的“保留最新 3 次失败”逻辑突然失灵，连最新、最关键的一次数据库报错也被提前折叠抹成了占位符，导致大模型彻底丢失报错线索。
* **原因**：在多次 ReAct 循环中，中间件会重入执行。当最老的失败被抹除为 `[SQL validation failed by Linter...]` 占位符后，其原始的技术协议头 `X-SQL-LINTER-STATUS: FAILED` 随之丢失。在下一次模型调用重入扫描时，该历史失败被误判定为了 `is_linter_error = False`（即判定为了成功 SQL），导致系统误以为本轮已经成功，从而把当次最新的报错也给抹除清扫了。
* **启示与方案**：**特征提取必须兼容占位符格式。** 规则判定不能仅看原始标头，必须将改写后的占位符 `"validation failed by Linter"` 也纳入 `is_linter_error` 的兼容检测，确保在多次重入扫描时状态判断依然 100% 幂等。

### 2.3 数据库运行期报错被误判定为 SQL 执行成功 Bug
* **现象**：当 SQL 执行触发了数据库底层运行时报错（如 `UndefinedColumn`）而非 Linter 静态拦截时，前面的 Linter 报错会被立刻误折叠抹除。
* **原因**：原本的“成功 SQL”判定逻辑过于粗糙——它认为只要不是 Linter 拦截的 SQL，都算作“成功 SQL”。这导致 `UndefinedColumn` 运行时报错被误判定为成功，提前终结了纠错重试的保护，破坏了保留集。
* **启示与方案**：**精准分类“报错”与“成功”。** 引入 `is_runtime_error` 检测（是否含 `error`/`exception` 关键字）。将“真正未报错、返回了数据集的 SQL”定义为成功，而将 Linter 拦截和运行期报错均归为“失败尝试”，共同受到 `keep_count` 保护。

### 2.5 多步级联查询下，前置成功误杀后续失败 Bug
* **现象**：在多步 SQL（分步/级联）查询场景中，大模型在 Attempt 1 成功执行并拿到了数据，随后开启下一步的 Attempt 2 查询时被 Linter 拦截。模型面临下一次 API 调用去改错，但它的 `Input` 消息里的 Attempt 2 却已经被系统提前抹除折叠了，导致模型丢失报错线索而纠错失败。
* **原因**：原本的“本轮成功清零”逻辑只作全局成功检测（`successful_sql_call_id is not None`）。由于系统探测到了 Attempt 1 成功，便粗暴认为本轮已经最终终结，直接将所有失败线索抹除，把本应受到保护的最新 Attempt 2 报错给误杀折叠了。
* **启示与方案**：**以“最后一个成功”为时序分水岭物理分流。** 失败尝试根据时序关系被划分为：
  1. **已解决的陈旧失败**：发生在最后一个成功 SQL 之前的失败，代表后续已经改对并成功，属于无用垃圾，全部抹除折叠。
  2. **活跃的重试失败**：发生在最后一个成功 SQL 之后的失败，代表后续新步骤仍在重试，属于最新活跃的纠错线索，必须受到 `keep_count` 额度保护保留。

## 三、 开发注意事项与设计原则

为防范类似问题在今后的会话管理与上下文控制开发中再次发生，必须遵守以下设计军规：

### 3.1 状态重入的幂等性与特征保留原则
在基于 Graph/Agent 节点的循环机制中，中间件或处理拦截器会被频繁地**重复调用（Re-entry）**。
* **规则**：任何对历史消息内容的重写或抹除，必须在重写后的文本中**原样保留可被重新识别的指纹特征**（例如本案中的 `"validation failed by Linter"`）。
* **警惕**：严禁抹除后导致该节点的业务状态属性（如：是否是失败节点）发生改变，否则会在第二次扫描中引发误判雪崩。

### 3.2 严格遵守三方大模型 API 的校验红线
大模型托管商在接收消息队列时，有一套不可违背的格式校验红线：
* **红线**：若 `AIMessage` 中含有 `tool_calls`，后续必须紧跟与之配对的 `ToolMessage`，且它们的 `id` 必须强一致。
* **开发原则**：
  1. **成对物理删除**：过滤时必须同时 Pop 掉 `AIMessage` 与其对应的 `ToolMessage`。
  2. **局部过滤兼容**：若一个 `AIMessage` 触发了多个并发工具调用，物理删除时只能过滤掉失败的那一个 `tool_call` 子项，若所有子项都失败，才可以将整条 `AIMessage` 物理删除。
  3. 绝对不能执行“单边物理删除”或丢弃对应的 ID 对应关系。

### 3.3 推导链路的连续性保护 (防信息断崖)
大模型的注意力与长上下文逻辑基于完整的会话推导链。
* **规则**：**历史成功的查询结果千万不能删除。** 大模型随后的总结和推理严重依赖这些数据。如果删除了，模型在回溯历史时就会因为数据断崖而产生幻觉或直接编造。
* **应对**：对于成功数据，只能对其 content 进行“内容占位折叠”，而其 `AIMessage` 骨架以及参数、`ToolMessage` 占位符必须保留在消息流中。

### 3.4 跨轮次状态物理隔离原则
在一个长会话窗口内，用户可能会连续提问多个不同的问题。
* **规则**：新问题的发起（即最新的 `HumanMessage`）必须作为一个物理屏障。本轮的 ReAct 重试与自愈轨迹不应该受到任何上一轮历史状态（如上一轮是成功还是失败）的影响。
* **应对**：在扫描重试状态时，首要步骤是定位 `last_human_idx`，一切当前轮状态判定和 kept 集合计算只在其后执行，从根源上消灭跨域污染。

### 3.5 辅助工具极限物理删除的「体积/复用性价比」原则
在精简长对话历史时，不能盲目对所有辅助工具实施一刀切的删除或折叠，应当建立「体积收益 vs 复用价值」的分析维度：
* **体积大、复用低、重复代价小**（如表结构 DDL、字典检索）：一律物理删除。重新检索的计算负担微乎其微，但彻底删除释放了巨大的 Token 空间。
* **体积小、复用高、重复代价大**（如 Few-shot SQL 示例）：采用常规折叠。用最少的占位 Token 在历史中为模型留下一个强有力的“已参考该案例”线索，避免引发大模型认知偏差导致重复发起检索调用。
