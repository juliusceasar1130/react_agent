# 轻量结构化输出：LLM 分析正文与侧信道明细分工渲染方案

> **修订日期**：2026-07-20（v3，吸收 10 号实施计划三类分流演进，修复其数值纪律遗漏与 Top3+其它 过度设计）  
> **方案状态**：设计提案 (PROPOSED v3)  
> **文档位置**：`docs/StructuredOutput/refactor/09_lightweight_structured_output_feasibility.md`  
> **前序讨论**：本方案经多轮反思收敛。核心修正：放弃"砍 LLM 内容、侧信道当主力"的原版定位（会丢失 LLM 综合分析价值），改为"LLM 分析正文为主体、侧信道明细为证据底座"的分工渲染。侧信道不作交互设计重点，但仍承担明细数据呈现。

---

## 一、核心共识与定位

### 1.1 方向共识

经真实交互场景剖析，达成关键共识：**"Prompt 规约 + 前端布局轻改"是当前正确的演进方向，侧信道数据作为底层载体，不作设计重点。**

如果把侧信道数据设计成交互核心主力，聊天助手会异化为"静态数据看板"，削弱大模型对多表横向对比、别名映射、汇总统计的语义分析能力。侧信道只需做好底层数据的证据链保障。

### 1.2 关键澄清："侧信道非重点"的含义

"侧信道不是重点"指**不过度设计其交互**（不搞复杂筛选/列拖拽/单元格编辑等），**不是"不渲染明细"**。侧信道表格仍承担"明细数据呈现"的职责，作为 LLM 分析正文的证据底座。即：

| 角色 | 承担方 | 内容 |
|---|---|---|
| 分析主体 | LLM 正文 | 综合分析、派生指标、对比、趋势洞察、必要的汇总透视表 |
| 明细底座 | 侧信道表格 | 单次查询的原始行级数据（分页/搜索/导出，交互从简） |

### 1.3 为什么"轻量"可行而历史"重量级"失败（核心论证）

项目在 2026-07-12 走过 `ToolStrategy(Union[StructuredDataResult, FreeMarkdownResult])` + LangGraph 状态图 + 动态 bind_tools 的**重量级**路线，最终未落地。`Agent_结构化输出流程机制与工具竞争分析报告.md` 记录了三个致命问题。本轻量方案如何规避：

| 重量级的坑 | 根因 | 本方案如何规避 |
|---|---|---|
| `TypeError: NoneType has no len()` | Pydantic `None` 序列化 + `.get()` 不返回默认值 | LLM 不产 schema，无 None 字段 |
| 模型调 `FreeMarkdownResult` 提前交卷 | 终态工具与业务工具扁平暴露，逃避 SQL 推理 | 不引入终态格式化工具，工具集不变 |
| 流式打字机被抑制 | Schema 校验需等完整 JSON/tool-call payload | LLM 仍流式输出自然语言 token，打字机保留 |

**"轻量"的本质**：LLM 不承担结构化责任，仍输出自然语言；结构化明细数据走已验证的 `tool_artifact` 侧信道（04/05/06 落地）。LLM 只退化为"写分析"，精确行级数据由表格承载。这一退化同时强化了 `base_system_prompt.md:16` 的数值纪律红线。

## 二、方案设计

### 2.1 步骤 1：Prompt 规约--按三大类意图分流输出格式

修改 `base_system_prompt.md` §4.4。原规则一刀切要求常规查询以 Markdown 表格呈现，现改为按用户提问意图进行精确的格式分流：

**A. 数据明细查询类**（用户提问指向"明细/列表/有哪些/明细流水"）：
- LLM 正文**严禁打印任何明细表格**，字数控制在 150 字/3 行以内，只提供简短的汇总概述（如总数、时间跨度、车辆特征等）。
- 行级明细数据物理上完全交由正下方的系统交互卡片渲染。

**B. 数据分析与统计对比类**（用户提问指向“分析/为什么/趋势/统计/对比/排名”）：
- LLM 正文不限制行数，应发挥其语义分析长处，输出高密度的**汇总透视表**（推荐 2~10 行，上限 30 行）用于横向对比，表头使用字段中文名。若分类过多逼近上限，应改用更粗粒度分组或只给定性结论 + 引导查看明细，**禁止**自行做“Top3+其它”式二次聚合（属 LLM 派生计算，放大数值纪律风险）。
- 同时在正文中提供**深度分析与洞察结论**（例如缺陷波动原因分析、质量问题归因诊断），让数据分析有血有肉，表格作为分析论据存在。归因诊断中出现的具体数字须遵守 §2.2 数值纪律。

**C. 开放问题与知识问答类**（用户提问指向"概念解释/你好/业务术语/如何计算/说明"，未查询数据库）：
- LLM 正文采用**标准的富文本 Markdown 回答**，完全不受任何字数或行数限制，确保专业术语的解释深度、公式推导与背景说明完整度。

**示例（B 类）**：
```markdown
本月各车型缺陷率对比，Model Y 缺陷率最高：

| 车型 | 缺陷数 | 产量 | 缺陷率 |
| :--- | :--- | :--- | :--- |
| Model Y | 120 | 2000 | 6.0% |
| Model 3 | 45 | 1800 | 2.5% |

缺陷率 = 缺陷数 / 产量，明细见下方表格。
```

### 2.2 步骤 2：数值纪律边界（关键约束）

汇总透视表与深度归因诊断中的数字是 LLM 基于查询结果的**派生计算**，存在算错风险，踩 `base_system_prompt.md:16` 数值纪律红线。Prompt 须明确约束：

1. 汇总数字与归因中引用的具体数值**必须直接来自当轮刚执行的 SQL 查询结果的聚合**，严禁基于对话记忆、历史示例或猜测补造。
2. **若对派生数字不确定，宁可省略具体数值只给定性结论**（如“Model Y 缺陷率明显高于 Model 3”），并引导用户核对下方明细表。
3. 汇总表与下方明细表口径若不一致，以明细表（原始数据）为准。
4. 归因诊断的“原因/解释”部分若无法从数据直接得出，必须明确标注为推测，不得当作事实陈述。

这条边界让 LLM 保留分析能力（含深度归因）的同时，不破坏数值纪律--原始数据可信（侧信道），派生数据可错（LLM）但有原始数据兜底验证。

### 2.3 步骤 3：前端分工渲染与时序协调

**现状**（已核实）：`MessageItem.vue:290-348` 的 `query_result` 表格是独立 `<details>` 折叠区（不在工具调用 debug 区），默认折叠。

**轻改**：
- 侧信道表格从折叠态改为**默认展开**，作为 AI 文本正文下方的"数据证据卡片"贴合展示。
- 交互从简：保留分页、全局搜索、CSV 导出；不增加复杂交互（列拖拽、单元格编辑等），呼应"侧信道非重点"。
- 前端 markdown 渲染样式增强：对 LLM 正文的汇总表、洞察列表做视觉分层（表格美化、间距），**不做正则反刮结构识别**（避免 `extractMetaData` 脆弱链路复辟）。
- **语义化标题 (Semantic Headings) 落地**：为 `.message-markdown h3` 样式增加左侧青色 (Teal) 3px 竖线及 padding 缩进。引导 LLM 在正文中使用标准的 `### 小标题` 代替 `>` 引用块来切分子主题，提供符合 HTML/Markdown 标准的最佳实践排版。
- **Layout Shift 防抖动**：当侧信道明细表格在 AI 文本 Token 尚未生成完毕前即已渲染时，在上方文本流式区放置一个微动的加载占位骨架屏（Skeleton）维持高度占位，消灭页面高度的闪烁与剧烈抖动。

**流式时序协调**：
- `tool_artifact` 在 `updates` chunk 发出（`services.py:803-809`），**先于** AIMessage 文本 token。
- 布局采用 **AI 文本在上、表格在下**（符合"分析主体在上、证据在下"的阅读理念）。
- 时序实现：`tool_artifact` 到达即在下区渲染表格，AI 文本 token 流式追加在上区。中间态（表格先出、文本后到）短暂可接受--工具执行完毕即生成文本，间隔极短。
- 若实测中间态体验不佳，降级方案：改为表格在上、文本在下（流式最自然，无需协调），但偏离"分析主体在上"理念。这是可切换的实现细节，不阻塞方案。

## 三、不解决的问题与边界（诚实取舍）

本方案是"输出规范与渲染优化"，非"数据通道重构"。以下问题**不在本方案范围**：

| 问题 | 现状 | 本方案处理 |
|---|---|---|
| 多结果集 `_last_wins` | `state.py:45` 后写覆盖前写，一轮多次查询只留最后一个 | 不解决。跨表对比场景由 LLM 正文承担（可打对比表），明细只展示最后一次查询 |
| 历史消息表格丢失 | `tool_artifact` 不入库（`models.py` 无此列），历史会话重开表格消失 | 不解决。留待 P2 `QueryResult` 落库方案统一处理 |
| LLM 不遵循 prompt 仍打明细大表 | prompt 是软约束 | 降级：前端表格照常渲染，LLM 表格作为正文 markdown 渲染（冗余但不冲突）；后续可加"正文表格检测折叠"增强 |
| 打字机延迟 | A 类查询已消除（不复述明细）；B 类查询仍有（汇总表小，延迟可控） | 接受 |

**收益边界**：本方案解决"明细冗余复述"+"输出结构规范"+"视觉分层"；**不解决**数据幻觉（靠数值纪律约束，非根治）、不解决派生数据可交互性（汇总表仍是 markdown）。
