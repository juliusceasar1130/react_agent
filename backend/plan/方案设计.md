# 业务知识 RAG 中间件方案设计

## 1. 背景与目标

### 1.1 背景
当前 SQL Agent 系统通过 `SkillMiddleware` 注入业务技能描述，但这种方式存在以下限制：
- 技能描述是静态的、预定义的
- 无法根据用户查询动态检索相关业务知识
- 业务知识库更新后需要手动更新技能定义

### 1.2 目标
实现一个业务知识 RAG（Retrieval-Augmented Generation）中间件，能够：
- 根据用户查询动态检索相关业务知识
- 将检索到的业务知识自动注入到 Agent 的上下文中
- 与现有的 `SkillMiddleware` 协同工作，提供更丰富的业务上下文

## 2. 技术方案

### 2.1 架构设计

```
用户查询
    ↓
BusinessRagMiddleware.before_model()
    ↓
向量检索 (vector_store.similarity_search)
    ↓
格式化检索结果
    ↓
注入为 SystemMessage 到 messages 列表
    ↓
Agent 处理（包含业务知识上下文）
```

### 2.2 核心组件

#### 2.2.1 BusinessRagMiddleware
- **位置**: `backend/app/agent/middleware/rag_middleware.py`
- **职责**: 
  - 在 `before_model` 钩子中检测用户消息
  - 执行向量检索获取相关业务知识
  - 将检索结果格式化为系统消息并注入到 messages
- **特点**:
  - 只在用户消息时触发检索（避免工具调用时重复检索）
  - 自动去重，避免重复添加业务知识系统消息
  - 支持替换已存在的业务知识系统消息

#### 2.2.2 向量存储配置
- **向量库**: Chroma（已存在 `chroma_langchain_db` 目录）
- **Embedding 模型**: DashScope `text-embedding-v3`
- **检索参数**: 
  - `k=5`（默认检索 5 条最相关的文档）
  - 可根据需要调整

#### 2.2.3 状态扩展
- **扩展 CustomState**: 添加 `rag_context` 和 `rag_query` 字段
  - `rag_context`: 存储检索到的文档列表
  - `rag_query`: 存储触发检索的用户查询

#### 2.3.2 消息去重机制
- 使用标识符 `__business_rag_context__` 标记业务知识系统消息
- 检查 messages 中是否已存在该标识符
- 如果存在则替换，否则在开头添加

#### 2.3.3 知识格式化

- 添加明确的提示，引导 Agent 使用这些知识

## 3. 集成方案

### 3.1 与现有中间件协同
- **SkillMiddleware**: 继续提供静态技能描述
- **BusinessRagMiddleware**: 提供动态业务知识检索
- **SummarizationMiddleware**: 继续处理长对话摘要

### 3.2 中间件执行顺序
```
1. BusinessRagMiddleware.before_model()  # 注入业务知识
2. SkillMiddleware.wrap_model_call()     # 注入技能描述
3. SummarizationMiddleware.before_model() # 处理对话摘要
```

### 3.3 Agent 初始化
在 `SQLAgentService._initialize_agent()` 中：
```python
middleware=[
    BusinessRagMiddleware(vector_store=vector_store),
    summarization_middleware,
    SkillMiddleware(),
]
```

## 5. 数据流

### 5.1 检索流程
```
用户查询文本
    ↓
Embedding 编码
    ↓
向量相似度搜索
    ↓
返回 Top-K 文档
    ↓
格式化文档内容
    ↓
注入到 SystemMessage
```

### 5.2 消息流
```
原始 messages: [UserMessage("查询问题")]
    ↓
BusinessRagMiddleware.before_model()
    ↓
更新后 messages: [
    SystemMessage("业务知识库\n\n[检索到的知识]"),
    UserMessage("查询问题")
]
    ↓
Agent 处理（包含业务知识上下文）
```

## 6. 优势与特点

### 6.1 优势
1. **动态检索**: 根据用户查询实时检索相关业务知识
2. **自动注入**: 无需手动调用工具，自动在模型调用前注入
3. **无缝集成**: 与现有中间件架构完美兼容
4. **智能去重**: 自动处理重复的业务知识系统消息

### 6.2 与工具方案对比
- **工具方案**: 需要 Agent 主动调用检索工具，可能遗漏
- **中间件方案**: 自动注入，确保每次用户查询都有业务知识上下文

### 6.3 与 wrap_model_call 对比
- **wrap_model_call**: 在每次模型调用时注入，但需要修改 ModelRequest
- **before_model**: 在模型调用前修改 state，更符合 LangChain 的设计模式

## 7. 扩展性

### 7.1 未来扩展方向
1. **多向量库支持**: 支持从多个向量库检索并合并结果
2. **检索策略优化**: 
   - 混合检索（向量 + 关键词）
   - 重排序（Reranking）
   - 查询扩展
3. **缓存机制**: 缓存常见查询的检索结果
4. **检索质量评估**: 评估检索结果的相关性，过滤低质量结果

### 7.2 配置化
- 检索参数可配置（k、相似度阈值等）
- 知识格式化模板可配置
- 支持启用/禁用中间件

## 9. 风险与缓解

### 9.1 潜在风险
1. **检索延迟**: 向量检索可能增加响应时间
   - **缓解**: 使用异步检索、缓存机制
2. **检索质量**: 检索结果可能不相关
   - **缓解**: 设置相似度阈值、优化 Embedding 模型
3. **Token 消耗**: 注入的业务知识会增加 Token 消耗
   - **缓解**: 限制检索数量、优化知识格式化

### 9.2 兼容性
- 确保与现有 `SkillMiddleware` 不冲突
- 确保不影响 `SummarizationMiddleware` 的工作
- 确保与 Agent 工具调用流程兼容

## 10. 总结

本方案通过实现 `BusinessRagMiddleware`，在 `before_model` 钩子中动态检索业务知识并注入到 messages，实现了业务知识的自动增强。该方案与现有架构完美兼容，提供了更好的业务上下文支持，提升了 Agent 回答的准确性和相关性。
