# SQL导出文件下载开发指南

修改时间: 2026-04-01 00:30 Asia/Shanghai

主要修改内容:
- 沉淀本次 SQL 导出文件下载能力的完整开发经验
- 总结后端导出、文件元数据管理、下载接口与前端下载卡片的设计取舍
- 提供后续在其他 Agent / Chat / 报表场景中复用的实现模板与检查清单

---

## 1. 背景

在 SQL Agent 场景里，用户经常会提出两类需求：

1. 先在聊天窗口里快速看结果摘要
2. 再把完整明细导出来，拿去 Excel、BI 或其他系统继续处理

如果直接把完整大结果塞回 LLM 上下文，会遇到几个问题：

- 上下文膨胀，推理成本高
- 大模型基于截断数据做汇总，容易产生错误结论
- 前端无法稳定展示几十万行明细
- 即使后端落盘了 CSV，如果只把服务器路径告诉前端，客户端也无法直接下载

因此，本次实现的核心目标不是“单纯导出 CSV”，而是打通一条完整链路：

`Agent 工具导出 -> 后端安全映射 -> 前端消息识别 -> 用户点击下载`

---

## 2. 这套能力解决什么问题

本次导出下载能力主要解决以下问题：

- 大结果集不再进入 LLM 上下文
- 前端不需要知道服务器绝对路径
- 会话消息中可以直接出现“下载 CSV”入口
- 流式和非流式聊天链路都能复用同一套导出结果结构
- 文件下载入口具备基本的安全边界与过期控制

---

## 3. 当前项目中的整体设计

这次实现采用了“四层分工”：

1. **查询限流层**
   - `sql_db_query` 在结果过大时不再全量回吐，而是返回预览 + `SYSTEM WARNING`
2. **导出工具层**
   - `export_to_csv` 直接从数据库拉全量数据并落盘 CSV
3. **文件元数据层**
   - 为每个导出文件分配 `file_id`
   - 用 sidecar JSON 保存文件元数据
4. **下载展示层**
   - 后端提供 `GET /api/chat/files/{file_id}`
   - 前端在聊天消息中识别导出结果并渲染下载卡片

这个分层的关键思想是：

**让大模型只处理“导出文件的指针（pointer）”，而不是处理文件内容本身。**

---

## 4. 核心调用链

当前项目里，一次完整的导出下载链路如下：

1. 用户发起查询请求
2. Agent 调用 `sql_db_query`
3. `sql_db_query` 发现结果达到硬限制，返回 `SYSTEM WARNING`
4. 系统提示词引导 Agent 改为调用 `export_to_csv`
5. `export_to_csv` 执行 SQL、写入 CSV 文件
6. 后端为 CSV 生成 `file_id` 与元数据
7. `export_to_csv` 将结构化导出结果作为工具结果返回
8. 聊天消息落库时，`tool_results` 中保留该结构化结果
9. 前端渲染消息时识别 `export_to_csv` 的结果
10. 用户点击“下载 CSV”
11. 浏览器请求 `/api/chat/files/{file_id}`
12. 后端读取元数据并返回 `FileResponse`

可以把它理解成：

`数据库大结果 -> CSV 文件 -> file_id -> 下载接口 -> 浏览器下载`

而不是：

`数据库大结果 -> LLM -> 前端文本展示`

---

## 5. 后端分层设计

### 5.1 查询限流层：`sql_tools.py`

入口文件：

- `backend/app/agent/tools/sql_tools.py`

职责：

- 检测结果是否超过 `sql_result_hard_limit`
- 超限时只返回预览数据
- 明确告诉 Agent：不要基于截断数据汇总，应改用聚合 SQL 或 `export_to_csv`

这一步很关键，因为它不是直接“自动导出”，而是把导出动作留给 Agent 自主决策。这样可以避免：

- 用户只想看摘要时，也被强制导出文件
- 轻量查询场景被过度工程化

设计经验：

- 限流层负责“发现问题并给策略”
- 导出层负责“执行导出”
- 两层不要混在一起

### 5.2 导出工具层：`csv_export_tool.py`

入口文件：

- `backend/app/agent/tools/csv_export_tool.py`

职责：

- 校验是否为只读 SQL
- 校验业务技能是否已加载
- 直接使用 SQLAlchemy 执行查询
- 使用 `csv` 模块写入 CSV 文件
- 调用文件元数据层创建 `file_id`
- 返回结构化导出结果

为什么导出工具要独立存在：

- 它和普通 `sql_db_query` 的目标完全不同
- 它不应该把全量结果重新放回大模型上下文
- 它的成功输出应该是“文件句柄/文件指针”，而不是“查询结果文本”

### 5.3 文件元数据层：`export_files.py`

入口文件：

- `backend/app/export_files.py`

职责：

- 统一导出目录
- 生成 `file_id`
- 落盘导出元数据 JSON
- 根据 `file_id` 反查真实文件路径
- 做基础校验：
  - `file_id` 格式是否合法
  - 文件是否存在
  - 是否已过期
  - 文件路径是否仍位于受控导出目录内

为什么这里单独做一层，而不是让下载接口直接拼路径：

- 避免前端或调用方构造任意文件路径
- 后续更容易切换到数据库、对象存储或 Redis 元数据
- 文件下载逻辑不必和 Agent 工具代码耦合

### 5.4 下载接口层：`api.py`

入口文件：

- `backend/app/api.py`

职责：

- 暴露 `GET /api/chat/files/{file_id}`
- 将 `file_id` 解析为真实文件
- 根据不同失败场景返回合理 HTTP 状态：
  - `400`: `file_id` 非法
  - `404`: 文件不存在或已被清理
  - `410`: 文件过期
- 使用 `FileResponse` 返回下载文件

这层的价值是把“受控文件下载”标准化，避免聊天前端去理解服务器文件系统。

---

## 6. 前端分层设计

### 6.1 下载入口封装

入口文件：

- `frontend/src/api/exports.ts`

职责：

- 构造 `/rearch/api/chat/files/{file_id}` 下载地址
- 提供统一的下载触发方法

为什么要单独抽 API 文件：

- 避免把下载 URL 拼接散落在组件里
- 后续若改为 token 鉴权、blob 下载或多环境域名切换，修改点更集中

### 6.2 消息识别与下载卡片

入口文件：

- `frontend/src/components/MessageItem.vue`
- `frontend/src/types/index.ts`

职责：

- 从消息的 `tool_calls` / `tool_results` 中找到 `export_to_csv`
- 将其对应的字符串结果解析成 `ExportArtifact`
- 在普通聊天消息下方渲染下载卡片
- 展示文件名、行列数、大小、过期时间等信息
- 点击按钮后触发浏览器下载

为什么把下载卡片放在消息组件里：

- 导出动作是一次聊天轮次的产物，语义上属于消息内容的一部分
- 流式和非流式消息最终都会进入统一的消息展示层
- 这样比在全局通知栏或其他页面单独显示更自然，也更容易追溯“这个文件是由哪次提问导出的”

## 7. 为什么这次选择“结构化 JSON 字符串”

这是这次开发里最关键的设计取舍之一。

当前聊天消息和流式协议里，`tool_results` 的结构仍是：

- `Dict[str, str]`

这意味着工具结果默认是字符串。

如果直接为了导出文件重构整个流式协议或数据库模型，改动面会很大。所以这次采用了折中但很实用的方案：

1. 保持 `tool_results` 外层结构不变
2. 让 `export_to_csv` 的结果字符串内部是 JSON
3. 前端只对 `export_to_csv` 的结果做定向解析

这样做的优点：

- 不破坏现有 SSE 协议
- 不破坏消息落库结构
- 流式与非流式链路都能直接复用
- 导出下载能力可以低风险上线

这是一种典型的：

**在既有协议上增加“结构化字符串载荷（structured string payload）”的渐进式扩展策略。**

## 8. 安全设计经验

这次导出功能最大的安全点，不在 SQL 本身，而在“文件如何暴露给前端”。

### 8.1 不要把服务器绝对路径返回给前端

错误做法：

- 返回 `C:\Users\xxx\AppData\Local\Temp\...`
- 返回 `/tmp/sql_agent_exports/...`

问题：

- 浏览器无法直接访问
- 泄露服务器目录结构
- 给后续路径拼接攻击埋坑

正确做法：

- 返回 `file_id`
- 由后端接口做受控映射

### 8.2 文件路径必须受控

元数据层在解析真实文件时，要确保：

- 最终文件仍位于受控导出目录下
- 不能被 `..` 等路径逃逸手段绕出目录

### 8.3 文件应有有效期

导出文件通常是临时产物，不适合长期堆积。

当前项目通过：

- `SQL_EXPORT_TTL_HOURS`

控制有效期。

经验建议：

- 临时下载类文件默认应有 TTL
- 即使暂时未实现后台清理任务，也应先从读取逻辑上限制过期访问

### 8.4 下载接口只认 `file_id`

不要设计成：

- `/download?path=...`

应设计成：

- `/files/{file_id}`

这样接口语义更清晰，也更容易控制边界。

## 9. 本次实践中的关键经验

### 9.1 “导出成功”不等于“可下载”

很多项目做到“服务器落盘成功”就结束了，但真正交付用户时，最重要的是客户端下载体验。

经验结论：

- 导出功能必须从一开始就把“前端如何拿到文件”纳入设计
- 否则导出只是服务器内部动作，不是完整产品能力

### 9.2 不要把下载能力耦合到聊天主协议重构

如果为了下载文件去重做整套 SSE / message schema，成本太高，也容易引入回归。

经验结论：

- 优先沿用现有消息与工具协议
- 用最小增量方式承载文件 artifact

### 9.3 Agent 工具结果最好返回“可编排对象”而不是“面向人类的纯文本”

如果工具结果只是：

- “文件已导出到 XXX 路径”

那前端几乎无法稳定消费。

如果工具结果是结构化对象：

- `file_id`
- `filename`
- `row_count`
- `col_count`
- `size_bytes`

那前端、日志、后续自动化流程都更容易复用。

### 9.4 文件元数据层值得独立出来

一开始看似只是多写一个 JSON 文件，但它带来的好处很明显：

- 下载逻辑更清晰
- 过期策略更集中
- 后续可平滑迁移到对象存储
- 单元测试边界更明确

### 9.5 消息组件适合承担“文件卡片”这类派生展示

这次前端没有新增复杂页面，只是在消息组件里基于工具结果做增强展示。

经验结论：

- 对话式系统中的“导出物（artifact）”，往往最自然的归宿就是消息本身

## 10. 适合复用的场景

这套模式不只适合 CSV。

后续以下场景都可以复用同样思路：

- 导出 Excel
- 导出 PDF 报表
- 导出日志压缩包
- 导出图片、截图、分析报告
- 生成临时数据包供用户下载

复用时通常只需要替换三件事：

1. 文件生成逻辑
2. `media_type`
3. 前端卡片文案与展示字段

整体骨架可以保持不变：

`工具生成文件 -> file_id -> 元数据 -> 下载接口 -> 消息卡片`

---

## 11. 推荐的复用模板

后续新增其他导出型工具时，建议沿用这个模板：

1. 新增工具
   - 只负责生成文件与返回 artifact
2. 新增元数据管理层
   - 统一校验、过期、路径映射
3. 新增下载接口
   - 用 `file_id` 获取文件
4. 前端新增 artifact 类型
   - 只解析特定工具的特定结果
5. 在消息组件渲染卡片
   - 让下载入口跟随消息上下文

如果规模继续增大，可以进一步抽象成统一的 `artifact` 机制。

---

## 12. 推荐检查清单

后续复用时，建议至少检查下面这些点：

### 后端

- 是否把文件生成与普通查询结果分离
- 是否避免把服务器绝对路径暴露给前端
- 是否为导出文件分配了稳定 `file_id`
- 是否有受控元数据层
- 是否校验了文件路径与过期时间
- 是否为下载接口定义了清晰的错误语义

### 前端

- 是否能稳定识别对应工具结果
- 是否不会误把普通工具结果当成文件 artifact
- 是否为用户展示了足够的文件信息
- 下载按钮是否使用统一 API 封装
- 流式和非流式消息是否都可显示下载卡片

### 协议

- 是否尽量复用现有消息结构
- 是否明确 artifact 的最小字段集合
- 是否为后续扩展预留了 `kind` 字段

---

## 13. 后续可选优化方向

当前实现已经可用，但后续仍有几个可以继续演进的方向：

### 13.1 后台清理任务

目前主要是“读取时判断过期”。后续可增加定时清理：

- 过期 CSV
- 过期元数据 JSON

### 13.2 统一 artifact 协议

当前导出文件只是一类 artifact。后续如果下载型产物变多，可以把消息中的导出物统一成：

- `file_export`
- `report_export`
- `image_artifact`
- `pdf_artifact`

### 13.3 对象存储迁移

如果后续部署为多实例，临时本地目录不再适合作为文件存储。

此时可将元数据层迁移到：

- MinIO
- S3
- OSS

前端和消息卡片层可以基本不动。

### 13.4 鉴权与访问控制

当前下载接口更偏内部系统场景。若后续面向多用户或公网，应继续补充：

- 会话归属校验
- 用户身份校验
- 一次性下载 token
- 审计日志

---

## 14. 一句话总结

导出型功能真正可复用的关键，不是“会不会写文件”，而是：

**是否把文件产物从大模型上下文中抽离出来，并通过结构化 artifact、受控元数据和标准下载接口，把它稳定地交还给前端与用户。**
